Structure tags define the organization of Calor code: modules, functions, and their boundaries.

> **Indent-only block structure.** Calor uses Python-style significant
> indentation: a block opens with `§M`, `§F`, `§CL`, `§L`, `§IF`, … and
> ends at the first line that **dedents** back to the parent column. No
> closing tags are required. The compiler default is `2` spaces per
> nesting level (mixing tabs and spaces is rejected). Legacy structural
> closers (`§/M`, `§/F`, `§/L`, `§/I`, …) were removed and now raise
> `Calor0830`. Bulk-migrate older corpora with
> [`calor fix --heal-closers`](/docs/cli/fix/). The expression closers
> `§/C` and `§/LAM` remain valid.

---

## Modules

Modules are like C# namespaces. They group related functions.

### Syntax

```calor
§M{name}
  // contents
```

### Example

```calor
§M{Calculator}
  // functions go here
```

### Rules

- `name` becomes the C# namespace
- The module block extends until the next line that dedents back to
  column 0 (or end of file)
- A legacy `§/M` closer raises `Calor0830`; migrate with
  [`calor fix --heal-closers`](/docs/cli/fix/)

### Named static containers

A named module inside the compilation unit groups static members and emits as a
C# static class with the same name. The converter uses this existing form for
C# static classes, including nested ones:

```calor
§M{Library}
  §M{Utilities:pub}
    §F{Twice:pub} (i32:value) -> i32
      §R (* value 2)
```

Static `§CL` declarations are rejected with `Calor0107`; replace the container
with `§M` and use `§F` for its functions. An ordinary non-static class may still
have static methods, fields and properties. This does not change namespace-header
syntax.

## Functions

Functions are the primary code containers.

### Syntax

```calor
§F{visibility}
  §I{type:param}       // inputs (0 or more)
  §O{type}             // output (required)
  §E{effects}          // effects (optional)
  §Q condition         // preconditions (0 or more)
  §S condition         // postconditions (0 or more)
  // body
```

### Visibility

| Value | Meaning | C# Equivalent |
|:------|:--------|:--------------|
| `pub` | Public | `public static` |
| `pri` | Private | `private static` |

Members of a class (`§MT`, `§FLD`, `§PROP`, `§CTOR`, `§EVT`, and so on) accept the full set
of C# accessibility levels. Each has a short and a long spelling:

| Short | Long | C# |
|:------|:-----|:---|
| `pub` | `public` | `public` |
| `int` | `internal` | `internal` |
| `prot`, `pro` | `protected` | `protected` |
| `priv`, `pri` | `private` | `private` |
| `prot-int` | `protected-internal` | `protected internal` |
| `priv-prot` | `private-protected` | `private protected` |

Any other word in a visibility slot is error `Calor0122`, and the message lists the
words above. Before 0.27 an unknown word, such as the typo `:bogus`, compiled
silently as `private`.

### Examples

**Simple function:**
```calor
§F{Add:pub}
  §I{i32:a}
  §I{i32:b}
  §O{i32}
  §R (+ a b)
```

**Function with effects:**
```calor
§F{PrintSum:pub}
  §I{i32:a}
  §I{i32:b}
  §O{void}
  §E{cw}
  §P (+ a b)
```

**Function with contracts:**
```calor
§F{Divide:pub}
  §I{i32:a}
  §I{i32:b}
  §O{i32}
  §Q (!= b 0)
  §R (/ a b)
```

## Async Functions

Async functions use `§AF` instead of `§F` and automatically wrap return types in `Task<T>`.

### Syntax

```calor
§AF{visibility}
  §I{type:param}       // inputs (0 or more)
  §O{type}             // output (auto-wrapped to Task<T>)
  // body with §AWAIT expressions
```

### Examples

**Simple async function:**
```calor
§AF{FetchDataAsync:pub}
  §I{str:url}
  §O{str}
  §B{result} §AWAIT §C{httpClient.GetStringAsync} §A url §/C
  §R result
```

Emits C#:
```csharp
public static async Task<string> FetchDataAsync(string url)
{
    var result = await httpClient.GetStringAsync(url);
    return result;
}
```

**Async void function (returns Task):**
```calor
§AF{ProcessAsync:pub}
  §O{void}
  §AWAIT §C{Task.Delay} §A 1000 §/C
```

### Automatic Task Wrapping

| Declared Output | Emitted Return Type |
|:----------------|:--------------------|
| `§O{void}` | `Task` |
| `§O{i32}` | `Task<int>` |
| `§O{str}` | `Task<string>` |
| `§O{Task<i32>}` | `Task<int>` (no double-wrap) |

## Async Methods

Async methods in classes use `§AMT` instead of `§MT`.

### Syntax

```calor
§AMT{name:visibility}
  §I{type:param}
  §O{type}
  // body
```

### Example

```calor
§CL{DataService:pub}
  §AMT{GetUserAsync:pub}
    §I{i32:id}
    §O{User}
    §B{user} §AWAIT §C{_repository.FindAsync} §A id §/C
    §R user
```

### Modifiers

Async methods support the same modifiers as regular methods:

```calor
§AMT{ProcessAsync:pub:virt}    // public virtual async
§AMT{HandleAsync:prot:ovr}     // protected override async
§AMT{ComputeAsync:pub:stat}    // public static async
```

## Await Expression

Use `§AWAIT` to await async operations.

### Syntax

```calor
§AWAIT expression                    // Simple await
§AWAIT{false} expression             // await with ConfigureAwait(false)
§AWAIT{true} expression              // await with ConfigureAwait(true)
```

### Examples

**Simple await:**
```calor
§B{data} §AWAIT §C{client.GetAsync} §A url §/C
```

**With ConfigureAwait(false) for library code:**
```calor
§B{data} §AWAIT{false} §C{client.GetAsync} §A url §/C
```

Emits: `var data = await client.GetAsync(url).ConfigureAwait(false);`

### Using Await in Conditions and Expressions

```calor
§IF §AWAIT §C{IsValidAsync} §A id §/C
  §P "Valid"

§R §AWAIT §C{ComputeAsync} §A x §/C
```

## Lambda Expressions

Lambda expressions create anonymous functions using `§LAM`/`§/LAM` blocks.

### Syntax

```calor
§LAM{param1:type1}              // single parameter
§LAM{param1:type1:param2:type2} // multiple parameters
§LAM{}                           // no parameters
```

The header encodes parameters as colon-separated `name:type` pairs after the ID.
Parameters without known types use `object` as the default type.

### Single Parameter

```calor
§B{doubler} §LAM{x:i32} (* x 2) §/LAM
```

Emits: `var doubler = (int x) => x * 2;`

### Multiple Parameters

Parameters are listed as consecutive `name:type` pairs:

```calor
§B{add} §LAM{a:i32:b:i32} (+ a b) §/LAM
```

Emits: `var add = (int a, int b) => a + b;`

**Three parameters:**
```calor
§B{combine} §LAM{x:i32:y:str:z:bool} §C{Process} §A x §A y §A z §/C §/LAM
```

### No Parameters

```calor
§B{getTime} §LAM{} §C{DateTime.Now} §/C §/LAM
```

### As LINQ Arguments

Lambdas are commonly used as arguments inside `§C{...}` calls:

```calor
§C{numbers.Where} §A §LAM{n:i32} (!= (% n 3) 0) §/LAM §/C
§C{items.Select} §A §LAM{x:i32} (* x 2) §/LAM §/C
```

### Statement Body Lambdas

For multi-statement bodies, include statements between the tags:

```calor
§B{printer} §LAM{x:i32}
§P x
§P (* x 2)
§/LAM
```

### Async Lambdas

Add `async` after the ID, before parameters:

```calor
§LAM{async:x:i32}
§B{result} §AWAIT §C{ProcessAsync} §A x §/C
§R result
§/LAM
```

> **Note:** `§I{type:name}` inline parameter declarations are NOT supported inside
> `§LAM` headers. All parameters must be encoded in the header using the
> `name:type` pair format.

## Local Functions

Local `§F` declarations are removed. For a local callable value, bind an ordinary
.NET delegate type to a lambda. Declare the binding before using it.

This is not a forward-declared static local function. Do not copy the old
recursive or mutually recursive local-`§F` recipes into active source. During C#
conversion, supported local functions lower to bindings and lambdas; unsupported
shapes remain explicitly preserved C#, rather than changing behavior silently.

### Example

```calor
§M{LocalCallables}
  §F{Use:pub} (i32:value) -> i32
    §E{alloc}
    §B{addOne:Func<i32,i32>} §LAM{x:i32}
      §R (+ x 1)
    §/LAM
    §R §C{addOne} §A value §/C
```

`Use(2)` returns 3. The binding is named `addOne`; the lambda header contains only
its parameter name and type, not a source identity field. Its body ends at the
required `§/LAM` delimiter. Effect checking still applies to lambda bodies and
their callers.

## Delegate Definitions

Delegates define function signatures that can be passed as values.

### Syntax

```calor
§DEL{name}
  §I{type:param}       // parameters (0 or more)
  §O{type}             // return type (optional for void)
  §E{effects}          // effects (optional)
```

### Examples

**Calculator delegate:**
```calor
§DEL{Calculator}
  §I{i32:a}
  §I{i32:b}
  §O{i32}
```

Emits: `public delegate int Calculator(int a, int b);`

**Void delegate:**
```calor
§DEL{Logger}
  §I{str:message}
```

Emits: `public delegate void Logger(string message);`

**Delegate with effects:**
```calor
§DEL{FileProcessor}
  §I{str:path}
  §O{bool}
  §E{fs:rw}
```

## Enum Definitions

Enums define a set of named constants.

### Syntax

```calor
§EN{Name}
  Member1
  Member2 = 1
  Member3 = 2
```

With underlying type:
```calor
§EN{Name:underlyingType}
  ...
```

### Examples

**Simple enum:**
```calor
§EN{Color}
  Red
  Green
  Blue
```

Emits:
```csharp
public enum Color
{
    Red,
    Green,
    Blue,
}
```

**Enum with explicit values:**
```calor
§EN{StatusCode}
  Ok = 200
  NotFound = 404
  Error = 500
```

**Enum with underlying type:**
```calor
§EN{Flags:u8}
  None = 0
  Read = 1
  Write = 2
```

Emits:
```csharp
public enum Flags : byte
{
    None = 0,
    Read = 1,
    Write = 2,
}
```

## Enum Extension Methods

Extension methods can be added to enums using `§EEXT` (Enum EXTension).

### Syntax

```calor
§EEXT{EnumName}
  §F{MethodName:pub}
    §I{EnumName:self}
    §O{returnType}
    // body using self
```

The first parameter with the enum type (or named `self`) becomes the `this` parameter.

### Example

```calor
§EN{Color}
  Red
  Green
  Blue

§EEXT{Color}
  §F{ToHex:pub}
    §I{Color:self}
    §O{str}
    §W self
    §K Color.Red → §R "#FF0000"
    §K Color.Green → §R "#00FF00"
    §K Color.Blue → §R "#0000FF"

  §F{IsPrimary:pub}
    §I{Color:self}
    §O{bool}
    §R (|| (== self Color.Red) (|| (== self Color.Green) (== self Color.Blue)))
```

Emits:
```csharp
public enum Color
{
    Red,
    Green,
    Blue,
}

public static class ColorExtensions
{
    public static string ToHex(this Color self)
    {
        return self switch
        {
            Color.Red => "#FF0000",
            Color.Green => "#00FF00",
            Color.Blue => "#0000FF",
            _ => throw new ArgumentOutOfRangeException(nameof(self))
        };
    }

    public static bool IsPrimary(this Color self)
    {
        return self == Color.Red || self == Color.Green || self == Color.Blue;
    }
}
```

## Event Definitions

Events allow objects to notify subscribers of state changes.

### Syntax

```calor
§EVT{name:visibility:delegateType}
```

| Part | Description |
|:-----|:------------|
| `id` | Unique identifier |
| `name` | Event name |
| `visibility` | `pub`, `pri`, `prot` |
| `delegateType` | Delegate type for handlers |

### Example

```calor
§CL{Button:pub}
  §EVT{Click:pub:EventHandler}
    §EVT{ValueChanged:pub:EventHandler<ValueChangedEventArgs>}
```

Emits:
```csharp
public class Button
{
    public event EventHandler Click;
    public event EventHandler<ValueChangedEventArgs> ValueChanged;
}
```

---

## Event Subscribe/Unsubscribe

Use `§SUB` and `§UNSUB` to add or remove event handlers.

### Syntax

```calor
§SUB eventRef handlerRef      // Subscribe
§UNSUB eventRef handlerRef    // Unsubscribe
```

### Examples

**Subscribe to event:**
```calor
§SUB button.Click OnButtonClick
```

Emits: `button.Click += OnButtonClick;`

**Unsubscribe from event:**
```calor
§UNSUB button.Click OnButtonClick
```

Emits: `button.Click -= OnButtonClick;`

**Subscribe with lambda:**
```calor
§SUB button.Click (sender, e) → §P "Clicked!"
```

## Input Parameters

Input parameters define function arguments.

### Syntax

```calor
§I{type:name}
```

### Examples

```calor
§I{i32:x}           // int x
§I{str:name}        // string name
§I{bool:flag}       // bool flag
§I{?i32:maybeVal}   // int? maybeVal (nullable)
§I{[u8}:data}       // byte[] data
§I{[str}:args}      // string[] args
```

### Multiple Parameters

```calor
§F{Add:pub}
  §I{i32:a}
  §I{i32:b}
  §I{i32:c}
  §O{i32}
  §R (+ (+ a b) c)
```

## Output Type

Every function must declare its output type.

### Syntax

```calor
§O{type}
```

### Examples

```calor
§O{void}     // returns nothing
§O{i32}      // returns int
§O{str}      // returns string
§O{?i32}     // returns nullable int
§O{[u8}}     // returns byte[]
§O{[str}}    // returns string[]
```

## Array Types

Calor uses bracket notation `[T]` for array types, which aligns with common programming language conventions.

### Syntax

```calor
[elementType]         // Single-dimensional array
[[elementType]]       // Jagged array (array of arrays)
```

### Examples

| Calor Type | C# Equivalent |
|:----------|:--------------|
| `[u8]` | `byte[]` |
| `[i32]` | `int[]` |
| `[str]` | `string[]` |
| `[bool]` | `bool[]` |
| `[[i32]]` | `int[][]` |

### Usage in Fields and Methods

```calor
§CL{DataProcessor}
  §FLD{[u8}:_buffer:priv}       // private byte[] _buffer
  §FLD{[i32}:_indices:priv}     // private int[] _indices

  §MT{ProcessData:pub}
    §I{[str}:args}              // string[] args parameter
    §O{i32}
    §R args.Length
```

## Block Structure (Indentation)

Calor blocks are delimited by **indentation**, like Python. A block
opens with one of the structural tags (`§M`, `§F`, `§AF`, `§MT`,
`§AMT`, `§CL`, `§IFACE`, `§L`, `§WH`, `§DO`, `§IF`, `§W`, `§TR`,
`§LAM`, `§DEL`, `§EN`, `§EEXT`, `§PROP`) and ends at the next line that
dedents back to (or past) the parent column.

### Rules

1. The compiler default is **2 spaces per nesting level**
2. Tabs and spaces must not be mixed within a block
3. Chain continuations (`§EI`, `§EL`, `§K`, `§WHEN`, `§CA`, `§FI`)
   sit at the **same** column as their parent (`§IF`, `§W`, `§TR`),
   not indented inside it
4. Legacy structural `§/X` closers raise `Calor0830`

### Example

```calor
§M{Example}
  §F{Main:pub}
    §O{void}
    §E{cw}
    §L{i:1:10:1}
      §IF (> i 5)
        §P i
      §EL
        §P "small"
```

The ends of the `§IF`, `§L`, `§F`, and `§M` blocks are inferred from dedents;
do not write structural closer lines.
If you write them anyway, the compiler rejects them with `Calor0830`;
`calor fix --heal-closers` removes them.

### Tag Reference

| Opener | Purpose |
|:-------|:--------|
| `§M{name}` | Module |
| `§F{vis}` | Function |
| `§AF{vis}` | Async function |
| `§CL{name}` | Class |
| `§IFACE{name}` | Interface |
| `§MT{vis}` | Method |
| `§AMT{vis}` | Async method |
| `§L{var:from:to:step}` | For loop |
| `§WH cond` | While loop |
| `§DO` | Do-while loop (condition on closing line during transition) |
| `§IF cond` | Conditional (with `§EI` / `§EL` continuations) |
| `§W expr` | Switch (with `§K` cases) |
| `§TR` | Try (with `§CA` / `§FI`) |
| `§LAM{params}` | Lambda (block body) |
| `§DEL{name}` | Delegate definition |
| `§EN{name}` | Enum |
| `§EEXT{enumName}` | Enum extension methods |
| `§PROP{type:vis}` | Property (may carry an effect row: `§PROP{...} §E{cw}`, since 0.17) |
| `§EVT{name:vis:type}` | Event (single line, no block) |
| `§C{target}` | Call expression (`§/C` ends the argument list) |

## Generics

Calor supports generic functions, classes, interfaces, and methods using angle bracket syntax.

### Type Parameters

Type parameters are declared using `<T>` suffix syntax after the tag attributes.

```calor
§F{name:vis}<T>         // Generic function with one type parameter
§F{name:vis}<T, U>      // Generic function with two type parameters
§CL{name}<T>            // Generic class
§IFACE{name}<T>         // Generic interface
§MT{name:vis}<T>        // Generic method
```

### Constraints

Type parameter constraints are declared using `§WHERE` clauses.

**New syntax (recommended):**
```calor
§WHERE T : class                    // T must be a reference type
§WHERE T : struct                   // T must be a value type
§WHERE T : new()                    // T must have parameterless constructor
§WHERE T : IComparable<T>           // T must implement interface
§WHERE T : class, IComparable<T>    // Multiple constraints
```

**Legacy syntax (still supported):**
```calor
§WHERE{T:class}                     // T must be a reference type
§WHERE{T:IComparable}               // T must implement interface
```

### Generic Type References

Generic types are written inline using angle bracket syntax.

```calor
§I{List<T>:items}                   // Parameter of type List<T>
§I{Dictionary<str, T>:lookup}       // Nested generic types
§O{IEnumerable<T>}                  // Generic return type
§FLD{List<T>:_items:priv}            // Generic field type
```

### Examples

**Generic identity function:**
```calor
§F{Identity:pub}<T>
  §I{T:value}
  §O{T}
  §R value
```

**Generic class with constraint:**
```calor
§CL{Repository:pub}<T>
  §WHERE T : class
  §FLD{List<T>:_items:priv}

  §MT{Add:pub}
    §I{T:item}
    §O{void}
    §C{_items.Add} §A item §/C

  §MT{GetAll:pub}
    §O{IReadOnlyList<T>}
    §R _items
```

**Generic interface:**
```calor
§IFACE{IRepository}<T>
  §WHERE T : class
  §MT{Get}
    §I{i32:id}
    §O{T}
```

**Empty interface (changed in 0.16):** a marker interface has no members, so
there is nothing indented under it to tell the parser where it stops. From 0.16
an empty `§IFACE` ends at the next **type** opener — `§CL`, `§IFACE`, `§EN`,
`§DEL`, or a `§CSHARP` block — written at **exactly the same column** as
the `§IFACE` itself:

```calor
§M{Demo}
  §IFACE{IMarker}
  §CL{Thing:pub}
    §MT{Go:pub} () -> void
      §E{}
```

Three things this rule does *not* say:

- **The column has to match.** An indented type opener is not a sibling — it
  looks like you meant to nest one type inside the interface, which Calor does
  not have — so it is still a `Calor0100` error rather than being quietly moved
  out one level.
- **Only type openers end it.** A same-column `§F` after an empty `§IFACE` is
  still `Calor0100`; the rule is about types sitting next to each other, not
  about columns in general.
- **This is an interface rule, not a general one.** An empty `§CL` does *not*
  behave the same way, and the difference is silent: a `§CL` written at the same
  column right after an empty `§CL` is parsed as **nested inside** it, with no
  diagnostic at all. If you write an empty class, give it a body or expect the
  next one to end up inside it.

## C# Attributes

C# attributes are preserved during conversion using inline bracket syntax `[@Attribute]`.

### Syntax

```calor
§CL{name}[@AttributeName]
§CL{name}[@AttributeName(args)]
§MT{name:vis}[@Attr1][@Attr2]
```

### Examples

**Class with routing attributes (ASP.NET Core):**
```calor
§CL{JoinController:ControllerBase}[@Route("api/[controller]")][@ApiController]
  §MT{Post:pub}[@HttpPost]
```

**Property with validation:**
```calor
§PROP{Email:str:pub}[@Required][@EmailAddress]
  §GET
    §SET
```

### Attribute Arguments

| Style | Syntax | Example |
|:------|:-------|:--------|
| No args | `[@Name]` | `[@ApiController]` |
| Positional | `[@Name(value)]` | `[@Route("api/test")]` |
| Named | `[@Name(Key="value")]` | `[@JsonProperty(PropertyName="id")]` |
| Mixed | `[@Name(pos, Key=val)]` | `[@Range(1, 100, ErrorMessage="Invalid")]` |

### Supported Elements

Attributes can be attached to:
- Classes: `§CL{...}[@attr]`
- Interfaces: `§IFACE{...}[@attr]`
- Methods: `§MT{...}[@attr]`
- Properties: `§PROP{...}[@attr]`
- Fields: `§FLD{...}[@attr]`
- Parameters: `§I{type:name}[@attr]`

---

## Why Indent-Based Blocks?

1. **Familiar to agents** - LLMs trained on Python have strong priors for indentation
2. **Tag-light** - No `§/X` to type, no mismatched-closer errors
3. **Refactoring safe** - Stable IDs on openers still survive code movement
4. **Lower edit cost** - In edit-workload studies, indent form reduced agent token cost by ~16% with no regression in correctness
