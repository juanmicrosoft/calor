The evaluation framework relies on benchmark programs to measure Calor vs C#. This guide explains how to add new benchmarks.

---

## Benchmark Requirements

Each benchmark needs:

1. **Calor source file** - The Calor implementation
2. **C# source file** - Semantically equivalent C# implementation
3. **Metadata** - Description and expected behavior
4. **Explicit validation** - Record compilation, execution and equivalence separately

Design cases that are representative, including cases where C# is more compact.
Do not rewrite measured sources, runtime oracles, policies or denominators to
improve a result. A compile-only success does not establish semantic equivalence.

---

## Directory Structure

```
tests/TestData/Benchmarks/
├── manifest.json
├── TokenEconomics/
│   ├── HelloWorld.calr
│   └── HelloWorld.cs
└── YourNewBenchmark/
    ├── program.calr
    └── program.cs
```

`tests/Calor.Evaluation/Benchmarks/` contains the loader and runner code, not
the benchmark source tree. The manifest associates each logical case with its
Calor and C# paths. A per-directory `metadata.json` is not automatically loaded.

## Creating a Benchmark

### Step 1: Create Directory

```bash
mkdir -p tests/TestData/Benchmarks/YourNewBenchmark
```

Run the later commands from the repository root.

### Step 2: Write Calor Code

Create `program.calr`:

```calor
module YourModule
  func Main () → void
    !
    return
```

**Guidelines:**
- Use current native declarations and infix expressions
- Let tooling maintain declaration IDs in `.calor/ids.json`, not source headers
- Declare effects explicitly
- Add contracts where meaningful
- Ensure it compiles

### Step 3: Write Equivalent C#

Create `program.cs`:

```csharp
namespace YourModule
{
    public static class Program
    {
        public static void Main()
        {
            // Equivalent implementation
        }
    }
}
```

**Guidelines:**
- Match the Calor logic exactly
- Match contract behavior and build configuration; `Debug.Assert` is not interchangeable with a throwing runtime guard
- Keep structure as parallel as possible

These empty programs are starting templates, not a finished benchmark pair.
Their generated type names differ; register the intended entry points and
compare any public API shape the benchmark claims to preserve.

### Step 4: Add Metadata

Add an entry to the suite's manifest. For a separate local suite, the complete
manifest shape is:

```json
{
  "version": "2.0",
  "description": "Describe the comparison and its limits",
  "benchmarks": [
    {
      "id": "your-benchmark",
      "name": "Your Benchmark Name",
      "category": "TokenEconomics",
      "calorFile": "YourNewBenchmark/program.calr",
      "csharpFile": "YourNewBenchmark/program.cs",
      "level": 1,
      "features": ["function"],
      "notes": "State the tested behavior and relevant exclusions"
    }
  ]
}
```

`level` is numeric. Store and execute the actual behavioral oracle through the
relevant test/metric mechanism; an invented `expectedOutput` metadata field
does not make the runner assert that output. Do not select an expected
advantage to favor Calor.

### Step 5: Verify

```bash
# Compile the exact Calor source with normal enforcement
dotnet run --project src/Calor.Compiler -- \
  --input tests/TestData/Benchmarks/YourNewBenchmark/program.calr \
  --output /tmp/your-benchmark.g.cs

# Inspect supported evaluation commands before selecting a run
dotnet run --project tests/Calor.Evaluation -- run --help

# Run a reviewed, bounded manifest without enabling provider-backed evaluation
dotnet run --project tests/Calor.Evaluation -- run \
  --manifest /absolute/path/to/reviewed-manifest.json --output report.json
```

Compile C# as part of an SDK-style project or the established Roslyn harness,
with the declared references, options and entry point. Do not assume
`dotnet build program.cs` is a valid standalone source-file build command.
Then run independent behavioral comparisons, including exceptions, mutations,
evaluation order and output where relevant.

The current evaluation adapter resolves explicitly registered active Calor
copies and records original/resolved paths. That is a **current-compiler**
input contract, not replay of historical producer bytes. Preserve historical
sources and use their dedicated replay lanes. Adding a `.calr` file can also
affect repository-wide source censuses; update only the intended suite through
its established process.

Do not add `--llm` or dispatch paid agent evaluation without separate approval
of the model, task selection and spending. These documentation examples are not
a measured run.

## Benchmark Categories

| Category | Description | Examples |
|:---------|:------------|:---------|
| `TokenEconomics` | Source/token comparison | Small and larger programs, including unfavorable cases |
| `Comprehension` | Understanding tasks | Explicit questions and answers |
| `EditPrecision` | Editing tasks | Defined change and allowed scope |
| `ErrorDetection` | Bug scenarios | Known faults with independent expectations |

Use feature tags such as `loops`, `contracts` and `effects` to describe a case.
Do not confuse those tags with measured outcomes or complexity denominators.

## Example: Factorial Benchmark

### Calor (`factorial.calr`)

```calor
module FactorialBenchmark Math
  func Factorial (int:n | ((# >= 0) && (# <= 12))) → int
    !
    => result >= 1
    if n <= 1
      return 1
    return n * Factorial(n - 1)

  func Main () → void
    ! cw
    Console.WriteLine(Factorial(5))
```

`Math.MathModule.Factorial(5)` returns `120`; `Main()` prints that value.
The upper bound prevents checked integer overflow.

### C# (`factorial.cs`)

```csharp
using System.Diagnostics;

namespace Math
{
    public static class Program
    {
        public static int Factorial(int n)
        {
            Debug.Assert(n >= 0, "n must be non-negative");
            Debug.Assert(n <= 12, "n must be <= 12 to avoid overflow");

            if (n <= 1) return 1;
            var result = n * Factorial(n - 1);

            Debug.Assert(result >= 1, "result must be >= 1");
            return result;
        }

        public static void Main()
        {
            Console.WriteLine(Factorial(5));
        }
    }
}
```

### Metadata (`metadata.json`)

The original C# fragment above assumes `System` is imported by its project
context. Its `Debug.Assert` calls can be compiled out and do not match Calor's
throwing contract checks on invalid inputs. It demonstrates the same factorial
calculation on the declared valid domain, **not** an established full-API
equivalence benchmark.

The following legacy metadata is illustrative only; it is not the manifest
schema shown earlier and does not register or execute an oracle:

```json
{
  "id": "factorial",
  "name": "Factorial",
  "description": "Recursive factorial with contracts",
  "category": "contracts",
  "complexity": "medium",
  "features": ["recursion", "contracts", "conditionals"],
  "expectedOutput": "120"
}
```

## Semantic Equivalence

Both implementations must be semantically equivalent:

### Same Logic
- Same algorithm
- Same control flow structure
- Same edge case handling

### Same Contracts
- Match parameter-refinement entry checks and `=>` postconditions under the actual modes
- Compare exception types and timing, not just condition text
- Do not substitute assertions that disappear in the measured build

### Same Effects
- Compare actual operations and observable behavior, not just declared rows
- An admitted `cw` or `fs:r` permission does not prove that the body performs I/O
- Unknown effects, waivers and preserved C# are separate outcomes, not native credit

## Quality Checklist

Before submitting:

- [ ] Calor compiles without errors
- [ ] C# compiles without errors
- [ ] Both produce identical output (if applicable)
- [ ] Uses current native syntax
- [ ] Tool-owned declaration identities are maintained
- [ ] Effects are declared
- [ ] Contract modes and exception behavior are equivalent
- [ ] Metadata is complete
- [ ] Code is clean and readable
- [ ] Original inputs, options, oracles and denominators are retained
- [ ] Compile-only, native, round-trip and runtime outcomes are reported separately

## E2E Test Scenarios

For simpler test cases, you can add to the E2E test suite instead:

```
tests/E2E/scenarios/
├── 01_hello_world/
│   ├── input.calr
│   └── verify.sh
├── 02_fizzbuzz/
│   ├── input.calr
│   └── verify.sh
└── XX_your_test/
    ├── input.calr
    └── verify.sh
```

### E2E Verification Script

```bash
#!/usr/bin/env bash
SCENARIO_DIR="$1"
OUTPUT_FILE="$SCENARIO_DIR/output.g.cs"

# Check generated C# contains expected patterns
grep -q "Console.WriteLine" "$OUTPUT_FILE" || exit 1
grep -q "namespace" "$OUTPUT_FILE" || exit 1
```

Text-pattern checks alone are not runtime equivalence tests. Also compile and
execute the generated program through the established scenario harness, with
independent expected results. Keep agent-task/model runs separate from local
compiler E2E tests.
