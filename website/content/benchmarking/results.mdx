## Read the Results Carefully

The static snapshot above covers **217 programs** and reports a legacy calculator
score of **1.32x**, with Calor ahead in seven of eight metrics. This is not a
measured language advantage. Comprehension is
1.84x, error detection is 1.49x, token economics is 1.42x, and information
density is 0.97x—the one category where C# leads.

The recorded source revision is `3a452b09`. Its `Directory.Build.props` declares
compiler `0.19.0`; the JSON's `version: "1.0"` identifies the data format, not the
compiler release. The corpus is `tests/TestData/Benchmarks`. The exact compiler
binary used for the measurement was not independently recorded. These are
fixed-source results, rerun for the 0.19 release. They are not a live measure of
coding-agent performance. The separate agent-study snapshots below were not rerun.

These measurements need important caveats:

- Source pairs are **not all behaviorally equivalent**. For example, the C#
  `CsvParser` implements parsing, while its Calor counterpart contains only
  helper functions. The 0.19 rerun fixes an invalid newline literal in the C#
  fixture, but does not establish equal work across the corpus. The ratios
  therefore cannot establish a language advantage. See
  [the benchmark integrity follow-up](https://github.com/juanmicrosoft/calor/issues/1276).
- The metrics are deterministic static analyses. The exporter reports both
  zero-width intervals from singleton category aggregates and pooled intervals
  from repeated program scores. Thirty repetitions are not independent samples.
  Neither interval establishes sampling uncertainty over the corpus, agent
  productivity, or safety.
- These C#-versus-Calor micro-benchmarks are not the v0.12 release gates.
  PP-A1 covered adoption readiness, while PP-W5 measured toolchain tax and
  concluded only that no large tax was detected—not that parity was proven.

Token economics is a composite of token, character, and line ratios. Calor
still pays a `§` token premium on small programs even though the current
composite favors Calor.

## Agent Proof Points

The static dashboard does not measure effect rows or live coding-agent
behavior. Those questions use separate, pre-registered agent studies.

### Effect-row toolchain cost

The 0.15 PP-E1 study had two legs:

- The compiler caught all 10 seeded effect-laundering mistakes at the
  registered locations. The unmutated fixtures reproduced their frozen
  diagnostic baselines exactly.
- Four ordinary programming tasks ran five times on each of two compiler
  configurations, for 40 green runs. The median paired output-token ratio was
  1.18. Its 95% lower bound was 0.90, below the registered 1.0 bound gate, and
  the point estimate stayed below the 1.35 failure threshold.

The combined registered verdict was **HIT**. The tasks measured compiler
feedback cost on ordinary code; because they contained no callbacks, they did
not measure the safety benefit of effect rows.

### Effect-row safety benefit

The 0.16 practice study used six callback-heavy tasks designed to catch a
hidden console effect. Across 28 usable runs, neither compiler arm produced the
target hidden-effect behavior. The practice data estimated that the full study
would need nine runs per task and compiler, while the registered budget could
fund three, giving about 48% power at the registered effect size.

The recorded verdict is therefore **underpowered: the claim is neither
supported nor refuted**. The stricter compiler cost about 12% more work to
reach a green build on these tasks, below the registered “noticeable” threshold,
but that is descriptive practice-round evidence rather than a product claim.

Keep the three statements separate:

- The 1.32x dashboard is a deterministic source/structure comparison.
- The 0.15 proof point did not detect a large toolchain tax.
- The 0.16 proof point did not have enough evidence to judge the safety benefit.

## When to Use Calor

These scores are not sufficient evidence for choosing a language. Consider
Calor when you want to experiment with:

- **Explicit contracts** and the documented limits of optional static verification
- **Explicit IDs and structural markers** for agent-editing experiments
- **Structured source representations**, while measuring costs on your own tasks

Use C# when:

- **Ecosystem libraries are needed** — Leverage existing tooling
- **Human readability is priority** — Familiar syntax for human developers

## Methodology

All benchmarks are automated and reproducible. Each program is evaluated across 8 metrics comparing Calor and C# implementations.

The published dashboard framework:

1. Compiles paired Calor and C# programs.
2. Applies deterministic metric calculators to source, syntax trees, and
   compilation results.
3. Aggregates the per-program Calor/C# ratios.
4. Repeats the deterministic evaluation 30 times for the reported statistical
   artifact. Greater than 1.0 favors Calor; less than 1.0 favors C#.

LLM-based task runners exist separately and are not folded into this dashboard
result.

See [Methodology](/docs/benchmarking/methodology/) for full details on the evaluation framework.

## Running Benchmarks

To regenerate benchmark results:

```bash
# Run the evaluation framework
dotnet run --project tests/Calor.Evaluation -c Release -- run -f website -o website/public/data/benchmark-results.json --statistical --runs 30

# Start the website to view results
cd website && npm run dev
```

Results are automatically loaded from `benchmark-results.json` and displayed in the dashboard above.
