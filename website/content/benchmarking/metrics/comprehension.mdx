## Overview

The Comprehension metric measures how easily an AI agent can understand code structure and extract semantic information without deep analysis.

---

## Why It Matters

When an AI agent reads code, it needs to answer:
- What are the function boundaries?
- What are the inputs and outputs?
- What side effects are possible?
- What constraints must hold?

Traditional languages require parsing and inference. Calor makes these explicit.

## Example Comparison

### Current Calor Illustration

```calor
module Calculator
  func Divide (int:a, int:b) → int
    requires b != 0
    => result >= 0
    return a / b
```

**Archived score calculation, not a score for the native illustration above:**
- `§M{`: +0.15
- `§F{`: +0.15
- `§I{`: +0.10
- `§O{`: +0.10
- `§R`: +0.10
- `§Q`: +0.15
- `§S`: +0.10
- Indented body lines: +0.10 (proportional)
- Indent-form completeness (every `§F{` has an indented body): +0.05

**Total: 1.00**

Current preconditions use `requires`; postconditions use `=>`. This preserves
the original Divide contracts, including `result >= 0`. The precondition alone
does not prove that postcondition: a negative quotient violates it.

### Unchanged C# Comparison

```csharp
namespace Calculator
{
    public static class Program
    {
        public static int Divide(int a, int b)
        {
            if (b == 0) throw new ArgumentException();
            var result = a / b;
            Debug.Assert(result >= 0);
            return result;
        }
    }
}
```

**Score calculation:**
- `namespace`: +0.15
- `class`: +0.10
- `public`: +0.05
- `return`: +0.10
- `int `: +0.10
- `Debug.Assert`: +0.15

**Total: 0.65**

**Illustrative ratio: 0.95 / 0.65 = 1.46x.** This single example is not the
aggregate historical result.

The archived narrative reports a Calor total of 1.00 but uses 0.95 in this ratio.
Those historical numbers are retained, not recalculated for current syntax.
The implementations agree on valid integer quotients. Their failure behavior is
not interchangeable: Calor's runtime contracts and C#'s conditional `Debug.Assert`
do not establish the same postcondition-enforcement behavior.

## What Agents Can Extract

### From Calor (Direct Extraction)

| Information | Extraction Method |
|:------------|:------------------|
| Function name | Read `func Divide` |
| Function ID | Query the project tools' `.calor/ids.json` sidecar; no ID is written in the declaration |
| Inputs | Read the typed parameter list, such as `(int:a, int:b)` |
| Output type | Read the signature after `→` |
| Side effects | Read the `!` effect row, when declared |
| Preconditions | Read `requires condition` |
| Postconditions | Read `=> condition` |
| Scope boundaries | An indented function body ends at dedent; no structural closer is written |

### From C# (Requires Inference)

| Information | Extraction Method |
|:------------|:------------------|
| Function name | Parse method declaration |
| Inputs | Parse parameter list |
| Output type | Parse return type |
| Side effects | Analyze all statements for I/O |
| Preconditions | Find throw statements, Debug.Assert |
| Postconditions | Find assertions near return |
| Scope boundaries | Count and match braces |

## Interpretation

The historical aggregate is 1.84x. Under this calculator, Calor source exposes more
of the structural signals being counted. That measures the calculator's
defined signals; it is not a direct measurement of human comprehension.

This doesn't mean C# is hard to understand—it means Calor makes structure *more explicit*, which benefits automated analysis.
