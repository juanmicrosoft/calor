## Overview

The Token Economics metric measures how compact each language is at expressing
the same logic. It is a **composite** of three dimensions — token count,
non-whitespace character count, and line count — combined as a geometric mean so
that no single dimension alone supplies the score. This is a source-size proxy,
not a provider tokenizer, billing measurement or measured editing cost.

> **Metric correction (v0.6.5, #668):** earlier releases reported this category as
> "C# wins" using a **raw token count only**. The calculator computed the composite
> (token × char × line) and then discarded it, reporting the token ratio alone. That
> bug is fixed: the category now reports the composite it always computed. On the
> historical benchmark corpus the composite **favors Calor** (**1.42×**),
> because Calor's character- and line-level compactness outweighs its higher raw token
> count. Raw token count *alone* — especially on tiny programs — still tends to favor
> C# (see the per-program examples below, which illustrate that single dimension).

---

## Why It Matters

LLM context windows are finite. Every token used for code is a token not available for:
- Instructions
- Examples
- Conversation history
- Reasoning

Token efficiency directly impacts what agents can accomplish.

## How It's Measured

### Tokenization

Simple tokenization splits on:
- Whitespace
- Punctuation
- Symbols

These are heuristic source tokens, not model tokens. The calculator treats
punctuation and symbols as individual characters; a model's tokenizer can split
or combine text differently. Do not use this count to claim a model-context or
paid-token improvement.

```csharp
foreach (var ch in source)
{
    if (char.IsWhiteSpace(ch))
    {
        if (inToken) { tokens++; inToken = false; }
    }
    else if (char.IsPunctuation(ch) || char.IsSymbol(ch))
    {
        if (inToken) { tokens++; inToken = false; }
        tokens++; // Punctuation is its own token
    }
    else { inToken = true; }
}
```

### Metrics Collected

| Metric | Description |
|:-------|:------------|
| Token count | Number of tokens |
| Character count | Characters after removing spaces, tabs, CR and LF |
| Line count | Number of segments from splitting on LF, including a final empty segment |
| Token ratio | C# tokens / Calor tokens |
| Char ratio | C# chars / Calor chars |
| Line ratio | C# lines / Calor lines |

### Composite Score

```
CompositeAdvantage = (TokenRatio × CharRatio × LineRatio)^(1/3)
```

Geometric mean of all three ratios. **This composite is the value the metric
reports** (as of v0.6.5 / #668). Because the underlying counts are deterministic,
the same input bytes produce the same score. That determinism does not quantify
uncertainty about corpus selection, semantic equivalence or model tokenization.

## Detailed Comparison

> The per-program ratios below report the **raw token dimension only** — one of the
> three inputs to the composite. They show that on small programs Calor often uses
> *more* raw tokens than C#. The composite metric additionally credits Calor's
> character- and line-level compactness. These historical approximate annotations
> have not been recomputed for the current illustrations. The legacy displayed
> ratios use Calor/C#, the inverse of the calculator's C#/Calor advantage ratio.

### Hello World

**Calor:**
```calor
module TokenHello
  func Main () → void
    ! cw
    Console.WriteLine("Hello World")
```

**Historical annotation, not a count of the native source above:**
- Tokens: ~25
- Lines: 7

**C#:**
```csharp
class Program
{
    static void Main()
    {
        Console.WriteLine("Hello World");
    }
}
```

**Historical annotation:**
- Tokens: ~15
- Lines: 7

**Ratio:** 25/15 = **1.67x** (Calor uses more)

### FizzBuzz

**Calor:**
```calor
module TokenFizzBuzz
  func Main () → void
    ! cw
    for i from 1 to 100 step 1
      if i % 15 == 0
        Console.WriteLine("FizzBuzz")
      else if i % 3 == 0
        Console.WriteLine("Fizz")
      else if i % 5 == 0
        Console.WriteLine("Buzz")
      else
        Console.WriteLine(i)
```

**Historical annotation, not a count of the native source above:**
- Tokens: ~80
- Lines: 13

**C#:**
```csharp
for (int i = 1; i <= 100; i++)
{
    if (i % 15 == 0) Console.WriteLine("FizzBuzz");
    else if (i % 3 == 0) Console.WriteLine("Fizz");
    else if (i % 5 == 0) Console.WriteLine("Buzz");
    else Console.WriteLine(i);
}
```

**Historical annotation:**
- Tokens: ~50
- Lines: 7

**Ratio:** 80/50 = **1.60x** (Calor uses more)

### Function with Contract

**Calor:**
```calor
module TokenContracts
  func Divide (int:a, int:b | (# != 0)) → int
    !
    => result >= 0
    return a / b
```

**Historical annotation, not a count of the native source above:**
- Tokens: ~40
- Lines: 8

**C#:**
```csharp
public static int Divide(int a, int b)
{
    if (b == 0) throw new ArgumentException();
    Debug.Assert(a / b >= 0);
    return a / b;
}
```

**Historical annotation:**
- Tokens: ~35
- Lines: 6

**Ratio:** 40/35 = **1.14x** (Closer when contracts matter)

The original C# fragments are retained unchanged. They require their appropriate
project or statement context and imports. Their `ArgumentException` and
conditional `Debug.Assert` behavior is not equivalent to Calor's throwing
runtime contracts on all inputs. Both shown division bodies can also overflow
on `int.MinValue / -1`. `Divide(6, 2)` returning `3` is a valid execution
observation, not a full-domain equivalence proof.

## Why Calor Uses More Raw Tokens

The historical result reflects its recorded sources and corpus. It does not
establish that current native programs necessarily use more or fewer source
tokens, characters or model tokens.

### 1. Native Declarations

Current declarations use ordinary headers such as `module Name` and
`func Value () → int`. Declaration identities live in tool-owned sidecars,
not source headers.

```csharp
namespace Name   // Just keyword + name
```

### 2. Effect Declarations

An effect row such as `! cw,fs:r,net:rw` adds explicit permission information.
C# has no built-in Calor-style row syntax, but library contracts and analyzers
can convey effect information. Compare the actual guarantees, not just spelling.

### 3. Block Indentation

Nested native bodies use indentation instead of structural closers. The
FizzBuzz example above is a complete executable illustration. Its formatting
also affects character and line counts, so fix formatting rules before comparing.

### 4. Contract Syntax

Contracts add information and source text: `int:x | (# >= 0)` is an entry
condition; `=> result >= 0` is a postcondition.

Though C# contracts can be verbose too:
```csharp
Contract.Requires(x >= 0);
Contract.Ensures(Contract.Result<int>() >= 0);
```

## When Token Efficiency Matters Less

Token efficiency is less critical when:

1. **Context is plentiful** - Large context windows reduce pressure
2. **Comprehension matters** - Worth extra tokens for clarity
3. **Contracts add value** - Security/correctness worth the cost
4. **Precision editing** - Tool-owned identities can target edits, but token savings need separate measurement

---

## Interpretation

The retained historical composite is **1.42×** on its recorded corpus. This page
does not establish that value for current native syntax or for an agent's actual
input/output tokens.

Use the exact original bytes, options and comparison policy when replaying a
historical result. For a new measurement, record the selected current inputs,
semantic-equivalence controls and all three raw dimensions. Keep model usage,
cache tokens, editing behavior and paid evaluation separate from this static
source-size proxy.
