> **Syntax and measurement:** These are current native compiler examples, not
> a remeasurement of historical benchmark results. The database and network
> examples use explicitly labelled synthetic dependency rows, not live services.

**Feature:** Compiler-enforced effect declarations

**Related metric:** [Effect Discipline](/docs/benchmarking/metrics/effect-discipline/)

**C# comparison:** C# has no built-in Calor-style effect rows; libraries,
analyzers and API contracts can still convey effect information.

## Overview

The compiler checks declared effects against recognized operations and resolved
calls. `!` declares a pure row; `! cw` admits console writes. For ordinary
resolved internal calls, available computed body effects propagate to callers.
Declared rows remain permission ceilings, not evidence that the body actually
performs every admitted effect. Dispatch and callback boundaries also use
declared rows.

Unresolved calls, preserved C# and other opaque boundaries require explicit
diagnostics or assumptions. A clean-looking row alone is not proof that those
boundaries were resolved. Callback rows also participate in checking; missing
or incompatible rows have their own diagnostics.

`--permissive-effects` changes that policy. It waives unknown-call diagnostics
and demotes ordinary undeclared-effect errors. It is not evidence that an
unknown operation is pure and must not count as ordinary enforced native
acceptance. See [Effects](/docs/syntax-reference/effects/).

## Why It Matters

Undeclared I/O can make tests, refactoring and dependency analysis unreliable.
Effect rows expose permissions that callers must account for on the checked
surface.

They do **not** by themselves establish determinism, thread safety, bounded
execution, exception freedom or complete knowledge of external libraries.
Those are separate properties.

## How It's Measured

An effect-checking evaluation must keep the original programs, compilation
options and expected outcomes fixed. Report direct and transitive violations,
unresolved calls, assumptions and waivers separately. A parse success or
preserved C# frame is not a native effect-checking result.

The executable controls below cover known direct console output and declared
rows in a closed source call graph. They do not measure actual database or
network implementation effects.

## Example

This complete example contains actual console output in a resolved source
callee. Its pure caller is rejected with `Calor0410`:

```calor expect=Calor0410
module TransitiveLogging
  func LogMessage private (string:message) → void
    Console.WriteLine(message)

  func Process () → int
    !
    LogMessage("Saved")
    return 42
```

If logging is intended, the caller must admit `cw`. Otherwise remove or replace
the operation. Changing the declaration is an API policy decision, not proof
that the original program already met its row.

The following dependencies, in contrast, are **synthetic stubs**. Their private
bodies infer Pure because they only return constants:

```calor
module OrderEffects
  func SaveOrder private () → bool
    return true

  func SendConfirmation private () → bool
    return true

  func ProcessOrder () → bool
    ! db:rw
    SaveOrder()
    SendConfirmation()
    return true
```

`ProcessOrder()` returns `true` and compiles. The available computed effects of
these source bodies are empty. This is **not** a negative network-effect
example: merely naming a function `SendConfirmation` does not make it perform
network I/O.

## What It Catches

### Hidden Network Calls

Real network operations need recognized or otherwise justified effect facts.
This synthetic dependency does not exercise a real HTTP client:

```calor
module HiddenNetwork
  func FetchExchangeRate private () → int
    return 2

  func Calculate () → int
    !
    return 100 * FetchExchangeRate()
```

`Calculate()` returns `200` and compiles: the known source callee returns a
constant. It must not be counted as detection of an undeclared network call.

### Undeclared Database Writes

Likewise, these synthetic dependencies perform no database operations. Their
caller's database permission does not prove that they access a database:

```calor
module DatabasePermissions
  func GetById private (int:id) → int
    return id

  func WriteAudit private (int:id) → bool
    return true

  func GetUser (int:id) → int
    ! db:r
    let int:user = GetById(id)
    WriteAudit(id)
    return user
```

`GetUser(42)` returns `42` and compiles. A real database-write control needs an
actual supported operation and its reference/effect context. This stub is not
such a control.

### Logging in "Pure" Functions

This example uses an actual recognized .NET console operation, not a synthetic
logger whose effects were guessed from its name:

```calor expect=Calor0410
module UndeclaredLogging
  func Report (string:message) → bool
    !
    Console.WriteLine(message)
    return true
```

Normal enforcement rejects the missing `cw` permission with `Calor0410`.

## Effect Propagation

Pure calls can compose without adding permissions:

```calor
module PureComposition
  func Increment private (int:value) → int
    return value + 1

  func Calculate () → int
    !
    return Increment(41)
```

`Calculate()` returns `42`. This observation is not a proof over all integer
inputs: checked overflow remains possible for `Increment(int.MaxValue)`.

## Effect Checking Modes

### Default Mode (Warnings)

Known undeclared effects are errors. Unknown-call diagnostics such as
`Calor0411` are warnings by default, but an unknown effect can also make an
under-declared caller fail with `Calor0410`. A warning is not a purity proof.

```bash
calor -i app.calr -o app.g.cs
```

### Strict Mode (Errors)

Strict effects promote applicable unknown-effect warnings to errors:

```bash
calor -i app.calr -o app.g.cs --strict-effects
```

Inspect binding errors separately: a missing type or reference is not repaired
by changing effect-checking mode. Permissive mode also does not waive every
callback-row or effect-manifest error.

## Comparison with Implicit Effects

| Aspect | C# | Calor |
|:-------|:---|:------|
| Effect information | API contracts, implementation, analyzers and conventions | Explicit rows plus compiler resolution |
| Native row enforcement | Not a built-in language feature | Checked for supported resolved operations and calls |
| External boundaries | Need dependency context | Also need context; unresolved effects remain explicit |
| Thread safety | Needs separate reasoning | Also needs separate reasoning |

### C# Example

This original fragment has unspecified dependencies and is not a standalone
execution fixture:

```csharp
// C#: What effects does this have?
public async Task<User> GetUser(int id)
{
    var user = await _repository.GetById(id);  // Database? Memory?
    _logger.Log($"Retrieved user {id}");        // Console? File? Network?
    await _cache.Set(user);                      // Memory? Redis?
    return user;
}
// Answer: You have NO IDEA without reading every dependency
```

The comment overstates the comparison: dependency interfaces and documentation
can provide information without reading every implementation. They are not,
however, Calor's checked source effect rows.

### Calor Example

This **separate synthetic pipeline** has a conservative public budget and
inferred private bodies. It is not a conversion or runtime-equivalent
implementation of the C# fragment. None of these stubs performs database,
console or network I/O:

```calor
module DeclaredPipeline
  func ReadUser private (int:id) → int
    return id

  func LogUser private (int:user) → void
    return

  func CacheUser private (int:user) → int
    return user

  func GetUser (int:id) → int
    ! db:r,cw,net:rw
    let int:user = ReadUser(id)
    LogUser(user)
    return CacheUser(user)
```

`GetUser(42)` returns `42`. Its declared permissions are conservative: admitting
an effect does not mean every invocation performs that effect.

## Benefits for AI Agents

### 1. Filtering by Effect

Use compiler/project-index tooling to inspect rows and resolved callees.
Text searches are useful navigation, not a substitute for semantic resolution.

### 2. Refactoring Safety

Recompile the exact changed program with normal enforcement. Inspect unknown
calls and assumptions instead of treating a written pure row as proof.

### 3. Test Planning

Rows can identify dependency boundaries worth isolating in tests. A `cw` row
does not prove a function is a console mock, and a pure row does not eliminate
the need for boundary and exception tests.
