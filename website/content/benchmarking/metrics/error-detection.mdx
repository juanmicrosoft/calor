## Overview

The calculator assigns points for contract, assertion and type markers. It does
not ask an agent to find bugs, execute every input or prove every contract. A
higher score means more recognized source signals, not more demonstrated bug
detections.

---

## Why It Matters

When reviewing code, agents need to detect:
- Precondition violations at call sites
- Postcondition violations in implementations
- Missing null checks
- Bounds errors
- Invariant violations

Explicit contracts state obligations that an agent, verifier or runtime check
can inspect. Their presence alone does not establish that the obligations are
correct or that a call satisfies them.

## How It's Measured

### Calor Detection Factors

These are the calculator's weights. The syntax column shows the native form the
calculator looks for.

| Factor | Points | Rationale |
|:-------|:-------|:----------|
| Precondition: `| (expression)` refinement | 0.25 | States a caller obligation |
| Postcondition: `=> expression` | 0.20 | States a result obligation |
| Invariant: `invariant expression` | 0.15 | States a state constraint |
| Effect row: `! effects` | 0.10 | Declares permitted effects |
| Typed parameters | 0.05 | Declares input types |
| Typed return | 0.05 | Declares the result type |

Base score: 0.30

On this page's five Calor programs the calculator scores 0.95 for the three that
have a precondition, a postcondition and an effect row, and 0.75 for the two
without a postcondition. None has an invariant.

### C# Detection Factors

| Factor | Points | Rationale |
|:-------|:-------|:----------|
| Has `Debug.Assert` | 0.15 | Runtime assertion checking |
| Has `Contract.Requires` | 0.20 | Code Contracts precondition |
| Has `Contract.Ensures` | 0.15 | Code Contracts postcondition |

| Has `readonly` | 0.05 | Immutability enforcement |

Base score: 0.30, cap at 0.90

## Example Comparison

### Calor with Contracts

```calor
module DivisionSignals
  func Divide public (int:a | (# >= 0), int:b | (# != 0)) → int
    !
    => result >= 0
    return a / b
```

With runtime contract checks enabled, `Divide(9, 2)` returns `4`, while a zero
divisor or negative `a` fails a precondition. This is not a guarantee of
compile-time diagnosis at every call.

The postcondition is **incorrect for the declared input domain**:
`Divide(9, -2)` satisfies both preconditions but produces `-4`, failing the
postcondition. The example deliberately retains that mistake. A contract is
an obligation to check, not proof that the implementation meets it.

### C# Equivalent

```csharp
public static int Divide(int a, int b)
{
    if (b == 0)
        throw new ArgumentException("b cannot be zero");
    if (a < 0)
        throw new ArgumentException("a must be non-negative");

    var result = a / b;
    Debug.Assert(result >= 0);
    return result;
}
```

**Detection capability:**
- Must recognize exception pattern as precondition
- Must recognize Debug.Assert as postcondition
- Less structured, more inference required

This C# fragment has the same negative-divisor mistake. It is not
exception-equivalent: its guards throw `ArgumentException`, while enabled Calor
contracts throw `ContractViolationException`. `Debug.Assert` also depends on the
C# build configuration and is not Calor's runtime postcondition mechanism.

## Bug Categories

### Null Reference

**Calor contract:**
```calor
module NullSignals
  func Length public (string:input | (# != null)) → int
    !
    return input.Length
```

`Length("abc")` returns `3`. Passing null through the CLR boundary fails the
precondition when checks are enabled; disabling checks exposes the ordinary
null dereference instead.

**C# detection:**
```csharp
if (input == null) throw new ArgumentNullException();
// or
input ?? throw new ArgumentNullException();
```

### Bounds Check

**Calor contracts:**
```calor
module BoundsSignals
  func At public (int[]:array, int:index | ((# >= 0) && (# < array.Length))) → int
    !
    return array[index]
```

`At([42], 0)` returns `42`. Index `-1` or `1` fails a precondition with checks
enabled and throws `IndexOutOfRangeException` with checks off. These contracts
do not guard a null array: evaluating `array.Length` can itself throw.

**C# detection:**
```csharp
if (index < 0 || index >= array.Length)
    throw new ArgumentOutOfRangeException();
```

### Contract Violation

**Calor:** Direct contract syntax identifies obligations for supported verifier
queries and enabled runtime checks. Unsupported or unproved queries are not proof.

**C#:** Must parse exception throws and assertions.

## Real-World Example

### Finding a Bug

Given this buggy call:

```calor
module BuggyCaller
  func Divide (int:a | (# >= 0), int:b | (# != 0)) → int
    !
    => result >= 0
    return a / b

  func Trigger public (int:x, int:y) → int
    !
    let int:result = Divide(x, y - y)
    return result
```

**Possible agent reasoning, not an observed agent run:**
1. See `Divide(x, y - y)`.
2. Read its `int:b | (# != 0)` obligation.
3. Evaluate `y - y` as zero.
4. Report that this call violates the precondition.

`Trigger(9, 5)` actually fails a runtime precondition with checks enabled.
With checks off, it reaches integer division by zero. Compilation of the example
does not by itself establish an interprocedural static diagnosis.

**C# agent detection:**
1. See `Divide(x, y - y)`
2. Find Divide implementation
3. Parse exception throw pattern
4. Infer precondition
5. Evaluate argument
6. Report potential issue

## Scoring Example

This is an explanatory example, not a measured corpus input. Its nullable return
type does not make the enabled precondition optional.

### Calor Code

```calor
module NullableSignals
  func SafeDivide public (int:a, int:b | (# != 0)) → int?
    !
    => result == a / b
    if b == 0
      return null
    else
      return a / b
```

**Score from the current calculator:**
- Base: 0.30
- Precondition: +0.25
- Postcondition: +0.20
- Effect row: +0.10
- Typed parameters: +0.05
- Typed return: +0.05

**Total: 0.95**

### C# Equivalent

```csharp
public static int? SafeDivide(int a, int b)
{
    if (b == 0)
        return null;
    return a / b;
}
```

**Score from the current calculator:**
- Base: 0.30

**Total: 0.30**

**Ratio: 0.95 / 0.30 = 3.17x.**

The C# fragment earns no bonus because none of the C# factors appear in it: its
`if (b == 0)` guard is not one of the recognized patterns. The ratio counts
recognized source signals. It is not evidence that Calor found more bugs.
An earlier version of this page showed an illustrative 0.85 / 0.45 = 1.89x that
the calculator never produced.

For valid input `(6, 2)`, both implementations return `3`. For `(6, 0)`, the
C# version returns null, but the Calor version fails `int:b | (# != 0)` when
checks are enabled; only checks-off execution takes its null branch. The two
versions do not have the same API behavior.

## Interpretation

The historical aggregate is 1.49x. It shows that the calculator finds more explicit
bug-detection signals in the paired Calor corpus; it does not by itself prove a
1.49x reduction in production defects.

The heuristic awards more points when:
- Functions have explicit preconditions and postconditions
- Different contract kinds are present; repeating one kind adds no points
- Recognized markers are present, regardless of condition complexity

No agent accuracy, false-positive rate or production defect reduction was
measured by these source-pattern scores.
