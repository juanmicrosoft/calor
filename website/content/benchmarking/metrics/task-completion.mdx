## Overview

The Task Completion runner asks a model for programs, compiles its responses and
executes manifest test cases. The neutral manifest supplies the same functional
requirements to both languages without language-specific syntax hints.

The runner still supplies language-specific system prompts, including Calor
teaching material. Neutral task wording does not make the entire model context
identical or eliminate every source of benchmark bias.

---

## What This Benchmark Answers

**Primary Question:** Can an LLM learn Calor and write correct code as easily as C#?

**Available result:** The published file has a 1.00x summary ratio, but both scores
are zero after provider failures. None of its 50 tasks uses the neutral prompt
field. That ratio is a zero-denominator fallback, **not evidence of language
parity**, successful learning or productivity.

---

## Methodology

### Language-Neutral Prompts

Unlike benchmarks that give language-specific guidance, our prompts describe **what** to achieve without dictating **how**:

```
Write a public function named Factorial that computes the factorial
of an integer n. The function must only accept non-negative values
of n. The result is always at least 1.
```

The same prompt goes to both Calor and C#. The LLM must apply its knowledge of each language to produce idiomatic code.

### Why Neutral Prompts Matter

| Approach | Problem |
|:---------|:--------|
| Calor-biased prompts | "Add a Calor `requires` precondition..." supplies syntax instead of testing its selection |
| C#-biased prompts | Unfair to Calor, doesn't reflect real usage |
| **Neutral prompts** | Tests whether LLM can translate requirements to idiomatic code |

### Task Corpus

The neutral manifest defines **50 programming tasks** across 4 categories:

| Category | Tasks | Examples |
|:---------|:------|:---------|
| basic-algorithms | 15 | Factorial, Fibonacci, IsPrime, GCD, Power |
| safety | 10 | SafeDivide, Clamp, SafeModulo, NormalizeScore |
| data-structures | 10 | Sum, Max, Min, Average, Median |
| logic | 15 | BoolToInt, LogicalAnd, IsMultipleOf, SameSign |

### Scoring Formula

Each task in the neutral manifest assigns these weights:

| Factor | Weight | Description |
|:-------|:-------|:------------|
| Compilation | 40% | Does the generated code compile? |
| Test Cases | 60% | What percentage of test cases pass? |

**Final score:** `0.4 × compile + 0.6 × tests`

Here `compile` is 0 or 1, and `tests` is the fraction of that task's executed
cases that pass. The neutral manifest assigns no contract-verification bonus.
The loader treats an omitted JSON `contracts` weight as zero; the runner rejects
invalid weights before requesting that task's model responses.
Changing prompts, weights, cases or teaching context requires a new identified
run; it does not revise an earlier result.

## What This Tells Us

### Calor is Learnable?

That remains a question for an actual successful run. This file establishes
neither equal compilation rates nor equal test performance. Provider failures,
cached responses, dry runs and mock-provider output are not evidence that a
real model learned the language.

### Task Completion ≠ Code Value

This benchmark measures **task completion** - can correct code be written? It does **not** measure:
- Whether the code has better safety properties
- Whether contracts catch bugs that C# misses
- Whether the code is more maintainable

These are different questions that require different benchmarks.

## Example: Generated Code Comparison

### Task: SafeDivide
**Prompt:** "Write a public function named SafeDivide that divides integer a by integer b. Division by zero must not be allowed."

**Current native illustration, not an archived model response:**
```calor
module TaskSafeDivide
  func SafeDivide public (int:a, int:b) → int
    requires b != 0
    return a / b
```

**Original C# illustration:**
```csharp
public static class Functions
{
    public static int SafeDivide(int a, int b)
    {
        if (b == 0)
            throw new ArgumentException("Division by zero");
        return a / b;
    }
}
```

For `(6, 2)` both return `3`. With runtime checks enabled, Calor's zero-divisor
contract throws `ContractViolationException`; the C# guard throws
`ArgumentException`. With Calor checks off, division by zero reaches the ordinary
`DivideByZeroException`. These are explicit boundary observations, not a model
task-completion score or a claim of exception equivalence.

---

### Task: NormalizeScore
**Prompt:** "Write a public function named NormalizeScore that normalizes a score to the 0-100 range using the formula (score * 100) / maxScore. The maxScore must be positive, score must be non-negative, and score must not exceed maxScore."

**Current native illustration, retaining the original formula:**
```calor
module TaskNormalizeScore
  func NormalizeScore public (int:score, int:maxScore) → int
    requires score >= 0
    requires maxScore > 0
    requires score <= maxScore
    => result >= 0
    => result <= 100
    return score * 100 / maxScore
```

**Original C# illustration:**
```csharp
public static int NormalizeScore(int score, int maxScore)
{
    if (maxScore <= 0)
        throw new ArgumentException("maxScore must be positive");
    if (score < 0)
        throw new ArgumentException("score must be non-negative");
    if (score > maxScore)
        throw new ArgumentException("score must not exceed maxScore");

    return (score * 100) / maxScore;
}
```

For `(75, 100)` both return `75`. Calor adds runtime result obligations, not a
proof that this formula is correct for every accepted integer.

The multiplication can overflow within the declared valid domain. For
`(30000000, 30000000)`, Calor's normal checked arithmetic throws
`OverflowException`, before a postcondition can check the result. Turning off
contracts does not turn off that arithmetic check. This C# fragment's ordinary
unchecked arithmetic returns `-43`, not `100`.

The original formula is deliberately not repaired here. Its preconditions do not
make it total over the accepted integer domain. Output bounds alone would not
prove the formula correct either: the unchecked C# call with both arguments
`int.MaxValue` returns `0` instead of `100`.

## Contract Usage Analysis

These are possible translations of requirements into current native contracts.
They are not observed extraction rates from the failed published run.

| Requirement Language | Generated Contract |
|:---------------------|:-------------------|
| "must only accept non-negative" | `requires n >= 0` |
| "must not be zero" | `requires n != 0` |
| "result is never negative" | `=> result >= 0` |
| "result is always at least 1" | `=> result >= 1` |
| "must be between X and Y" | `requires n >= X` and `requires n <= Y` |

Whether a model chooses complete, correct contracts must be measured from its
actual responses and tested obligations, including invalid-input cases.

## Benchmark Execution

### Running Locally

```bash
# Inspect options without making model requests
dotnet run --project tests/Calor.Evaluation -- llm-tasks --help

# Estimate with a configured provider; do not generate model responses
dotnet run --project tests/Calor.Evaluation -- llm-tasks \
  --manifest tests/Calor.Evaluation/Tasks/task-manifest-neutral.json \
  --dry-run

# Paid run: requires separate authorization and provider credentials
dotnet run --project tests/Calor.Evaluation -- llm-tasks \
  --manifest tests/Calor.Evaluation/Tasks/task-manifest-neutral.json \
  --budget 5.00 \
  --refresh-cache
```

### Cost Controls

- Results are cached to avoid redundant API calls
- The budget option is checked between tasks, not as a hard per-request billing cap
- A task and its retries can exceed the remaining budget
- The old ~$0.76 estimate for 50 tasks is not a current price quote
- Dry-run estimates and cache hits are not newly executed model evaluations

### Model Information

| Property | Value |
|:---------|:------|
| Provider | Anthropic |
| Recorded provider key | `claude` |
| Recorded model | Not available in the failed language results |

The previously advertised `claude-sonnet-4-20250514` ID does not establish which
model handled a failed request. A new accepted run needs its actual model,
teaching context, prompts, options and case outcomes recorded.

## Transparency

### Reproducibility

All benchmark data is available:
- Task definitions: `tests/Calor.Evaluation/Tasks/task-manifest-neutral.json`
- Current teaching source: `src/Calor.Compiler/Resources/Teaching/reference.json` (rendered into the packaged reference consumed by current evaluation runs; historical runs retain their recorded prompts).
- Published historical record: `website/public/data/llm-results.json` (50 failed
  task pairs, empty generated code, no executed cases)
- New runner output defaults to `llm-results.json`; publishing it is a separate action

### Limitations

- Results may vary with model updates
- 50 tasks is a limited sample size
- Simple tasks may not reveal differences in more complex scenarios
- A ratio alone cannot distinguish equal successes from equal failures
- The available file does not establish results for the current neutral manifest

## Future: Safety Benchmark

Task completion measures "can correct code be written?" A separate **Safety Benchmark** would measure "does the code catch more bugs?" by:

1. Running adversarial tests with invalid inputs
2. Measuring contract enforcement (Calor) vs exception handling (C#)
3. Comparing error message quality and precision

Such a comparison needs the same input domain and runtime observations in both
languages. It must not count contract presence, differing exception types or
compilation alone as proof of superior bug detection.
