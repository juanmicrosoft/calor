Calor explores a simple question: when an AI assistant helps write .NET
software, can the language make it easier for people to see what a change is
meant to do and check whether it follows important rules?

Calor is an experimental programming language. It lets a project write down
some expectations alongside its code, checks certain cases, and runs on the
.NET runtime. It is not a proven way to make software safer or
teams more productive.

## What Calor makes easier to see

When reviewing a change, people often need to know what a piece of code is
expected to do and what actions it may take. In many languages, they have to
work this out by reading the implementation. Calor gives a project a way to
write down some of that information directly:

| What you want to know | What Calor can record |
|:---------------------|:---------------------|
| What should this part of the program do? | Rules about the input and the result |
| What actions might it take? | Whether it reads or changes things such as files, databases, or network services |
| How can a tool refer to a particular part? | An optional name that stays with that part when it moves |

This information can help people and tools review a change. It does not replace
reading code, testing it, or deciding whether the rules describe the right
behavior.

## What Calor checks—and what it cannot

Calor can flag some conflicts between the rules a project has written down and
the code being built. For supported rules, an optional verifier can sometimes
show that a rule holds or give an example that breaks it. It may also report
that it could not decide.

A successful check applies only to the rule and code it examined. It does not
prove that the whole program is correct, safe, or free of bugs. Some code,
external libraries, and system behavior are outside the checks. Keep code
reviews and tests in place.

For exact details, see the [guide to check results and limits](/docs/guides/verification-guarantees/).

## A tradeoff: helpful to tools, unfamiliar to people

Calor is designed so software tools can find important information in a
program. Its notation may look unfamiliar and take time to get used to.
That is a real cost, not a benefit for everyone.

You do not need to memorize the notation to try Calor. An AI coding assistant
can write it, but a person still needs to decide what the program should do,
review its behavior, and understand any limits in the checks.

## What the research does—and does not—show

Calor's published comparisons use a limited set of examples and calculations.
They do not measure whether real teams finish work faster, make fewer mistakes,
or build safer software with Calor. The results are not proof of an advantage.
See the [research results and their limits](/docs/benchmarking/).

The project has not established a qualifying adopter, independent adopter
handoff, economic advantage, or safety advantage. Treat Calor as an experiment:
start with a small task, keep your normal checks, and decide based on your own
experience.

For readers who want the exact historical figures: one comparison prepared for
publication with v0.22.0 was recorded on 2026-09-15 for 30 repetitions from
source `c2a8816d`, which declared compiler v0.21.0 before the release version
change. Its calculated Information Density ratio was 0.97x. The source pairs
were not all behaviorally equivalent. This calculation did not measure real
team performance or prove an advantage. The
[research status and evidence limits](/docs/benchmarking/evidence-status/)
explain what has and has not been studied.

## Can I start with an existing C# project?

Yes. You can keep your existing C# project and convert to Calor in phases.
Start with one small, well-tested file, keep the rest as it is, and decide
whether to convert more after you have tried the workflow.

| Calor may be worth exploring if… | Calor may not be a fit if… |
|:--------------------------------|:---------------------------|
| Your team uses AI coding assistants for .NET projects and wants to try clearer rules for review | You need a stable, widely adopted tool with long-term support today |
| You are comfortable testing an early project and keeping your own reviews and tests | You need all code to be easy to read without learning unfamiliar notation |
| You want to try one small change before deciding whether to continue | You need support for code that Calor does not currently handle well |

The [phased conversion guide](/docs/guides/adding-calor-to-existing-projects/)
explains that journey, including how to review each step before expanding.

## Common questions

### Do I need to learn Calor?

You can ask an AI assistant to write Calor, but reviewers still need to
understand what a change is meant to do and what the checks cover. You do not
need to learn every notation mark before trying the guided example.

### Do I still need code reviews?

Yes. Review whether the change does what you asked, whether its written rules
make sense, what the checks could not decide, and whether the tests pass.
Calor does not take responsibility for those decisions.

### Can I still use my .NET tools?

Calor applications use the .NET runtime and can be built and tested with
.NET tools. Try the tools your team relies on during your first small trial;
not every feature or tool integration is supported.

### Is Calor ready for production?

Calor is a pre-1.0 research project maintained by one person. Its checks and
conversion tools have known limits, and there is no established evidence that
it improves safety or productivity. If you evaluate it, start with a small,
low-risk task and follow the [adoption guide](/docs/guides/adoption-playbook/)
and [check limitations](/docs/guides/verification-guarantees/).

### Where can I find the technical details?

The [language reference](/docs/syntax-reference/) and
[technical specification](/docs/semantics/) explain the notation and exact
behavior for developers and coding agents.
