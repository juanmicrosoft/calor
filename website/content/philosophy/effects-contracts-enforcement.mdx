Coding agents may make contracts and effect annotations cheaper to produce.
That is a hypothesis to measure, not a guarantee of correct annotations or
zero-cost review. These techniques are also practical outside agent-oriented
languages.

---

## The 50-Year Struggle

Computer scientists have known since the 1970s how to make software more reliable:

- **Effect Systems**: Track side effects at compile time (Gifford & Lucassen, 1986)
- **Design by Contract**: Specify preconditions and postconditions (Meyer, 1986)
- **Dependent Types**: Encode invariants in the type system (Martin-Löf, 1972)

These techniques can prove specific obligations inside a precisely modeled
surface. They do not prove that an entire program is correct. When Calor cannot
make a clean proof, it reports why. Runtime checks separately require an enabled
contract mode and supported lowering.

**So why isn't all software written this way?**

---

## Why Humans Don't Write Annotations

Annotation burden is one integration cost. Tooling, libraries, education,
runtime behavior, and review requirements also matter; the examples below do
not establish why a language or verification system gained adoption.

| Reason | Impact |
|:-------|:-------|
| **Annotation fatigue** | Developers skip contracts when tired or rushed |
| **Time pressure** | Deadlines trump verification discipline |
| **Maintenance burden** | Contracts rot when code changes |
| **Learning curve** | Teams resist unfamiliar syntax |
| **Broad interfaces** | A broad exception or effect declaration can lose useful specificity |

### Haskell's Effect System

```haskell
-- Explicit signatures expose these IO-returning interfaces
readFile :: FilePath -> IO String
writeFile :: FilePath -> String -> IO ()

-- An implementation performing IO also has an IO result
processConfig :: FilePath -> IO Config
processConfig path = do
    contents <- readFile path  -- Forces IO in type signature
    return (parseConfig contents)
```

Haskell can infer types; explicit signatures are not required everywhere.
This example shows an `IO` interface, not an adoption or productivity result.

### Eiffel's Design by Contract (1986)

```eiffel
-- An Eiffel contract written alongside its implementation
deposit (amount: INTEGER)
    require
        positive_amount: amount > 0
        account_open: is_open
    do
        balance := balance + amount
    ensure
        balance_increased: balance = old balance + amount
    end
```

The contract makes the intended balance change explicit. Its usefulness still
depends on the chosen specification and implementation.

### Java's Checked Exceptions

```java
// Java requires handling or declaring checked exceptions
public void processFile(String path) throws IOException, ParseException {
    String content = Files.readString(Path.of(path));  // throws IOException
    parse(content);  // throws ParseException
}
```

Unchecked exceptions do not have this declaration requirement. Broad checked
exception declarations can reduce specificity; they do not prove that the
implementation handles failures correctly.

### C# Code Contracts (2008-2015)

Microsoft introduced Code Contracts for .NET—a promising approach to design-by-contract:

```csharp
public int Divide(int a, int b)
{
    Contract.Requires(a >= 0 && b > 0);
    Contract.Ensures(Contract.Result<int>() >= 0);
    return a / b;
}
```

The [historical Code Contracts project](https://github.com/Microsoft/CodeContracts)
is a useful comparison, not evidence that agents eliminate integration costs.
Integer division truncates: a postcondition claiming `result * b == a` would
be false for `Divide(9, 2)`.

## Why AI Agents Change Everything

Agents can draft annotations, but their output still needs checking:

| Human Developers | Coding Agents |
|:----------------|:--------------|
| Write and review annotations | Generate candidates that still need review |
| Can forget to update contracts | Can produce stale or vacuous contracts |
| Can skip checks | Can omit checks or misread failures |
| Learn a language and toolchain | Need accurate teaching material and real compiler feedback |
| Balance time and correctness | Consume tokens, execution time, and reviewer attention |

Generating a contract is not the same as choosing the right contract.

Measure annotation quality, task outcomes, review time, and total cost under
both workflows before claiming a benefit.

## C# vs Calor: What's Different

### Problem 1: Hidden Side Effects

In C#, function signatures don't reveal their side effects:

```csharp
// C#: What effects does this function have?
public async Task<User> GetUser(int id)
{
    var user = await _repository.GetById(id);  // Database? Memory?
    _logger.Log($"Retrieved user {id}");        // Console? File? Network?
    await _cache.Set(user);                      // Memory? Redis?
    return user;
}
// Answer: You have NO IDEA without reading every dependency
```

In Calor, an effect row is a permission contract. This is a signature template,
not an executable database or network implementation:

```calor-fragment
func GetUser public (int:id) → User
  ! db:r,cw,net:rw
  // Implementation and dependency contracts are required.
```

The row permits database reads, console writes, and network operations. It does
not prove that all three happen, identify a server, or establish that a
third-party API's declared effects are accurate.

This complete example isolates a real console write, without pretending to
query a database or send a network request:

```calor
module VisibleConsoleEffect
  func LogRetrieval public (int:id) → int
    ! cw
    System.Console.WriteLine("Retrieved user {0}", id)
    return id
```

`LogRetrieval(42)` writes `Retrieved user 42` once and returns `42`.
The Console call performs the formatting under its `cw` contract; the example
does not assume that numeric interpolation is pure.
External APIs need selected-call coverage and reviewed effect contracts;
unknown calls are not automatically pure.

### Problem 2: Contracts That Disappear

C# offers `Debug.Assert`, but these vanish in release builds:

```csharp
// C#: These contracts vanish in release builds
public static int Divide(int a, int b)
{
    Debug.Assert(b != 0, "Divisor cannot be zero");  // GONE in Release
    return a / b;
}
// In production: DivideByZeroException with no context
```

Calor preconditions (parameter refinements) are always emitted as runtime
checks, in every contract mode. For supported body shapes,
postconditions are emitted unless optional `--verify` produces an eligible,
clean, non-vacuous `proven` result. Inconclusive results do not authorize
proof-based removal; they do not guarantee that runtime lowering is supported.
See [verification modes and limits](/docs/guides/verification-guarantees/).

```calor
module EnforcedDivide
  func Divide public (int:a, int:b | (# != 0)) → int
    !
    return a / b
```

`Divide(9, 2)` returns `4`. `Divide(9, 0)` fails the precondition before
division, in every contract mode. A parameter refinement has no custom-message clause.
The condition does not prevent every arithmetic exception:
`Divide(int.MinValue, -1)` still overflows.

The generated check throws `System.ArgumentOutOfRangeException` with
`ParamName` `b` and the message
`Violation of inline refinement for parameter 'b'`. The guard is the same in
`debug`, `release`, and `off` modes. Postconditions and invariants still throw
`Calor.Runtime.ContractViolationException`. An explicit body check is the
alternative when an API needs its own exception type or message.

## Interprocedural Analysis

Calor follows resolved calls within its admitted effect-analysis surface.
For example, the following caller is missing the console permission:

```text illustrative
error Calor0410: Function 'ProcessOrder' uses effect 'cw'
                 but does not declare it
  Call chain: ProcessOrder → NotifyCustomer → PrintNotice → System.Console.WriteLine
```

This is an explanatory call chain, not a byte-for-byte CLI transcript.

```calor expect=Calor0410
module MissingConsoleEffect
  func ProcessOrder (int:order) → bool
    !
    return NotifyCustomer(order)

  func NotifyCustomer (int:order) → bool
    ! cw
    return PrintNotice(order)

  func PrintNotice (int:order) → bool
    ! cw
    System.Console.WriteLine("Order {0}", order)
    return true
```

Ordinary compilation rejects `ProcessOrder` with `Calor0410`. Declaring the
actual permission makes this complete counterpart compile:

```calor
module DeclaredConsoleEffect
  func ProcessOrder (int:order) → bool
    ! cw
    return NotifyCustomer(order)

  func NotifyCustomer (int:order) → bool
    ! cw
    return PrintNotice(order)

  func PrintNotice (int:order) → bool
    ! cw
    System.Console.WriteLine("Order {0}", order)
    return true
```

`ProcessOrder(42)` writes `Order 42` once and returns `true`. These controls
exercise source calls and an actual console effect, not arbitrary network
coverage. Unknown, preserved, or unmodeled paths cannot borrow this result.

## The Virtuous Cycle

When agents both write and verify code, a powerful feedback loop emerges:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Agent generates code  ───►  Compiler verifies effects     │
│         ▲                           │                       │
│         │                           ▼                       │
│  Agent fixes violations  ◄───  Errors with call chains     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

1. **Agent generates code** with effect declarations and contracts
2. **Compiler verifies** effects are properly declared
3. **Errors include resolved call chains** when the analysis can recover them
4. **Agent fixes violations** with precise information
5. **Repeat until checks pass and the remaining assumptions are reviewed**

This defines a feedback loop to evaluate. A passing compiler check still
requires review of assumptions, coverage boundaries, and task behavior; the
diagram is not a measured productivity result.

## Real-World Impact

### Bug Categories Surfaced Earlier

| Bug Category | Traditional Detection | Calor Detection |
|:-------------|:---------------------|:----------------|
| Undeclared side effect in an analyzed path | Review or runtime observation | Compile error |
| Possibly-null value crossing a supported receiving boundary | Runtime null-reference exception | Calor 0.22 binding Error at initialization, native return, or method input |
| Invalid state transition | Integration test (if lucky) | Contract violation when the contract covers it |
| Effect leaking through a resolved supported call | Review or runtime observation | Compile error; call-chain detail depends on analysis coverage |
| False contract on a supported runtime path | Tests or explicit validation | `ArgumentOutOfRangeException` for a failed precondition (every contract mode); `ContractViolationException` for a failed postcondition when checks are enabled |

The [nullability guide](/docs/guides/nullability-and-dotnet-interop/) defines
Calor 0.22's bounded support. It does not promise whole-program
null safety: mutable assignment/rebinding and constructor-input enforcement
remain excluded. Missing interop annotations (`Oblivious`) are conservatively
possibly null; available annotations are trusted, not proved. Type/effect
controls and transpile-only do not bypass active binding checks.

These checks are separate from contract proof. D3 nullability, D12 string
indexing/counting semantics, and D14 reference-model limits still require
verifier proof demotions and retained runtime guards.
[#875](https://github.com/juanmicrosoft/calor/issues/875) remains open. A bounded
regression set is not a universal safety result; see
[Verification Guarantees and Limits](/docs/guides/verification-guarantees/).

## Getting Started

To see effect and contract enforcement in action:

```bash
# Compile with enforcement (enabled by default)
calor --input myprogram.calr --output myprogram.g.cs

# See effect violations with call chains
# error Calor0410: Function 'ProcessOrder' uses effect 'cw' but does not declare it

# Migration-only bypass: NOT evidence of effect enforcement
calor --input myprogram.calr --output myprogram.g.cs --no-enforce-effects
```

Do not count bypassed compilation as a normally enforced native success.
