If you're skeptical about Calor, you're in good company. The most common question we hear is:

> "AI models were trained on millions of files of Python, JavaScript, C#, and other languages. They've never seen Calor. How can they possibly write it?"

This is a completely valid concern. Let's address it directly.

---

## The Chicken and Egg Problem

Traditional programming languages succeed because:
1. Developers learn them
2. Developers write code in them
3. That code becomes training data for AI
4. AI learns to write that language

Calor breaks this cycle. It's a new language designed *for* AI agents, but AI agents weren't trained on it. So how can this work?

---

## Our Approach: Teach at Runtime

Instead of waiting for AI models to be trained on Calor (which could take years), we teach them at runtime using three mechanisms:

### 1. Project Instructions (CLAUDE.md)

When Claude Code starts a session, it reads `CLAUDE.md` from your project root. This file contains:

- **Clear rules**: "All new code MUST be written in Calor"
- **Syntax overview**: Key constructs and their meanings
- **Type mappings**: How C# types translate to Calor (`int` → `i32`)

Modern AI models can follow novel syntax instructions, but reliability depends
on the model, task, context, and feedback loop. The compiler, not the
instruction alone, determines whether generated Calor is valid.

### 2. Skills (Detailed Syntax Reference)

The `.claude/skills/` directory contains detailed syntax documentation that Claude can consult. Think of it as giving Claude a language reference manual it can look up when needed.

The `calor` skill includes:
- Complete syntax for all constructs
- Working templates (FizzBuzz, functions with contracts, classes)
- ID naming conventions

When Claude needs to write a loop or a conditional, it has the reference right there.

### 3. Hooks (Enforcement)

Here's where healthy skepticism meets practical engineering. What if Claude "forgets" the instructions? What if it falls back to C# out of habit?

The hook mechanism catches this:

```
Claude tries to create: UserService.cs
Hook response: BLOCKED

"This is a Calor-first project. Create UserService.calr instead."
```

The agent receives this feedback and may retry with the correct file extension.
The hook blocks the selected file operation; it does not guarantee a correct
retry or remove the need for review.

## Why This Can Work

### Models Can Use Runtime Guidance

Depending on the model and task, runtime guidance can help an agent:

- **Follow novel instructions** - use a syntax reference supplied in context
- **Generalize from examples** - adapt templates to related constructs
- **Respond to constraints** - revise an attempt after a hook or compiler error

These are capabilities to evaluate, not guaranteed outcomes.

### Calor's Syntax Is Designed for This

Calor's syntax is designed to make structure and constraints explicit. Whether
that makes a particular model more reliable is an empirical question:

| Design Choice | Why It Helps |
|:--------------|:-------------|
| Indentation-defined blocks | Scope is visible without structural closer tags |
| Optional stable IDs on structural targets | Clear targets when durable identity is needed |
| Lisp-style expressions | Unambiguous operator precedence |
| Declared effects | AI knows what side effects are allowed |

The syntax uses recurring declaration patterns such as `§F{id:Name:vis}`,
`§M{id:Name}`, and `§L{id:var:from:to:step}`. The reference documents those
patterns; it does not prove that every model extrapolates them correctly.

### The Feedback Loop Works

When the hook blocks a `.cs` file, the agent receives actionable feedback and
can retry with Calor. The repository has not measured how often one correction
is sufficient across current models and real projects.

## Evidence from Practice

The repository contains bounded tests of this approach:

The repository includes deterministic generation and structure calculators, but
they are not a substitute for a blinded, live-agent success study. In practice,
agents should use the compiler feedback loop: generate a small change, run
`calor -i change.calr -o change.g.cs`, and repair any syntax, type, contract,
or effect diagnostics. MCP clients can use the equivalent `calor_check` tool.

Instructions, skills, hooks, and compiler diagnostics form a concrete feedback
loop. The dated agent-task snapshot records 77 successful tasks out of 89 for
its model, prompt, and verifier configuration. That runner skipped lifecycle
hooks and made one agent invocation per task, so it did not test the full
feedback loop. It is not a model-wide reliability result or an independent
adopter study.

## Addressing Remaining Concerns

### "But what about complex programs?"

Calor compiles to C#. Claude already knows C# deeply. It's translating concepts it understands into a new syntax, not learning new programming concepts.

### "What if Claude hallucinates syntax?"

The Calor compiler rejects invalid syntax and reports diagnostics. An agent can
use those diagnostics to retry, but a diagnostic does not guarantee that the
next attempt compiles or satisfies the intended behavior.

### "Is this just prompt engineering?"

Yes and no. Project instructions and skills describe what to do. Hooks can block selected
operations, and compiler diagnostics reject invalid programs. Their combined
reliability has not been established across adopters or current models.

### "Will this work with other AI models?"

We provide integration guidance for Claude Code, Gemini CLI, Codex CLI, and
GitHub Copilot. Their lifecycle and policy-hook capabilities differ and evolve;
see the [integration pages](/docs/getting-started/) for the current setup and
verify the behavior of the installed client.

## The Bottom Line

The Calor workflow is designed around:

1. **Novel instructions** - CLAUDE.md provides the rules
2. **Reference documentation helps** - Skills provide syntax details
3. **Mechanical feedback** - Hooks block selected policy violations and the compiler rejects invalid programs

You do not need to assume that an agent already knows Calor. You still need to
measure the workflow on your tasks, review the generated behavior, and keep the
documented exit path. The
[research evidence status](/docs/benchmarking/evidence-status/) explains what
has and has not been established.

Try it yourself. Initialize a project, ask Claude to write some code, and see what happens:

```bash
dotnet new console -o TestProject
cd TestProject
calor init --ai claude
```

Then open Claude Code and ask: "Write a function that calculates factorial."
