Calor supplies project instructions, compiler tools and file-writing hooks for
Claude Code. They help an agent use the current language; they do not guarantee
that every generated program is correct.

## Quick setup

```bash
calor init --ai claude
```

Initialization configures the repository root when it can identify one.

| File | Purpose |
|:-----|:--------|
| `CLAUDE.md` | Project instructions and the generated native language reference |
| `.claude/settings.json` | Calor write/edit checks and post-write lint hooks |
| `~/.claude.json` | The project's `calor` MCP server configuration |

Review the command's actual created/updated-file report. Re-running it updates
the managed Calor instructions; it is not permission to discard custom project
configuration. Review changes before using `--force`.

The command does **not** install `.claude/skills/calor/SKILL.md` or
`.claude/skills/calor-convert/SKILL.md`.

## MCP server integration

MCP, the Model Context Protocol, exposes compiler operations to a compatible
client. The initializer records the server configuration; starting and approving
it remains the client's responsibility.

| Tool | Purpose |
|:-----|:--------|
| `calor_check` | Diagnostics, lint, type checking and validation actions |
| `calor_verify` | Contract verification with explicit result statuses |
| `calor_navigate` | Definitions, references, symbols, types and scope |
| `calor_structure` | Outlines, call graphs and impact |
| `calor_query` | Project-index callers, callees, impact and effect rows |
| `calor_analyze` | Additional analysis |

Consult [MCP tools](/docs/cli/mcp/) for the actual tool arguments and available
actions. A configured server is not evidence that a call succeeded.

### Example: contract verification

```calor
module ContractReview
  func Next (int:value) → int
    !
    requires value < 2147483647
    => result == value + 1
    return value + 1

  func Main () → int
    !
    return Next(41)
```

`Main()` returns `42`. The precondition excludes checked overflow at
`int.MaxValue`. Ask the agent to invoke verification and report its actual
status and assumptions. Do not turn a successful execution into a proof that
every caller satisfies the precondition.

```text illustrative
Verify Next in this file. Report the returned status, assumptions and any
unsupported expressions. Keep runtime precondition checks unless an eligible
proof from the relevant compilation authorizes their removal.
```

## Calor-first enforcement

The configured hooks check Claude Code's supported write/edit operations.
They direct new product code toward `.calr` files and run content/identity
checks; post-write lint provides additional feedback.

Generated C# and build artifacts have specific allowances. A hook is not an
operating-system sandbox and does not prove that every possible file-writing
mechanism is covered. Read any refusal and correct its cause instead of
changing the extension to evade it.

If you deliberately change this policy, review only the relevant Calor hook
entries. Do not delete the whole settings file: it can contain unrelated
project configuration. Reinitialization is a configuration change to review,
not a blanket repair for every client problem.

## Available skills

Slash skills such as `/calor` or `/calor-convert` are usable only if separately
installed and discovered by the client. `calor init --ai claude` does not install
them. The generated `CLAUDE.md` and the compiler's
[current-language catalog](/docs/syntax-reference/current-language/) supply the
native syntax reference without depending on those slash commands.

## How Claude learns Calor

The project instructions describe lowercase declaration headers, C# type names,
type-first parameters, infix expressions and two-space indentation. MCP
operations provide real compiler feedback. Hooks can reject specific writes
and report lint findings.

These are distinct mechanisms. Instructions are guidance; a hook checks an
operation; compilation checks a program. None makes an agent's prose a compiler
or verifier result.

## Why Calor works well with agents

### Visible structure

```calor
module LoopReview
  func Sum (int:count) → int
    !
    requires count >= 0 && count <= 100
    var int:total = 0
    for i from 1 to count step 1
      set total total + i
    return total

  func Main () → int
    !
    return Sum(5)
```

`Main()` returns `15`. The range includes its endpoint and snapshots its
bounds. The final `return` is outside the loop because it is dedented.
Do not silently replace this with a different loop's evaluation rules.

### Precise edit targeting

Identify a declaration by name and file, or obtain its persistent identity from
tooling. Declaration IDs belong in `.calor/ids.json`, not source headers.
Use identity-aware refactoring tools and inspect their actual edit result.

```text illustrative
In LoopReview.calr, change the loop inside Sum to start at 2.
Keep the inclusive endpoint and snapshot-bound semantics.
```

### Explicit effects

`!` declares a pure row; `! cw` admits console output. A pure function cannot
silently acquire that effect:

```calor expect=Calor0410
module UndeclaredConsoleEffect
  func Report (string:message) → void
    !
    Console.WriteLine(message)
```

The compiler rejects this program with `Calor0410`, an effect used but not
declared. Declare the real effect when the operation is intended; do not disable
enforcement to call the program native acceptance.

## Example prompts

### Generate a bounded function

```text illustrative
Write checked integer factorial for inputs 0 through 12, with explicit input
bounds and a positive-result postcondition. Compile it and report actual
verification results separately from execution results.
```

One native implementation is:

```calor
module BoundedFactorial
  func Factorial (int:n) → int
    !
    requires n >= 0 && n <= 12
    => result >= 1
    if n <= 1
      return 1
    return n * Factorial(n - 1)

  func Main () → int
    !
    return Factorial(5)
```

`Main()` returns `120`. The upper bound matters: `13!` does not fit in `int`.
The postcondition describes normal returns, not permission to ignore overflow.

### Refactor without changing behavior

```text illustrative
Extract the square calculation into a private function. Preserve checked
arithmetic, declaration identities and the public result.
```

```calor
module ExtractedCalculation
  func Square private (int:value) → int
    !
    return value * value

  func Main () → int
    !
    return Square(5)
```

`Main()` returns `25`. This is an executable example, not a transcript claiming
an agent already performed the refactoring.

## Best practices

Use the [current syntax reference](/docs/syntax-reference/), declare actual
effects and keep contracts before body statements. Use ordinary .NET nullable
types and exceptions for absence and failure. Let tooling maintain identities.

Read native diagnostics and generated C# failures separately. A preserved C#
frame can retain behavior without being native language coverage. Unknown
effects, unsupported verifier expressions and missing project references need
explicit handling, not success-shaped summaries.

## Workflow tips

Start with a bounded change and an observable result. Compile the exact source
you intend to keep, run relevant tests, and inspect verification statuses.
Do not infer a benchmark improvement from the syntax alone.

For existing C#, use the converter with the original project context when
needed. Keep generation receipts and check the reported losses and disposition;
writing output is not proof of successful compilation or tests.
