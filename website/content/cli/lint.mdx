The `lint` command reports source-format issues and lexer/parser diagnostics.
Its write mode uses the lossless formatter. It is not a substitute for
compilation, effect checking or contract verification.

## Usage

```bash
# Check files and report issues
calor lint <files...>

# Fix supported whitespace issues
calor lint <files...> --fix

# Check without modifying (exit code indicates issues)
calor lint <files...> --check

# Show detailed issue information
calor lint <files...> --verbose

# Combine options
calor lint src/*.calr --fix --verbose
```

## Options

| Option | Description |
|--------|-------------|
| `--fix`, `-f` | Fix supported issues through the validated formatter write path |
| `--check` | Check mode - exit with error if issues found (CI-friendly) |
| `--verbose` | Show detailed information about each issue |
| `--format` | `text`, schema 2.0 `json`, or `sarif`; no short alias |
| `--experimental` | Deprecated compatibility flag; validated fixes are enabled by default |

The writer preserves non-trivia tokens, comments, strings and declaration
names. It checks generated C# and idempotence before writing. If semantic
errors prevent those checks, it leaves the source unchanged and reports a
conservative fallback. Review the result; formatting is not a semantic repair.

## Exit Codes

| Code | Meaning |
|------|---------|
| `0` | No issues found (or all issues fixed with `--fix`) |
| `1` | Issues found and not fixed, or fixes conservatively suppressed |
| `2` | Parse error or invalid file |

## Design Principles

Calor uses meaningful indentation. Removing indentation, comments or names to
save characters can change semantics or discard useful context. Formatting
must preserve the program, not minimize its text at any cost.

### Traditional Linters vs Agent-Optimized Linters

| Aspect | Traditional Linters | Calor Linter |
|--------|---------------------|--------------|
| **Indentation** | Enforce style indentation | Preserve meaningful block indentation |
| **Whitespace** | Format for readability | Trim eligible trailing whitespace without changing tokens |
| **Identifiers** | Descriptive names encouraged | Source names remain names; persistent IDs live outside source |
| **Blank lines** | Separate logical sections | Preserve existing line structure |
| **Comments** | Encouraged for clarity | Preserve comments; contracts do not replace explanations |
| **Line length** | May impose a limit | No lint line-length rule |

### Why Agent-Optimized?

Consistent source can make reviews easier for people and agents. That is not
a measured model-accuracy or latency result. Character count is not token
count; see [token economics](/docs/benchmarking/metrics/token-economics/).

### Key Principle: Structure Through Indentation

Traditional code uses indentation to show structure:

```csharp
// Human-optimized (indentation shows structure)
public void Main() {
    for (int i = 0; i < 10; i++) {
        if (i % 2 == 0) {
            Console.WriteLine(i);
        }
    }
}
```

The equivalent native Calor program uses keywords and indented bodies:

```calor
module LintLoops
  func Main public () → void
    ! cw
    for i from 0 to 9 step 1
      if i % 2 == 0
        System.Console.WriteLine(i)
```

Both loops print `0`, `2`, `4`, `6`, and `8`, each on its own line. The native
range includes its upper bound, so `9` preserves the C# condition `i < 10`.
Declaration identities live in the sidecar, not block headers.

## Lint Rules

### Declaration Identity

There is no source-ID abbreviation rule. Declaration IDs belong in the
tooling-maintained `.calor/ids.json` sidecar, not in source headers.
Use [`ids check`](/docs/cli/ids/) to validate persisted identity state.
The formatter must not treat a program name such as `f001` as an ID to shorten:

```calor
module LintNames
  func f001 public (int:value) → int
    !
    // Keep this explanation.
    return value * 2
```

`f001(21)` returns `42`. Formatting preserves both its name and comment.

### Whitespace

Use two spaces per block level. Read-only lint reports trimmable trailing
whitespace plus lexer/parser diagnostics. It does not report every possible
formatting difference. Comments, strings and converter-preserved C# payloads
have protected whitespace; the writer does not trim them indiscriminately.

### Tag Formats

Declarations use native headers such as `func Main public () → void`.
The linter does not migrate retired declaration syntax or invent modifiers.

### Expression Format

Use infix expressions with C# precedence: `a + b * c`. Parentheses such as
`(a + b) * c` change grouping. Formatting preserves those expression tokens;
it does not convert expressions to prefix notation.

### Type Names

Use C# type spellings such as `int`, `string`, `int[]` and `string?`.
User-defined names such as `Customer` retain their case. Formatting does not
repair an unknown type by lowercasing it.

### Effect Codes

Use `! cw` for console output or `! cr, cw` for console input and output.
A standalone `!` declares purity. Compilation, not linting, checks whether
the body's effects fit that row.

## Examples

### Basic Usage

```bash
# Lint a single file
calor lint src/hello.calr

# Machine-readable findings for the same source
calor lint src/hello.calr --format json
```

### Auto-Fix

```bash
# Fix supported whitespace issues
calor lint src/hello.calr --fix

# A file that was changed is reported as:
# Fixed: hello.calr
```

### CI Integration

```bash
# In CI pipeline - fail if any issues
calor lint src/**/*.calr --check

# Exit code 1 if issues found, 0 if clean
```

### Verbose Output

```bash
calor lint src/hello.calr --verbose

# For a file with trailing spaces on line 5, the text includes:
# hello.calr: 1 issue(s)
#   Line 5: Line has trailing whitespace
```

### Agent Output

```bash
calor lint src/hello.calr --format json
```

There is no `--agent` option. JSON contains the shared diagnostic envelope,
including located lint warnings; human status messages go to stderr.

## Best Practices

1. **Run lint before commit** - Use pre-commit hooks to ensure all code is properly formatted
2. **Review write-mode changes** - Confirm that comments, names and behavior remain intact
3. **Use `--check` in CI** - Fail builds on lint issues to maintain consistency
4. **Format after code generation** - If generating Calor from other sources, always lint the output

## Integration with Format

The `lint` command checks for issues while `format` rewrites the entire file. Use them together:

```bash
# Check for issues first
calor lint src/module.calr

# If issues found, format to fix
calor format src/module.calr --write
```

Both commands use the same validated writer. Lint fixes files with reported
issues; format also handles supported indentation changes:

```bash
calor lint src/module.calr --fix
```
