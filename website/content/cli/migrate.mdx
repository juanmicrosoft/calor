Migrate an entire project between C# and Calor.

See [Converting C#: What Stays C# and Why](/docs/guides/csharp-interoperability/)
for native conversion, preserved C#, and how to interpret the report.

```bash
calor migrate <path> [options]
```

---

## Overview

The `migrate` command converts all applicable files in a project or directory. It:

- Scans for convertible files
- Creates a migration plan
- Converts files in parallel (optional)
- Generates detailed reports
- Handles errors gracefully without stopping

---

## Quick Start

```bash
# Preview migration (dry run)
calor migrate ./src --dry-run

# Migrate C# to Calor
calor migrate ./src

# Migrate with report
calor migrate ./src --report migration-report.md

# Migrate Calor back to C#
calor migrate ./src --direction calor-to-cs
```

---

## Options

| Option | Short | Default | Description |
|:-------|:------|:--------|:------------|
| `--dry-run` | `-n` | `false` | Preview changes without writing files |
| `--benchmark` | `-b` | `false` | Include before/after metrics comparison |
| `--direction` | `-d` | `cs-to-calor` | Migration direction |
| `--parallel` | `-p` | `true` | Run conversions in parallel |
| `--report` | `-r` | None | Save migration report to file (`.md` or `.json`) |
| `--verbose` | `-v` | `false` | Enable verbose output |
| `--skip-analyze` | — | `false` | Skip the migration analysis phase |
| `--skip-verify` | — | `false` | Skip the Z3 contract verification phase |
| `--verification-timeout` | — | `5000` | Z3 verification timeout per contract, in milliseconds |

## Migration Plan

Before converting, the command analyzes your codebase and creates a plan:

```bash
calor migrate ./src --dry-run
```

Output:
```text illustrative
=== Migration Plan ===

Direction: C# → Calor
Source: ./src

Files to Convert:
  ✓ 24 files fully convertible
  ⚠ 8 files partially convertible (will have warnings)
  ✗ 3 files skipped (unsupported constructs)
```

## Migration Reports

Generate detailed reports for documentation:

```bash
# Markdown report
calor migrate ./src --report migration-report.md

# JSON report
calor migrate ./src --report migration-report.json
```

Each file result in the JSON report carries `losses[]`, where every entry
names its `path` (`interop`, `rescue`, `passthrough`, `lossy`, or `dropped`)
and, for rescues, the `trigger` and `enabledBy` that applied. It also carries
`conversionPaths`, the same per-file summary `calor convert --format json`
writes (see [Which Path Preserved Each Member](/docs/cli/convert/#which-path-preserved-each-member)).
The console summary adds one line when any member was preserved:

```text
  Preservation paths: 1 by automatic rescue (parse-failure: 1; no passthrough request needed)
```

## What Gets Written

Since 0.30, `calor migrate` writes a `.calr` file for every C# file that parses.
This reverses the old all-or-nothing rule (#770, #932). Before, one failing file
or a failed project build meant no file was written.

Each file tries four rungs, in order:

1. Native Calor.
2. Native Calor with some members kept as C#.
3. Native Calor with some types kept as C#.
4. The whole file kept as C#, byte for byte (whole-file preservation).

A file drops one rung when conversion fails, crashes, or takes longer than 60
seconds, or when the generated Calor or C# fails a check. The report records the
reason for every drop. Quality is the native fraction: the share of files written
as native Calor. Writing is not the quality measure, because every file is written.

Three rules keep one problem from blocking the rest:

- **C# that parses but does not compile** is kept exactly and marked `unverified`.
- **The project build is a check, not a gate.** Migration compiles all generated
  C# with the project's references. Files whose own C# fails drop to rung 4. If
  errors remain even when every file is its original C#, native files are not
  blamed: every file is written and marked `unverified`.
- **A write error affects only its file.**

A file is not written in only six cases:

| Case | What you see |
|:-----|:-------------|
| The C# does not parse (syntax errors, or an active `#error`) | The file fails |
| A safety check on the destination: an output you edited, an output with no receipt (`.conversion.json`), or two inputs mapped to one output | The file fails; the message says what to delete or where to convert instead |
| A disk error while writing | The file fails |
| Whole-file preservation cannot reproduce the original exactly | The file fails; this is a converter bug |
| The file is outside the project folder (a NuGet `contentFiles` item, a linked file) | The file is skipped; nothing is written outside the project |
| `--dry-run` or Ctrl+C | Nothing is written |

Native fraction excludes preserved C#. It is reported apart from writing,
compiling, and running tests. The `--lossy` and branch-selection options were
removed in 0.30.

One known gap: the build names generated C# files `*.g.cs`, and the C# compiler
treats such files as generated code with nullable annotations off. A whole-file
preserved original that uses `?` annotations then reports CS8669 in a project with
`<Nullable>enable</Nullable>`. If the project also sets `TreatWarningsAsErrors`,
it does not build. Migration still writes those files and marks them `unverified`.

## Exit Codes

| Code | Meaning |
|:-----|:--------|
| `0` | No files failed; warnings alone do not fail the command |
| `1` | The path was missing, one or more files failed, or migration raised a handled error |
