Initialize Calor development environment with MSBuild integration and optional AI agent support.

```bash
calor init [options]
```

---

## Overview

The `init` command sets up your project for Calor development by:

1. **Adding MSBuild targets** - Integrates Calor compilation into your .NET build process
2. **Configuring AI agent integration** (optional) - Writes project instructions and client-specific MCP and hook configuration

After running `init`, you can write `.calr` files alongside your `.cs` files and they'll compile automatically during `dotnet build`.

The compiler and .NET SDK must be available. Initialization changes configuration;
it does not itself build the project or prove that its programs are correct.

---

## Quick Start

```bash
# Basic initialization (MSBuild integration only)
calor init

# Initialize with Claude Code support
calor init --ai claude

# Initialize with a specific .csproj
calor init --project MyApp.csproj
```

---

## Options

| Option | Short | Required | Description |
|:-------|:------|:---------|:------------|
| `--ai` | `-a` | No | Agent to configure; repeat for `claude`, `codex`, `gemini`, and/or `github` |
| `--project` | `-p` | No | Target .csproj file; without either project option, detection tries solutions before projects |
| `--solution` | `-s` | No | Initialize all projects in a `.sln` or `.slnx` solution |
| `--force` | `-f` | No | Replace managed configuration where supported; review changes and backups |

`--project` and `--solution` are mutually exclusive. Multiple detected solutions
require an explicit selection. Review the actual created/updated-file report;
initialization is not an atomic transaction across all files.

## AI Agent Support (Optional)

When you specify `--ai`, the command also sets up AI-specific configuration files.

### Claude (`--ai claude`)

Creates the following files:

| File | Purpose |
|:-----|:--------|
| `.claude/settings.json` | Supported write/edit checks and post-write lint hooks |
| `CLAUDE.md` | Project guidelines instructing Claude to prefer Calor for new code |
| `~/.claude.json` | Project-specific `calor` MCP server entry |

#### Calor-First Enforcement

The hooks check supported Write/Edit operations and lint changed Calor files.
Generated C# and build artifacts have specific allowances; Calor writes still
undergo content and identity checks.

A hook is not an operating-system sandbox. It does not cover every file-writing
mechanism or guarantee that the agent retries correctly. Read refusals and review
the resulting files.

Initialization does not install `/calor` or `/calor-convert` slash skills.
The generated instructions and MCP tools provide language guidance.

### Codex (`--ai codex`)

Creates the following files:

| File | Purpose |
|:-----|:--------|
| `.codex/config.toml` | MCP server configuration for Calor tools |
| `.codex/hooks.json` | Codex-native pre-write validation and post-write lint hooks |
| `AGENTS.md` | Project documentation with Calor-first guidelines |

#### MCP Server Integration

The `.codex/config.toml` file configures an MCP server that gives Codex direct
access to the consolidated MCP tools such as `calor_check`, `calor_verify`,
`calor_analyze`, and `calor_convert`:

```toml
# BEGIN CalorC MCP SECTION - DO NOT EDIT
[mcp_servers.calor]
command = "calor"
args = ["mcp", "--stdio"]
# END CalorC MCP SECTION
```

See [calor mcp](/docs/cli/mcp/) for the complete list of available tools.

#### Enforcement

Codex project lifecycle hooks cover supported `apply_patch`, Edit, and Write
operations and lint changed `.calr` files afterward. The user must review and
trust them with `/hooks`. Specialized file-change paths and shell commands can
bypass hooks, so run the generated smoke test and retain CI checks. Calor writes
current project guidance into `AGENTS.md`; it does not create project-local
Codex skills.

### Gemini (`--ai gemini`)

Creates the following files:

| File | Purpose |
|:-----|:--------|
| `.gemini/settings.json` | BeforeTool hooks and the `calor` MCP server configuration |
| `GEMINI.md` | Project guidelines instructing Gemini to prefer Calor for new code |

#### Calor-First Enforcement

The generated BeforeTool configuration checks supported file-writing operations.
The client must load and accept that configuration. These checks are not a
sandbox or a guarantee about every generated program.

Initialization does not install `@calor` or `@calor-convert` skills. Use the
generated instructions and the configured compiler tools.

### GitHub Copilot (`--ai github`)

Creates the following files:

| File | Purpose |
|:-----|:--------|
| `.github/copilot-instructions.md` | Project documentation with Calor-first guidelines |
| `.vscode/mcp.json` | MCP server configuration for Copilot Agent mode |

#### Guidance + MCP Tool Enforcement

This initializer does not install GitHub Copilot hooks. Its Calor-first setup is
**guidance-based with MCP tool support**; this is not a claim about every
Copilot client's capabilities.

MCP tools give Copilot programmatic access to the Calor compiler:
- `calor_compile`, `calor_verify`, `calor_analyze`, and `calor_convert`
- `calor_check` actions for diagnostics, type checking, lint, and snippet validation
- Enforcement is not automatic - review file extensions after generation
- Use `calor assess` to find any unconverted `.cs` files

Initialization does not create project-local Copilot skills. Starting or
approving the configured MCP server remains the client's responsibility.

## MSBuild Integration

The `init` command adds MSBuild targets to your `.csproj` file that:

- Compile `.calr` files before C# compilation
- Include generated `.g.cs` files in the build
- Clean generated files on `dotnet clean`

### Output Location

Generated C# files are placed in:

```
obj/<Configuration>/<TargetFramework>/calor/
```

This keeps generated files out of your source tree.

### Build Settings

The inline targets written by `init` invoke the compiler once per source file
with input and output paths. They are distinct from the `Calor.Sdk` build-task
integration.

| Property | Inline target behavior |
|:---------|:-----------------------|
| `CalorOutputDirectory` | Defaults to `$(BaseIntermediateOutputPath)$(Configuration)/$(TargetFramework)/calor/` |
| `CalorCompilerPath` | Compiler executable; defaults to `calor` when unset |
| `CalorCompilerOverride` | Supplies the compiler path when `CalorCompilerPath` is unset; the target checks that the override exists |
| `CalorToolVersion` | Version used to locate the packaged runtime |
| `CalorRuntimePath` | Runtime assembly reference path |
| `CalorSkipRuntimeReference` | Set to `true` when the injected runtime reference should be omitted |

Adding a property does not automatically forward it to a CLI invocation.
The injected targets do not pass effect, verifier, transpile-only or verbosity
properties, nor do they supply a complete evaluated-project reference context.
Inspect the actual targets before relying on such settings.

### CalorPermissiveEffects (New in 0.16)

`Calor.Sdk` supports this setting through its build task; the inline targets
generated by `init` do not forward it. The CLI equivalent is
[`--permissive-effects`](/docs/cli/compile/).

Permissive compilation is a migration policy, not proof that unknown calls are
pure. Do not count it as ordinary enforced native acceptance. See
[Effects](/docs/syntax-reference/effects/) for diagnostic meanings.

## Examples

### Basic Initialization

```bash
# Initialize Calor (MSBuild only)
calor init

# Analyze codebase for migration candidates
calor assess ./src --top 10
```

### With Claude Code

```bash
# Add Claude Code support
calor init --ai claude
```

### With GitHub Copilot

```bash
# Add GitHub Copilot support
calor init --ai github
```

### Initialize New Project

```bash
dotnet new console -o MyCalorApp
cd MyCalorApp
calor init
calor init --ai claude  # Optional
```

For example, save this native source as `Answer.calr`:

```calor
module InitializedExample
  func Answer () → int
    !
    return 42
```

`GlobalModule.Answer()` returns `42`. Run `dotnet build` and inspect its actual
result; the presence of injected targets alone is not a successful build.
