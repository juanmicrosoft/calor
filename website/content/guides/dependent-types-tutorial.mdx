Use ordinary .NET types, explicit input contracts and observable tests to define
API boundaries. This page replaces the retired dependent/refinement-type
tutorial. It does not claim that a precondition creates a nominal type, a
per-assignment invariant or a dependent type.

## Part 1 — API Parameter Validation

### The C# Problem

An ordinary `int` parameter does not express a port's allowed range. The
original C# example validates inputs explicitly:

```csharp
public void ConfigureServer(int port, string hostname, int maxConnections)
{
    if (port < 1 || port > 65535)
        throw new ArgumentOutOfRangeException(nameof(port));
    if (string.IsNullOrEmpty(hostname))
        throw new ArgumentException("Hostname required", nameof(hostname));
    if (maxConnections <= 0)
        throw new ArgumentOutOfRangeException(nameof(maxConnections));

    // ... actual logic buried after validation
}
```

### Calor With Explicit Preconditions

Write the requirements before the body:

```calor
module ServerContracts
  func ConfigureServer (int:port | (# >= 1 && # <= 65535), string:hostname | (# != null && #.Length > 0), int:maxConnections | (# > 0)) → int
    !
    => result == maxConnections
    return maxConnections

  func Main () → int
    !
    return ConfigureServer(443, "localhost", 10)
```

`Main()` returns `10`. The short-circuiting null check precedes the length
read. With runtime contracts enabled, invalid ports, null or empty hostnames,
and nonpositive connection limits fail at entry.

This is a contract example, not a server implementation or an exact conversion
of the C# function. Its ordinary parameter types remain `int` and `string`.

### Reusing Constraints

Another API can repeat the relevant parameter refinements. That does not introduce
named `Port`, `NonEmpty` or `Positive` types. If distinct domain types matter,
design ordinary classes or records with explicit construction and mutation
rules.

### What Happens in the Emitted C#

With runtime contract checks enabled, a failed parameter refinement throws
`ArgumentOutOfRangeException` naming the parameter. It does not reproduce the
original C# example's other `ArgumentException` subclasses or messages.

Turning runtime contracts off removes these checks. It does not make invalid
inputs valid. A refinement is rechecked when the body assigns that parameter,
but it does not constrain assignments to ordinary local variables.

## Part 2 — Financial Calculations with Input and Output Contracts

### The Setup

Require a nonnegative balance, a positive amount and sufficient funds.
Describe the successful result with a postcondition:

```calor
module BankingContracts
  func Transfer (int:balance | (# >= 0), int:amount | ((# > 0) && (balance >= #))) → int
    !
    => result >= 0
    return balance - amount

  func Main () → int
    !
    return Transfer(100, 30)
```

`Main()` returns `70`. With runtime contracts enabled, `Transfer(3, 5)` fails
the sufficient-funds precondition before subtraction.

### Requesting Verification

Pass the **complete unchanged source** to `calor_verify`. Inspect each contract's
returned status, assumptions, unsupported expressions and any counterexample.
Running `Main()` successfully is not a proof over all inputs.

The preconditions are assumptions when verifying the body. A proof about
`Transfer` under those assumptions does not establish that every caller meets
them. Keep runtime boundary checks unless an eligible proof from the relevant
compilation authorizes their removal.

### When the Requirement Is Missing

This variant deliberately omits sufficient funds:

```calor
module MissingFundsContract
  func Transfer (int:balance | (# >= 0), int:amount | (# > 0)) → int
    !
    => result >= 0
    return balance - amount

  func Main () → int
    !
    return Transfer(100, 30)
```

Its shown `Main()` still returns `70`. However, `Transfer(3, 5)` computes `-2`
and fails the **postcondition** with runtime checks enabled. With checks off,
the same call returns `-2`. A passing happy-path test did not expose the missing
entry requirement.

### The Fix Cycle

Add `int:amount | (# <= balance)` when insufficient funds should be rejected at
entry. Recompile the exact changed program and rerun both valid and invalid
calls. This is a behavioral contract change; do not silently replace a frozen
benchmark input or its expected behavior to obtain a better result.

No standalone proof statement or retired refinement authoring form is required
by these examples.

## Part 3 — The MCP-Guided Agent Repair Loop

### Starting Point

Integer division needs more than a nonzero divisor: checked
`int.MinValue / -1` overflows.

```calor
module DivisionContracts
  func Divide (int:a, int:b | ((# != 0) && (a != -2147483648 || # != -1))) → int
    !
    return a / b

  func Main () → int
    !
    return Divide(-7, 3)
```

`Main()` returns `-2`, truncating toward zero. With runtime contracts enabled,
`Divide(1, 0)` and `Divide(-2147483648, -1)` fail their entry requirements.
With checks off, the body throws `DivideByZeroException` and
`OverflowException`, respectively.

### Step 1: Inspect the Exact Program

Invoke `calor_check` with `action: "diagnose"` and the complete source. Keep
actual compiler diagnostics separate from an agent's suggestions.

### Step 2: Check Contracts and Behavior

Invoke `calor_verify` with the same source. Report the actual per-contract
statuses, not a fabricated success response. Compile and execute positive and
boundary cases separately; verifier success and runtime execution answer
different questions.

### Step 3: Review a Candidate Repair

Use parameter refinements when an input restriction matches the API's
intended behavior. Read suggested edits before applying them. A suggested patch,
an agent's confidence score or a successful tool transport is not proof that
the repair is correct.

### Step 4: Recheck the Saved Result

Compile the exact saved source, rerun relevant tests and request verification
again. Preserve declaration identities through tooling. Do not copy IDs into
source headers or disable effect enforcement to make an example pass.

### Why This Matters for Agent Workflows

Compiler tools provide concrete feedback, but the workflow still needs a
reviewed API contract and independent observations. Unsupported or timed-out
verification remains unresolved. Preserved C# behavior is not native language
acceptance.

This tutorial does not present an automatic refinement-repair transcript or
claim that a tool discharged the retired tutorial's obligations.
