Calor rejects possibly-null values at specified initialization, return and
method-input boundaries. This is not whole-program null safety.

**Version scope:** the receiving-boundary checks were introduced in Calor 0.22;
the examples below use current native syntax. Stage A established scalar string checks; Stage B added
the bounded shapes below. See [Stage A evidence (#1386)](https://github.com/juanmicrosoft/calor/issues/1386)
and [Stage B activation (#1402)](https://github.com/juanmicrosoft/calor/issues/1402).

## Types: native .NET nullability

Use `string` or `System.String` for a .NET string and `string?` or
`System.String?` for a nullable string reference. For a resolved reference type
such as `Widget`, `Widget?` permits null without wrapping the object.
Nullable value types use .NET syntax too, such as `int?`.

A nullable reference uses `null` and ordinary reference values. Use `value ??
fallback` to choose a default, or preserve the nullable annotation through the
API. Failure uses native exceptions (`throw`, `try`, `catch`), not a second
success/error representation.

## Supported receiving boundaries

“Active” below means an Error from the production compiler, not just a binder
finding. The checks compare supported source and destination shapes; they are
not general conversions between arbitrary types.

| Shape | Current status | Boundary covered |
|:------|:-----------------|:-----------------|
| Scalar STRING (`string`) | Active since Stage A | Initialization, native return, resolved method input |
| Arrays | Active in Stage B | `string[]?` is a nullable container; `string?[]` has possibly-null STRING elements. Neither satisfies `string[]` at these boundaries; jagged arrays retain separate container/element information |
| One-level string payloads | Active in Stage B | Matching definitions of `List`, `IList`, `IEnumerable`, `IReadOnlyList`, `ICollection`, `IReadOnlyCollection`; for example `List<string?>` cannot satisfy `List<string>` |
| Nominal reference types | Active in Stage B when identity is established | `Widget?` cannot satisfy `Widget` when both share a resolved underlying reference identity; this is not a name-based guess that every unknown type is a reference |
| Closed source-reference generic payloads | Active, with or without optional type checking | The six actual .NET collection definitions listed above retain element and container annotations. Nullable elements or containers cannot satisfy non-null receiving contracts. Invariant containers also reject nullable-writer aliases |
| Other generic payloads, nested generics, delegates, type parameters, unknown nominal identities | Outside the active guarantee | Unsupported boundaries, not non-null proof; no promise of Calor0272–0274 coverage |
| Mutable assignment/rebinding and constructor inputs | Excluded | Initializing a mutable local is checked; later writes and `new` arguments are not covered by this receiving-boundary guarantee |

Unsupported nullability shapes may still fail ordinary type checking. Absence
of one of these three diagnostics is not evidence that a value is non-null.
Array-element checks do not prove that every element created by an allocation
is initialized to a non-null value.
The source-reference generic rule is a deliberate stricter compatibility change,
not a repair for erased annotations. For example, `List<Widget?>` cannot satisfy
`List<Widget>`, and `List<Widget>?` requires a container guard before non-null
receiving. Guarding the container does not validate its elements.

An invariant `List<Widget>` also cannot become `List<Widget?>`: the new alias
would permit nullable writes that break the original element contract.
Covariant read-only targets can accept nullable elements. Matching invariant
contracts and nullable-container targets remain supported.

The older one-level string-generic policy is unchanged: **Generic payload checks
do not enforce the generic container's own nullability** for that bounded shape.
Its outer annotation is retained as information, unlike the source-reference
generic rule above. External-call
effect checks remain independent; a selected metadata method is not permission
to call an unknown library API.

## Diagnostics and complete examples

All examples below are complete files. The three marked **Rejected** examples
are intentionally invalid. Their corrected controls use an explicit default.

| Code | Severity | Receiving boundary | Highlighted source |
|:-----|:---------|:-------------------|:-------------------|
| `Calor0272` | Error | Initialization of a non-null binding | Initializer expression |
| `Calor0273` | Error | Return from a non-null native function/method | Returned expression |
| `Calor0274` | Error | Argument supplied to a non-null parameter | Offending argument expression |

### Calor0272: initialization

**Rejected:** `input` on line 4, column 27.

```calor expect=Calor0272
module InitRejected
  func Copy (string?:input) → void
    !
    let string:required = input
```

**Corrected:** choose a meaningful default for missing input.

```calor
module InitSafe
  func Copy (string?:input) → void
    !
    let string:required = input ?? "anonymous"
```

### Calor0273: return

**Rejected:** `input` on line 4, column 12.

```calor expect=Calor0273
module ReturnRejected
  func Name (string?:input) → string
    !
    return input
```

**Corrected:** return a non-null fallback.

```calor
module ReturnSafe
  func Name (string?:input) → string
    !
    return input ?? "anonymous"
```

### Calor0274: method input

**Rejected:** `input` on line 6, column 10.

```calor expect=Calor0274
module ArgumentRejected
  func Take (string:value) → void
    !
  func Send (string?:input) → void
    !
    Take(input)
```

**Corrected:** default before crossing the boundary.

```calor
module ArgumentSafe
  func Take (string:value) → void
    !
  func Send (string?:input) → void
    !
    Take(input ?? "anonymous")
```

Statement calls and expression calls use the same argument check. Discarding
the result does not waive it. Named arguments are matched to the named
parameter, not to their source position:

```calor
module NamedSafe
  func Choose (string:required, string?:optional) → string
    !
    return required
  func Send (string?:input) → string
    !
    return Choose(optional: input, required: "ready")
```

For an otherwise applicable native overload, a nullable argument now yields
`Calor0274` rather than being discarded as an overload candidate and producing
`Calor0208` (“no matching overload”). Genuine overload failures still use
`Calor0208`; an unrelated generic library type is not implicitly unwrapped into a string.
This diagnostic change applies to the supported boundaries in Calor 0.22.

## Defaults, throwing, and typed patterns

A default changes behavior when the input is missing. If absence is an error,
throw instead. Declare the allocation and throw effects:

```calor
module ThrowSafe
  func Require (string?:input) → string
    ! alloc,throw
    return input ?? throw new ArgumentNullException()
```

A typed pattern binds a new non-null value in its matching arm:

```calor
module PatternSafe
  func Name (string?:input) → string
    !
    return match input
      case string text → text
      case _ → "anonymous"
```

These are explicit consumption constructs, not whole-program flow analysis.
Writing `string?:input | (# != null)` states a precondition; it does not change a
`string?` parameter into `string` for receiving-boundary checks. Likewise, a
postcondition written with `=>` does not suppress these diagnostics. Use an
explicit consumption construct where a non-null value is required. See
[Contracts](/docs/syntax-reference/contracts/) for runtime modes and proof limits.

Calor 0.22 also transfers some local guard facts, but loops, mutation,
aliases, callbacks, and repeated member reads make arbitrary narrowing unsafe.
Do not assume that a prior null test proves every later use safe. See
[working migration controls (#1398)](https://github.com/juanmicrosoft/calor/issues/1398).

A built-in `== null` guard can establish non-null local or parameter facts when
its guarded branch actually returns or throws. A false `||` guard can establish
facts for each checked value. Overloaded or unresolved comparisons do not
provide this proof.
The Stage A limitation, "An early return after a null test does not currently
narrow a later method argument", no longer applies to these certified guards.

Scalar string property reads also qualify when the compiler certifies a
nonvirtual, getter-only auto-property with a readonly backing field in a complete
native declaring type. Facts follow the exact receiver storage, not a member's
name. Constructors, partial types, mutable properties, custom or virtual getters,
and uncertified member chains remain outside this support. These flow facts do not change
declaration metadata or grant permission for effects.

Calling a tracked callback that may write a guarded reference invalidates the
guard fact. This conservative invalidation is not assignment/rebinding
receiving-boundary enforcement. Merely declaring an unused lambda does not
execute its writes.

## Native code, BCL members, and metadata

Native Calor return annotations describe the result at a call site. Resolved
.NET methods, properties, and fields contribute their available metadata:

| Information | Meaning at a supported receiving boundary |
|:------------|:------------------------------------------|
| Known non-null | May satisfy a non-null destination |
| Declared nullable | Possibly null; consume or preserve that possibility |
| Truly missing annotation (`Oblivious`) | Conservatively possibly null, not an assertion of non-null |

For example, an environment variable may be absent. Preserve that possibility
or choose an application-specific default:

```calor
module EnvironmentSafe
  func Name () → string
    ! env
    let input = System.Environment.GetEnvironmentVariable("CALOR_NAME")
    return input ?? "anonymous"
```

An inferred local retains supported nullability information from its
initializer; omitting the explicit `string` type does not make a nullable result non-null.
Constructor expressions can establish a non-null result without checking
their inputs. That distinction matters when migrating object creation.

Metadata depends on the referenced assemblies and nullable context. Calor
trusts available annotations; it does not prove an external implementation
honors them. Conversion must distinguish enabled, disabled, and restored C#
nullable contexts, including inherited project settings. See
[conversion context (#1401)](https://github.com/juanmicrosoft/calor/issues/1401)
and [genuinely Oblivious metadata (#1400)](https://github.com/juanmicrosoft/calor/issues/1400).
Missing information is not an instruction to add `?` to every declaration.

Migration should follow the API's meaning: preserve a nullable result if
absence is legitimate, provide a meaningful default, reject absence explicitly,
or correct inaccurate upstream annotations. Changing a destination to `string?`
only moves the obligation to its consumers. A working manual default/throw
example does not establish behavior-preserving automatic conversion or
automatic guard insertion.
This is a manual migration, not an automatic converter rewrite.

## Modes and entry points

The active diagnostics are binding errors. They survive `--no-type-check`,
`CALOR_NO_TYPE_CHECK=1`, `--no-enforce-effects`, `--permissive-effects`,
`--no-strict-bind-inference`, and `--transpile-only`. These controls affect
different checks; they are not nullable-reference suppression switches.
Verification and contract-mode choices do not bypass these boundaries either.
There is no promised legacy-module warning downgrade.

The root compile command, `Program.Compile`, build paths using that pipeline,
and `calor verify` retain these active errors. Editor binding diagnostics use
the same active routing policy, but an editor diagnostic is not proof that
the generated C# or the complete project builds. Project references and other
entry-point settings still matter. See [entry-point evidence (#1396)](https://github.com/juanmicrosoft/calor/issues/1396).

## Reproducing the examples

Save one complete example as `example.calr`, then run:

```bash
calor --input example.calr --output example.g.cs
```

Each rejected example exits `1` with its listed Error and writes no new C#
output. Each safe control exits `0` and emits C#. Use a fresh output path:
a failed invocation is not evidence that an older output file was deleted.
`NullabilityDocumentationTests` reads these MDX examples and checks the
production `Program.Compile` result, severity, span, and generated output,
including type-off, effect-off, transpile-only, and verification modes. This dedicated
test complements the MDX example checks in `calor self-check docs`
([#1143](https://github.com/juanmicrosoft/calor/issues/1143)).

This is a bounded regression set, not a corpus measurement or universal proof.
Revision-specific command results belong with the source review evidence;
this page does not certify a release or report corpus counts.

## Verification is a separate guarantee

Receiving-boundary checks do not lift verifier proof demotions or remove runtime
guards. D3 tracks nullable references, D12 tracks string indexing/counting
semantics, and D14 tracks the reference model. [#875](https://github.com/juanmicrosoft/calor/issues/875)
remains open; completing nullability work does not close it. Read
[Verification Guarantees and Limits](/docs/guides/verification-guarantees/).
