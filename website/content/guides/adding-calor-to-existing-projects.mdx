You do not need to rewrite your application to try Calor. Start with your
existing C# project, convert one small part, and keep the rest in C#. Both can
remain in the same .NET application while you decide what to convert next.

---

## Your journey, one phase at a time

### Phase 1: Keep your working project

Run your existing build and tests before making changes. Save a version you
can return to. Add Calor's build support without replacing the application's
starting code or converting every file.

### Phase 2: Try one small file

Choose a file whose behavior is easy to test and understand. Convert it on a
separate branch, read the conversion report, and review the Calor code and its
rules. Some features may stay in C# or need more work; that is a reason to
pause and review, not to force a full conversion.

### Phase 3: Check the mixed application

Build and run the whole application with both languages in place. Run the same
tests you ran before, check the feature you changed, and review any warnings
or limits in Calor's checks. Conversion success alone does not establish that
the application's behavior is unchanged.

### Phase 4: Expand only when it is useful

Convert the next small file only after the first step works for your team.
Repeat the review and tests each time. You can leave parts in C# as long as
you need, stop after a single file, or return to your saved version. There is
no requirement to convert the project in one pass.

The steps below are the developer setup and commands for that journey. For
help evaluating the risks and checks, see the
[adoption guide](/docs/guides/adoption-playbook/).

## Overview

Adding Calor to an existing project is a gradual process:

1. **Enable Calor** - Add MSBuild integration
2. **Analyze the codebase** - Find useful pilot candidates
3. **Add a Calor file** - Confirm the mixed project builds
4. **Build and verify** - Exercise the normal project workflow
5. **Convert one C# file** - Validate and review the result
6. **Inspect project impact** - Query a converted method and its callers

You don't need to convert everything at once. Calor and C# can share a .NET
project, subject to the conversion and integration limits described below.

---

## Step 1: Enable Calor in Your Project

Enable Calor with MSBuild integration:

```bash
# Initialize Calor in your project
calor init

# Or specify a specific project file
calor init --project MyApp.csproj
```

Your `.csproj` is updated with MSBuild targets that compile `.calr` files automatically during `dotnet build`.

---

## Step 2: Analyze Your Codebase

Use `calor assess` to find C# files that would benefit most from Calor:

```bash
# Analyze your source directory
calor assess ./src

# Show top 10 candidates with detailed scores
calor assess ./src --top 10 --verbose
```

### Understanding the Output

```text illustrative
=== Calor Migration Analysis ===

Analyzed: 42 files
Average Score: 34.2/100

Top 10 Files for Migration:
--------------------------------------------------------------------------------
 82/100 [Critical]  src/Services/PaymentProcessor.cs
 78/100 [Critical]  src/Services/OrderService.cs
 65/100 [High]      src/Repositories/UserRepository.cs
```

| Priority | Score | Recommendation |
|:---------|:------|:---------------|
| **Critical** | 76-100 | Convert to Calor - high benefit |
| **High** | 51-75 | Good conversion candidate |
| **Medium** | 26-50 | Optional - some benefit |
| **Low** | 0-25 | Keep in C# - minimal benefit |

---

## Step 3: Add Your First Calor File

Create a new `.calr` file alongside your existing code:

```calor
§M{m001:Calculator}

  §F{f001:Add:pub}
    §I{i32:a}
    §I{i32:b}
    §O{i32}
    §R (+ a b)

```

---

## Step 4: Build and Verify

```bash
# Build your project - Calor compiles automatically
dotnet build
```

Your normal .NET build now includes the Calor files alongside the existing
code. Run your project's tests as well as building it before continuing.

---

## Step 5: Convert One C# File

Use the assessment as a starting point, not an instruction to convert your
most important code first. Choose one small, well-tested file that your team
can review, then try the conversion on your working branch:

```bash
# Convert, parse-check, and return the structured loss report
calor convert src/Services/PaymentProcessor.cs --validate --format json

```

Do not convert the whole source directory for your first trial. Finish the
review and tests for this file before deciding whether to convert another.
The [migration command reference](/docs/cli/migrate/) covers project-wide
options for developers who need them later.

### Review the Conversion Result

Conversion is not an all-or-nothing claim. The command above returns JSON;
without `--format json`, inspect the equivalent text loss report. Review:

- `losses[]` in JSON output or the text loss report,
- every `§CSHARP` block that preserves source the converter could not express
  natively,
- validation diagnostics,
- the Calor code, its rules, and your existing tests.

When a member cannot be converted safely, `calor convert` can preserve the
original C# inside `§CSHARP` rather than discarding the whole file. That is a
useful migration boundary, not completed conversion. `--no-fallback` asks the
command to fail instead.

To tell a fully native file from a partly preserved one, read
`data.conversionPaths.outcome` in the JSON output: `native`, `preserved`,
`lossy`, or `refused`. Each loss also names its `path`: `interop` (the
converter has no Calor form for the construct), `rescue` (its Calor failed to
parse or to compile back to C#, so the original C# of the type was kept), or
`passthrough` (kept only because you asked). `calor convert` rescues by
default. `calor migrate` and the MCP tools do not rescue a round-trip failure
by default, so the same file can be refused there; see
[Which mechanism kept the C#](/docs/guides/csharp-interoperability/#which-mechanism-kept-the-c).

### Common C# Features in a Pilot File

The 0.25 converter, not yet released, handles these as follows. The
[C# interoperability guide](/docs/guides/csharp-interoperability/) shows each
one with real converter output.

| C# feature | Native in 0.25 | Stays C# |
|:-----------|:---------------|:---------|
| `ref`, `out`, `in` arguments | `TryParse`/`TryGetValue` with a declared variable, `out _`, `out var` in a declaration, `return` or `if` condition; `ref`/`in` on locals, fields and array elements | `out var` in a call statement or loop header, ref locals and returns, generic `out T`; `[NotNullWhen]` is kept but does not narrow |
| Interpolated strings | `string`/`object` targets; `FormattableString`/`IFormattable` targets with holes (explicit cast) | Handler targets such as `StringBuilder.Append($"...")`; holes outside the native subset stay `§CS{...}` |
| Local functions | Non-capturing, non-generic, synchronous helpers declared in a method body | Capturing, generic, `async` and iterator local functions (the whole member) |
| Arrays in expressions | 1-D, jagged and rectangular arrays in returns, arguments and `?:` branches | Collection-initializer elements, multi-line elements in rectangular rows, assignments used as elements |
| Iterator properties and indexers | — | Always: the member stays `§CSHARP` |

In 0.24, more of these stayed C#, often the whole type, through the CLI's
automatic rescue. Converted output often also needs effect declarations (`§E{...}`)
before it compiles with default options; until then, compile it with
`--permissive-effects` (see below).

The converter is continuously exercised against MediatR, Serilog, and
FluentValidation. All 364 converted modules currently parse, but parse success
does not mean every member is native Calor or that every call binds. The loss
report and interop blocks remain the source of truth for each file.

### Use a Migration Waiver Deliberately

Converted code often calls APIs the compiler cannot resolve yet. Prefer the
project-file permissive setting over switching effect checking off:

```xml
<PropertyGroup>
  <CalorPermissiveEffects>true</CalorPermissiveEffects>
</PropertyGroup>
```

This suppresses the two “cannot tell” diagnostics (`Calor0411` and
`Calor0425`) and demotes `Calor0410` to a warning. It never waives a known
callback mismatch (`Calor0424`) or an override/interface violation
(`Calor0420`, `Calor0421`). Because unknown calls are assumed harmless, this
waives the full effect guarantee. Record the setting in the pull request, and
pass `--permissive-effects` to `calor review-packet` so the waiver prints on
the packet's first line.

## Step 6: Build and Inspect Project Impact

After the converted file builds, create or refresh the project index:

```bash
dotnet build
calor index build .
calor query effects ProcessPayment --in-file src/Services/PaymentProcessor.calr
calor query callers ProcessPayment --in-file src/Services/PaymentProcessor.calr
calor query impact ProcessPayment --in-file src/Services/PaymentProcessor.calr
```

Replace `ProcessPayment` with a converted method. Effect queries apply to
functions, methods, constructors, and accessors, not to the containing class.
Read any `PARTIAL` residual before relying on a caller count. For an
agent-driven workflow, use the equivalent `calor_query` MCP tool and compile
with `options.crossModule: true` so effects are checked across files.

See
[Project Intelligence for Agents](/docs/guides/project-intelligence-for-agents/)
for the complete pre-edit and post-edit loop.

## Optional: Enable Claude Code Integration

For AI-assisted Calor development:

```bash
calor init --ai claude
```

This adds:
- `/calor` and `/calor-convert` skills
- `CLAUDE.md` with guidelines instructing Claude to write new code in Calor and analyze C# files before modifying them

### Using Claude Code

**Write new Calor code:**
```
/calor

Write a function that validates email addresses with:
- Precondition: input is not null or empty
- Postcondition: returns true only for valid emails
```

**Convert existing C# to Calor:**
```
/calor-convert src/Services/PaymentProcessor.cs
```

## Best Practices

### What to Convert First

1. **Small, well-tested files** with a clear owner and rollback path
2. **Contract-dense code** where preconditions and postconditions add value
3. **Pure or first-order effect-checked code** with few dynamic boundaries
4. **High-scoring files** from `calor assess`, after the first three checks

### What to Keep in C#

- Simple DTOs and record types
- Auto-generated code (EF migrations, gRPC stubs)
- Code using features Calor doesn't support yet
- Reflection-heavy, dynamic, or delegate-heavy service layers for the first
  pilot
