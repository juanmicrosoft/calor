IL analysis can propagate manifest-covered effects through concrete methods in
referenced .NET assemblies. It can reduce the number of intermediate methods
that need manual manifest entries. It is not a proof of arbitrary external code:
missing bodies, dynamic dispatch and leaf assumptions still matter.

---

## The Problem

Effect manifests cover .NET framework types (`DbCommand`, `HttpClient`, `ILogger`), but they don't cover **your** code. If you have a data access layer:

```csharp
// Fragment from MyApp.DataAccess.dll; CreateConnection is supplied by the project.
public static class UserRepository
{
    public static void Save(string name)
    {
        using var conn = CreateConnection();
        conn.Open();
        using var cmd = conn.CreateCommand();
        cmd.CommandText = "INSERT INTO Users ...";
        cmd.ExecuteNonQuery(); // This is the actual db:w
    }
}
```

The corresponding Calor caller has this shape. This is a fragment requiring the
referenced project and its dependencies, not a standalone native acceptance case:

```calor-fragment
func CreateUser public (string:name) → void
  ! db:w
  UserRepository.Save(name)
```

Without IL analysis, the compiler doesn't know that `UserRepository.Save` has `db:w` — it would flag it as an Unknown external call (Calor0411). You'd need to write a custom manifest for every intermediate method.

With the required implementations available, analysis can trace the call chain
to `DbCommand.ExecuteNonQuery` and propagate its `db:w` manifest seed. This
does not establish that the call binds or that the project builds; those are
separate checks against the project's actual references.

## Enabling IL Analysis

Add one property to your project file:

```xml
<PropertyGroup>
  <CalorEnableILAnalysis>true</CalorEnableILAnalysis>
</PropertyGroup>
```

The build task initializes an analyzer from the referenced assemblies and reuses
it across Calor inputs. Missing or unusable requested implementation assemblies
fail initialization rather than silently disabling analysis.

## What It Finds

IL analysis traces through **concrete call chains** — method A calls method B which calls method C which calls a manifest-covered method. It handles:

| Pattern | How it works |
|---------|-------------|
| **Direct calls** | `Repo.Save()` → `DbCommand.ExecuteNonQuery()` → `db:w` |
| **Transitive chains** | `Service.Process()` → `Repo.Save()` → `DbCommand.ExecuteNonQuery()` → `db:w` |
| **Async methods** | Traces through compiler-generated state machines (`MoveNext()`) |
| **Iterator methods** | Traces through `yield`-based state machines |
| **Delegate creation** | `Task.Run(() => repo.Save())` traces through the lambda via `ldftn` |
| **Virtual dispatch** | Unions effects from concrete implementations (up to 5) |
| **Deep chains** | Follows up to 50 hops (configurable) |
| **Mutual recursion** | Fixpoint iteration converges correctly |

### Example: What the compiler sees

An illustrative propagation tree, not output measured from a supplied project:

```text illustrative
UserService.CreateUser()     → db:rw, db:w   (propagated)
  UserRepository.Save()      → db:rw, db:w   (propagated)
    DbConnection.Open()      → db:rw         (from manifest)
    DbCommand.ExecuteNonQuery() → db:w       (from manifest)
  UserRepository.FindById()  → db:r, db:rw   (propagated)
    DbCommand.ExecuteReader() → db:r          (from manifest)
MathHelper.Add()             → pure           (no effects found)
```

## What It Doesn't Find

IL analysis has known limitations. These patterns still require manifests:

| Pattern | Why | Solution |
|---------|-----|---------|
| **Interface-heavy calls** (`ILogger.Log`, `IConfiguration.GetSection`) | Runtime implementations may be unavailable or exceed the dispatch cap | Use applicable reviewed manifests and inspect unresolved results |
| **Delegate invocations** (`Func<T>.Invoke`) | Runtime-determined target, not visible in IL | Mark as Unknown or cover with manifests |
| **Reflection** (`MethodInfo.Invoke`, `dynamic`) | Not visible as direct calls in IL | Cover with manifests |
| **P/Invoke / native calls** | No managed IL body to inspect; a leaf assumption is not verified behavior | Cover with reviewed manifests |

The key insight: IL analysis works well for **your** code (repositories, services, handlers) where the call chain is concrete. For .NET framework types (ILogger, IConfiguration), the built-in manifests already cover them. The two approaches complement each other.

## How It Works

The resolution pipeline, in order:

```
1. Specific method in manifest
2. Method name in manifest
3. Wildcard in manifest
4. Type default effects in manifest
5. Namespace defaults in manifest
6. IL analysis
7. Unknown (Calor0411)
```

Manifests take precedence. IL analysis supplies results for calls not already
covered by a manifest. A trace marked incomplete, for example after a depth or
dispatch limit, cannot supply a resolved effect row.

### Soundness guarantee

IL analysis uses three-state resolution:

- **Resolved** — propagation produced effects under the analyzer's model
- **Pure** — propagation found no effects under that model
- **Incomplete** — analysis cut short (depth limit, missing body, too many implementations)

Incomplete traces are not reported as pure. They fall through to unresolved
effect handling.

There is a separate limitation: a missing method or a declaration with no IL
body can become an **assumed empty leaf** during propagation. Detailed results
record those assumptions, but the ordinary IL resolver's effect status does
not itself establish that the chain is assumption-free. An empty row is
therefore not an unconditional safety proof.

`calor import` applies a stricter publication rule: a chain with such leaf
assumptions remains unresolved and is excluded from the generated manifest.
Supply the missing dependencies or a reviewed contract, then inspect the report.
Do not treat build-time IL resolution and assumption-free import derivation as
the same guarantee.

## Performance

The analyzer caches results and is reused across `.calr` inputs in a build.
Cost depends on the loaded implementations, reachable call graph, dispatch
fan-out and configured budgets. Measure clean and incremental builds on your
project; this page does not establish a universal millisecond overhead.

IL analysis is disabled by default.

## Interaction with Incremental Builds

When IL analysis is enabled, the build state includes the analysis options and
referenced implementation inputs, not just the Boolean flag. A changed
dependency must invalidate the result that depended on it. Check the build
receipt after changing package versions or implementation paths; an old cached
effect result is not evidence about the new binary.

## Diagnostics

| Code | Severity | Meaning |
|------|----------|---------|
| Calor0414 | Info (verbose only) | Effect resolved via IL analysis — tells you which assembly the effect was traced through |
| Calor0415 | Info | IL analysis could not resolve a method — explains why (depth limit, missing body, etc.) |
| Calor0416 | Warning | IL analysis budget exhausted — too many methods visited, remaining treated as Unknown |

## When to Enable It

**Enable if:**
- Your project references custom DLLs (data access layers, service libraries) that call effectful .NET methods
- You're getting many Calor0411 (Unknown external call) warnings for methods in your own assemblies
- You want to reduce the number of custom manifest entries you need to write

**Don't bother if:**
- All your external calls are to .NET framework types already covered by manifests
- Your project is small enough that a few custom manifest entries are easy to maintain
- Your measured analysis cost exceeds the budget for the pilot

## Relationship to Manifests

IL analysis **reduces** the number of manifests you need to write — it doesn't replace them. Think of it as:

- **Manifests**: curated, precise, reviewed. Best for framework types and ecosystem libraries.
- **IL analysis**: automatic, best-effort. Best for your own code and concrete call chains.

The two work together. Manifests provide the "seeds" (e.g., `DbCommand.ExecuteNonQuery → db:w`), and IL analysis propagates those seeds backward through your code's call graph.
