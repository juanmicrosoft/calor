**An agent-friendly language needs a spec that is tighter than "it emits C#."**

Emitting C# can hide a lot of semantic gaps. When an agent writes Calor code, it needs to know *exactly* what that code will do—not what the C# compiler happens to do today, or what one version of the .NET runtime does differently than another.

If the semantics are not crisp, you get "works on this compiler version" behavior, and that kills trust.

---

## The Problem with "It Compiles to X"

Consider a language that "compiles to JavaScript" or "emits C#". What does this code do?

```
result = f(a(), b()) + g(c())
```

The answer depends on:
- **Evaluation order**: Is `a()` called before `b()`? Before `c()`? The backend language may not specify this.
- **Side effects**: If `a()` modifies state that `b()` reads, the result depends on call order.
- **Overflow behavior**: Does `INT_MAX + 1` wrap, trap, or produce undefined behavior?
- **Null semantics**: What happens when you dereference `null`?

C# does specify left-to-right argument evaluation and many other relevant
behaviors. Calor must state where it relies on those guarantees and where its
emitter adds different behavior, such as checked native arithmetic.

A successful translation alone does not establish that every language rule or
interop boundary was checked.

---

## Calor's Solution: Crisp, Backend-Independent Semantics

The specification describes intended rules; the production C# emitter must
implement them. The CNF prototype is not a mandatory enforcement stage, and
there is no current native source-version declaration. Those missing mechanisms
must not be inferred from this section's design goals.

### What We Specify

| Concern | Calor's Decision | Why It Matters |
|:--------|:----------------|:---------------|
| **Evaluation Order** | Strictly left-to-right | Agents can reason about side-effect ordering |
| **Short-Circuit** | `&&`/`||` always short-circuit | Predictable control flow |
| **Scoping** | Lexical lookup, subject to declaration-space restrictions | Nested reads do not imply unrestricted local shadowing |
| **Integer Overflow** | TRAP by default | Safety-first; silent bugs are unacceptable |
| **Type Conversions** | Explicit for narrowing | Prevents accidental data loss |
| **Nullability** | .NET nullable types and `null` | Models absence; supported receiving boundaries are checked, not whole-program null safety |
| **Exceptions** | Typed, with semantic meaning | `ContractViolationException` carries context |

### Why This Matters for Agents

1. **Trainable Rules**: Agents can be trained on precise semantics, not approximations.
2. **Testable Behavior**: Exercise actual emitted code, including failure boundaries.
3. **Version Stability**: Pin the installed compiler and test upgrades.
4. **Reviewable Limits**: Distinguish intended rules from admitted, measured behavior.

## The Three Pillars

### 1. Precise Definitions

The core reference describes:

- **Evaluation order**: [Core Semantics](/docs/semantics/core/) Section 2
- **Scoping and shadowing**: [Core Semantics](/docs/semantics/core/) Section 3
- **Lifetimes**: Defined by scope boundaries
- **Numeric behavior**: [Core Semantics](/docs/semantics/core/) Section 4

### 2. Precise Mapping to .NET

The [backend specification](/docs/semantics/dotnet-backend/) defines exactly how Calor semantics map to .NET:

- When direct emission is safe (C# matches Calor)
- When additional code is required (checked arithmetic, temporaries)
- Type mappings (native Calor uses C# spellings such as `int`)
- Exception types and their contents

### 3. Stable Versioning

The [versioning reference](/docs/semantics/versioning/) distinguishes:

- **Compatibility policy**: MAJOR.MINOR.PATCH and a retained comparison API
- **Current native source**: Uses the installed compiler, with no source-version gate
- **Historical declarations**: Not syntax to copy into current modules
- **Upgrade checks**: Pin the compiler and rerun affected programs

## How It Works: The CNF Pipeline

The production pipeline binds and analyzes the AST, then emits C#:

```
Source -> Lexer/Parser -> AST -> Binder/Checks/Analysis -> C# Emitter -> C#
```

The separate **Calor Normal Form (CNF)** prototype explores explicit
temporaries, types, labels, and branches. It does not receive every native
program and is not consumed by the production C# emitter.

See [Normal Form](/docs/semantics/normal-form/) for its implemented subset and
limitations, including rejected complex callees and unsupported-node placeholders.

## Test-Backed Semantics

The following are historical semantics-test obligations. Several retained
fixtures still use retired source syntax; their names are not evidence of
current native acceptance. The core and normal-form references also have
separate ordinarily enforced native programs with CLR execution controls.

| Semantic | Test | What It Verifies |
|:---------|:-----|:-----------------|
| S1 | `FunctionArguments_EvaluatedLeftToRight` | Arguments evaluated in order |
| S2 | `BinaryOperators_EvaluatedLeftToRight` | Operators evaluated in order |
| S3 | `LogicalAnd_ShortCircuits` | `&&` doesn't evaluate right if left is false |
| S4 | `LogicalOr_ShortCircuits` | `||` doesn't evaluate right if left is true |
| S5 | `LexicalScoping_InnerReadsOuter` | Inner scope accesses outer variables |
| S6 | `ReturnFromNestedScope` | Return unwinds to function boundary |
| S7 | `IntegerOverflow_Traps` | Overflow throws `OverflowException` |
| S8 | `NumericConversion_IntToFloat` | Implicit widening works |
| S10 | `RequiresFails_ThrowsContractViolation` | Contracts throw with function ID |
| S11 | `SemanticsVersionMismatch_EmitsDiagnostic` | Historical declaration checking; no current native source-version gate |

## For Agent Developers

If you're building agents that generate Calor code:

1. **Train on the spec, not the output**: Use the Core Semantics as the source of truth
2. **Version your prompts**: Pin the installed compiler; do not generate a retired semantics-version tag
3. **Test against semantics tests**: Your generated code should pass the same tests
4. **Don't assume C# behavior**: If it's not in the Calor spec, don't rely on it
