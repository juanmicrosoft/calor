Version: 2.0.0

The installed compiler implements semantics version 2.0.0. Current native
source has **no semantics-version declaration syntax**. Pin the compiler
package version and test upgrades; do not copy the retired section-tag
declaration into native source.

The compatibility policy and historical checks below do not establish a
native source-version gate. That channel remains unimplemented.

---

## Why Versioning Matters for Agents

> **Agents will be trained and prompted against specific rules.**

When an agent generates Calor code, it relies on specific semantic behaviors:
- "Overflow traps" (not wraps)
- "Left-to-right evaluation" (not unspecified)
- "`&&` short-circuits" (not eager)

If these rules change between versions without clear versioning:
1. Agents trained on v1 rules will generate incorrect code on v2 compilers
2. Prompts that describe v1 behavior will mislead agents on v2
3. Code that "worked before" will silently break

A version pin identifies the compiler being used. It does not ensure that an
agent followed its rules or that an upgrade preserves every program's behavior.

---

## Version Format

Calor semantics versions follow [Semantic Versioning 2.0.0](https://semver.org/):

```
MAJOR.MINOR.PATCH
```

- **MAJOR**: Breaking semantic changes (review code and agent instructions)
- **MINOR**: Backward-compatible semantic additions (old code still works)
- **PATCH**: Clarifications, bug fixes in semantics (no behavior change)

### Diagnostic routing correction (2026-09-11)

`Error` severity in the binder is not the same as production CLI rejection.
**Historical routing through Calor 0.21:** at checked main revision `080ed5a7`,
`Program.Compile` used `BindingDiagnosticPolicy`, which excluded
`Calor0272` (binding initialization),
`Calor0273` (return), and `Calor0274` (argument). The language server's
`DocumentState` bound directly, so editor diagnostics could differ. Other
compiler passes may independently reject the same program.

This historical behavior was not a newly introduced regression. The routing policy and its
`Program.Compile` call were introduced in
[`cc62c4ac`](https://github.com/juanmicrosoft/calor/commit/cc62c4ac7b6059de4cb7a31809c298269c6dafe7),
an ancestor of all three release commits below. Each tagged source has the
same exclusion and calls the policy from `Program.Compile`.

| v0.14.0 | `0e327664` | [Policy](https://github.com/juanmicrosoft/calor/blob/0e32766496beebf6ef43e62d211efd8bf34586e6/src/Calor.Compiler/Binding/Scope.cs#L53-L99) / [Compile](https://github.com/juanmicrosoft/calor/blob/0e32766496beebf6ef43e62d211efd8bf34586e6/src/Calor.Compiler/Program.cs#L792-L796) |

These are scoped source-history findings, not a claim that every possibly-null
program compiles or that every published binary has been independently tested.
[Calor 0.22's bounded checks (#1082)](https://github.com/juanmicrosoft/calor/issues/1082)
now activate production Errors at specified initialization, native-return,
and resolved method-input boundaries. They cover scalar strings, supported
arrays, one-level whitelisted string generic payloads, and identity-proven
nominal references. The historical exclusion above is not the current routing
policy for those shapes. See the
[nullability guide](/docs/guides/nullability-and-dotnet-interop/) for complete
examples and mode behavior.

General mutation, member writes, constructor inputs, and outer generic-container
enforcement remain excluded; array annotations do not prove every slot initialized.
These checks do not establish whole-program non-nullness. The D3/D12/D14 safeguards
that demote conditional proofs and retain their runtime guards remain in place.
[#875](https://github.com/juanmicrosoft/calor/issues/875) remains open.

## Version Declaration

Native modules currently use the installed compiler's semantics. There is no
native declaration that requests another version or checks compatibility with
a source-specified version. This complete program uses the current rules;
`Next(41)` returns `42`:

```calor
module InstalledSemantics
  func Next public (int:value) → int
    !
    return value + 1
```

### Syntax

Do not add a section tag, an invented module-header version field, or a
version comment expecting it to select semantics. The retained compatibility
helper accepts exact three-part versions for its declaration checks, but
that API is not a native source declaration.

### Modules That Declare Nothing

Ordinary native modules do not need a version declaration. The write hook
recommends pinning the compiler instead of adding retired syntax.
`calor hook validate-calr-content` reports current lexer/parser errors in the
supplied content without blocking the write. It is not a type, effect, runtime,
or source-version compatibility check; compilation remains a separate step.

## Compatibility Rules

### Patch Version Changes (x.y.Z)

The versioning policy reserves patch changes for compatible corrections:
- Documentation clarifications
- Specification bug fixes
- Test additions

The compatibility helper classifies 2.0.0 and 2.0.1 as compatible. Run regression
tests when upgrading the compiler; that classification is not a behavioral proof.

### Minor Version Changes (x.Y.z)

The policy reserves minor changes for backward-compatible additions:
- New constructs added
- New operators added
- New optional behaviors
- Extended standard library

The helper classifies an older minor within the same major as compatible.
This does not prove that an arbitrary source program compiles or behaves identically.

### Major Version Changes (X.y.z)

**Incompatible by definition.** Changes may include:
- Evaluation order changes
- Operator precedence changes
- Type system changes (the 2.0.0 bump changed binder nullability severity,
  not production CLI routing; see the correction above)
- Default behavior changes
- Removed constructs

The compatibility helper classifies 1.x and 2.x as incompatible. Native source
currently has no declaration through which to request that comparison.

## Compiler Behavior

The retained `SemanticsVersion` compatibility API requires matching major
versions. Its declaration-reporting helper can produce the diagnostics below.
These are API and historical section-tag behaviors, **not an admitted native
source-version gate**. Retired syntax is rejected before it can establish
native compatibility.

There is no dual-semantics or legacy `Info` compilation mode. Nullability
severity and production routing are distinct; see the current bounded checks
and historical correction above, and
[#1084](https://github.com/juanmicrosoft/calor/issues/1084).

### Diagnostic Codes

| Code | Severity | Condition |
|:-----|:---------|:----------|
| Calor0700 | Warning | Same major, declared minor newer than the compiler's (might work) |
| Calor0701 | Error | Declared major differs from the compiler's — older or newer |
| Calor0702 | Error | Historical declaration is malformed or duplicated |

### Compatibility Matrix (2.0.0 compiler)

| Version supplied to the compatibility/declaration helpers | Result |
|:----------------|:-------|
| 2.0.0, 2.0.5 | Compatible |
| 2.1.0 | Possibly incompatible; declaration helper reports Calor0700 |
| 1.0.0, 1.9.9, 0.9.0 | Error (Calor0701) with migration pointer to #1084 |
| 3.0.0 | Error (Calor0701), "upgrade the compiler" |
| `^1.0.0`, `2`, `2.0` | Declaration helper reports Calor0702 |

## Version History

### Version 2.0.0 (Current)

The v0.14 bump changed binder diagnostic severity. The v0.14.0 promise of
legacy `Info` severity was a future plan, not a shipped mode. The severity
helper's lower-major branch does not make older modules compatible.
The historical declaration parser and fail-closed refusal arrived in
[#1087](https://github.com/juanmicrosoft/calor/commit/4ac335d5932383bcf6590b34fdc2ad73ff96afbb):
that commit is not an ancestor of v0.14.0-v0.14.2, but is an ancestor of
[v0.15.0 (`3bb2601e`)](https://github.com/juanmicrosoft/calor/tree/3bb2601e3ff83597ddf2f27dcc334b6399ab97ea).
That historical parser refused modules declaring `1.x` or `0.x` with
`Calor0701`, rather than compiling in an `Info` mode. Native source does not
currently expose an equivalent declaration. This correction adds neither a
native channel nor an automated semantics migration tool.

### Version 1.0.0

Initial formal semantics specification including:

**Evaluation Order**
- Left-to-right function argument evaluation
- Left-to-right binary operator evaluation
- Short-circuit `&&` and `||`

**Scoping**
- Lexical scoping with parent chain lookup
- Inner scope shadows outer
- Return from nested scope

**Numeric Semantics**
- Integer overflow traps by default
- INT to FLOAT implicit
- FLOAT to INT explicit

**Contracts**
- REQUIRES evaluated before body
- ENSURES evaluated after body with `result` binding
- ContractViolationException with FunctionId

## When to Bump Versions

### Bump MAJOR When

- Changing evaluation order of existing constructs
- Changing default overflow behavior
- Removing constructs
- Changing type coercion rules
- Changing contract semantics

### Bump MINOR When

- Adding new syntax constructs
- Adding new operators
- Adding new built-in types
- Extending pattern matching
- Adding optional compiler flags

### Bump PATCH When

- Fixing ambiguities in specification
- Adding test cases
- Improving documentation
- Fixing compiler bugs that didn't match spec

## Migration Guidance

### Upgrading Modules

When upgrading a module to a new semantics version:

1. **Review changelog** for breaking changes
2. **Run tests** with new compiler version
3. **Pin the compiler version** used by the build and agent tooling
4. **Test edge cases** related to changed semantics

For historical 1.x source, manually review current semantics, convert retired
syntax, and test null-handling choices. A version pin or successful compile
alone does not establish null safety. Use the current
[nullability guide](/docs/guides/nullability-and-dotnet-interop/) for the actual
receiving boundaries and diagnostics; do not infer them from the helper's
version comparison alone.

### Mixed-Version Projects

There is no dual-semantics mode. Native modules in one compilation use the
same installed compiler. A source comment or retired declaration cannot
select an older implementation for an individual module.
