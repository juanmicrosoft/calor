Semantics Version: 2.0.0

Calor Normal Form (CNF) is a retained intermediate-representation prototype.
`CnfLowering` can lower a subset of the AST to explicit temporaries and branches.
**The production compiler does not route C# generation through CNF.**
The native programs below run on the production C# path; the IR diagrams are
explanations, not a claim that the prototype handles every program.

---

## The Problem: Backend-Dependent Semantics

When compiling directly to a backend language (like C#), semantic decisions can become implicit:

```
result = f(a(), b()) + c()
```

Direct compilation to C# might produce:

```csharp
var result = f(a(), b()) + c();
```

C# specifies left-to-right operand and argument evaluation. Direct emission
can rely on that rule. A different backend would need its own conforming
implementation; Calor does not currently supply the IL or LLVM backends
described in the original CNF design.

CNF explores making selected evaluation decisions explicit in an IR. Its
existence alone does not establish backend-independent conformance.

---

## Purpose

The prototype's design goals are to:

1. **Make evaluation order explicit** - Temporaries enforce left-to-right evaluation
2. **Introduce explicit temporaries** - All intermediate values have names
3. **Linearize control flow** - Branch/label/goto instead of structured control
4. **Remove implicit conversions** - All conversions are explicit nodes

These are not guarantees of the current production pipeline. The lowerer still
skips some unsupported statements and substitutes placeholders for some
unsupported expressions. It must not be used as an authority for accepting
arbitrary native source.

---

## Pipeline Position

```
Production: Source -> Lexer/Parser -> AST -> Binder/Checks/Analysis -> C# Emitter -> C#
Prototype:  AST -> CnfLowering -> CNF -> CnfValidator / CnfPrettyPrinter
```

The prototype is exercised separately. It is not a hidden backend stage or a
replacement for ordinary binding, type checking, effects, and runtime tests.

---

## CNF Node Types

### Expressions (Atomic)

The lowerer stores operation results in temporaries. Operands to its binary,
unary, and call nodes are intended to be literals or variable references; the
operation nodes themselves are not atomic.

| Node | Description |
|:-----|:------------|
| `CnfLiteral` | Constant value (42, 3.14, true, "hello") |
| `CnfVariableRef` | Reference to a named variable |
| `CnfBinaryOp` | Binary operation on two atomic operands |
| `CnfUnaryOp` | Unary operation on one atomic operand |
| `CnfCall` | Function call with atomic arguments |
| `CnfConversion` | Explicit type conversion |

### Statements

| Node | Description |
|:-----|:------------|
| `CnfAssign` | Assign value to variable |
| `CnfSequence` | Ordered list of statements |
| `CnfBranch` | Conditional jump to label |
| `CnfLabel` | Target for jumps |
| `CnfGoto` | Unconditional jump |
| `CnfReturn` | Return from function |
| `CnfThrow` | Throw exception |
| `CnfTry` | Try/catch/finally block |

## Lowering Examples

### Binary Operations

**Source:**
```calor
module NormalBinary
  func Value (int:a, int:b, int:c) → int
    !
    return a * b + c
```

`Value(2, 3, 4)` returns `10`.

**CNF:**
```
t1 = CnfBinaryOp(Multiply, a, b)
t2 = CnfBinaryOp(Add, t1, c)
return t2
```

The evaluation order is now explicit: `a * b` is computed first, stored in `t1`, then `t1 + c` is computed.

### Short-Circuit AND

**Source:**
```calor
module NormalAnd
  func Both (bool:left, bool:right) → bool
    !
    return left && right
```

**CNF:**
```
t_result = false
branch left -> then_block, end_block
then_block:
  t_result = right
  goto end_block
end_block:
return t_result
```

The branch represents short-circuit control flow. If `left` is false, the
right operand is not evaluated. `Both(false, true)` returns `false`.

### Short-Circuit OR

**Source:**
```calor
module NormalOr
  func Either (bool:left, bool:right) → bool
    !
    return left || right
```

**CNF:**
```
t_result = true
branch left -> end_block, else_block
else_block:
  t_result = right
  goto end_block
end_block:
return t_result
```

If `left` is true, the right operand is not evaluated.
`Either(true, false)` returns `true`.

### Function Call

**Source:**
```calor
module NormalCalls
  func Mark (int:value) → int
    ! cw
    System.Console.Write(value)
    return value

  func Combine (int:a, int:b, int:c) → int
    !
    return a * 100 + b * 10 + c

  func Main () → int
    ! cw
    return Combine(Mark(1), Mark(2), Mark(3))
```

`Main()` writes `123` once and returns `123` on the production path.

**CNF argument-temporary pattern:**
```
t1 = call a()
t2 = call b()
t3 = call c()
t4 = call f(t1, t2, t3)
return t4
```

Arguments are evaluated left-to-right, stored in temporaries, then the function is called.

The prototype can lower this program's simple named calls. More complex
callee forms represented by `ExpressionCallNode` are explicitly rejected with
`NotSupportedException`. Testing this program's CNF shape is separate from
testing its production execution; it does not prove complete call, type, or
effect support in the prototype.

## Design Principles

### Explicit Over Implicit

The design represents operations as nodes. The prototype does not yet cover
every native operation or make every implicit conversion explicit.

### Flat Structure

No deeply nested expressions. Every intermediate value has a name.

### Backend Agnostic

An IR could be shared by multiple backends. Only the C# production emitter
exists here, and it does not consume this IR.

### Verifiable

`CnfValidator` checks selected structural invariants, not full language
semantics or execution equivalence.

## CNF Validation

For an already constructed `CnfFunction` named `func`, the API is:

```csharp
var validator = new CnfValidator();
validator.ValidateFunction(func);

if (!validator.IsValid)
{
    foreach (var error in validator.Errors)
    {
        Console.WriteLine(error);
    }
}
```

### Validation Rules

1. **Atomic operands**: Binary, unary, and call operands must be literals or variable references.
2. **Recorded definitions**: Variable references must name a parameter or an assignment encountered by the visitor.
3. **Label targets**: Recorded branch and goto targets must exist.

The visitor is not a path-sensitive definite-assignment checker. It does not
establish type consistency, all-path return coverage, correct effects, or
faithful lowering of unsupported nodes. Use a fresh validator per function;
its current error collection persists between validations.
