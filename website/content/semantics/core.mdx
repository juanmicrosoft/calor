This page describes the intended evaluation rules and current native C# path.
Complete programs below are checked through ordinary compilation and generated
C# execution. The retained CNF prototype and historical semantics tests are
separate evidence; neither establishes conformance for every source form.

## 1. Design Principles

### 1.1 Why "Emits C#" Is Not Enough

**Problem:** An agent-friendly language needs a spec that is tighter than "it emits C#."

Emitting C# can hide semantic gaps:

| What You Write | What You Need to Know |
|:---------------|:---------------------|
| `f(a(), b())` | Is `a()` guaranteed to be called before `b()`? |
| `x + y` | What happens if the result overflows? |
| `inner.x = 1` | Does this shadow or mutate the outer `x`? |
| `return` in `if` | Does this return from the function or just the block? |

C# specifies argument order and many other relevant behaviors. Calor can rely
on those guarantees where they match its rules, and must generate additional
code where they do not.

### 1.2 Backend Independence

> **Key Principle:** The semantics of Calor are defined independently of any backend. The C# emitter must conform to Calor semantics, not define them.

The backend must:
- Enforce evaluation order through code generation
- Never rely on unspecified backend behavior
- Generate explicit temporaries when needed to preserve semantics

### 1.3 Safety First

Calor prioritizes safety and predictability:
- Overflow traps by default (no silent wraparound bugs)
- Explicit type conversions for narrowing (no accidental data loss)
- Contracts are first-class semantic constructs (not just comments)
- Effects are tracked and enforced (side effects are visible)

## 2. Evaluation Order

### 2.1 Left-to-Right Evaluation

Operands and call arguments evaluate left-to-right in source order. Conditional
and short-circuit expressions evaluate only the selected branch.

#### Function Arguments

```
f(a(), b(), c())
```

**Semantics:** Evaluate `a()`, then `b()`, then `c()`, then call `f`.

**Rationale:** Predictable side-effect ordering enables reasoning about code behavior.

**Test:** `S1: FunctionArguments_EvaluatedLeftToRight`

#### Binary Operators

```
a() + b() + c()
```

**Semantics:** Evaluate `a()`, then `b()`, compute `a() + b()`, then evaluate `c()`, compute result.

**Test:** `S2: BinaryOperators_EvaluatedLeftToRight`

### 2.2 Short-Circuit Evaluation

Logical operators `&&` and `||` use short-circuit evaluation.

#### Logical AND (`&&`)

```
left && right
```

**Semantics:**
1. Evaluate `left`
2. If `left` is `false`, result is `false` (do NOT evaluate `right`)
3. If `left` is `true`, evaluate `right` and return its value

**Test:** `S3: LogicalAnd_ShortCircuits`

#### Logical OR (`||`)

```
left || right
```

**Semantics:**
1. Evaluate `left`
2. If `left` is `true`, result is `true` (do NOT evaluate `right`)
3. If `left` is `false`, evaluate `right` and return its value

**Test:** `S4: LogicalOr_ShortCircuits`

### 2.3 Conditional Expressions

```
condition ? whenTrue : whenFalse
```

**Semantics:**
1. Evaluate `condition`
2. If `true`, evaluate and return `whenTrue` (do NOT evaluate `whenFalse`)
3. If `false`, evaluate and return `whenFalse` (do NOT evaluate `whenTrue`)

## 3. Scoping Rules

### 3.1 Lexical Scoping

Calor uses **lexical scoping** with parent chain lookup.

```calor
module CoreScopes
  func Read (bool:enter) → int
    !
    let int:outer = 1
    if enter
      let int:inner = outer + 1
      return inner
    return outer
```

`Read(true)` returns `2`; `Read(false)` returns `1`. The inner scope can read
`outer`, but `inner` is not visible after that scope.

### 3.2 Shadowing

Name lookup selects the nearest visible declaration. This is not permission
to reuse every spelling: duplicate declarations and C# local declaration-space
rules can still reject a program. Use distinct names for nested locals; the
complete example above tests outer reads, not unrestricted local shadowing.

**Key Semantics:**
- A declaration is visible only in its applicable scope
- Reading an outer binding does not mutate it
- Leaving an inner scope does not change the outer binding

**Test:** `S5: LexicalScoping_InnerReadsOuter`

### 3.3 Scope Resolution Order

1. Look up in current scope
2. If not found, look up in parent scope
3. Continue until found or root scope reached
4. If not found in any scope, emit `Calor0200: UndefinedReference`

### 3.4 Return from Nested Scope

Return statements in nested scopes must correctly unwind to the function boundary.

```calor
module CoreNestedReturn
  func Read (bool:early) → int
    !
    if early
      return 42
    return 7
```

`Read(true)` returns `42`, not `7`.

**Test:** `S6: ReturnFromNestedScope`

## 4. Numeric Semantics

### 4.1 Integer Overflow

**Default Behavior:** TRAP (throw `OverflowException`)

```calor
module CoreOverflow
  func Increment (int:value) → int
    !
    return value + 1
```

`Increment(41)` returns `42`; `Increment(int.MaxValue)` throws
`OverflowException`, including with contract mode `off`.

The CLI has no `--overflow` option. Native arithmetic uses the module's default
checked policy. Migration can preserve an imported C# unchecked policy; that
does not make it the native default. See
[integer overflow policy](/docs/guides/verification-guarantees/#integer-overflow-policy).

**Test:** `S7: IntegerOverflow_Traps`

### 4.2 Type Coercion

| Conversion | Behavior | Rationale |
|:-----------|:---------|:----------|
| `int` to `double` | Implicit widening | Every 32-bit integer is representable |
| `double` to `int` | Explicit cast required | Fractional part is discarded; checked range rules apply |
| Narrowing | Explicit required | Data may be lost |

```calor
module CoreConversions
  func Value () → int
    !
    let int:whole = 42
    let double:widened = whole
    let int:narrowed = (int)3.75
    return (int)widened + narrowed
```

`Value()` returns `45`. Widening is not universally exact: for example, large
`long` values can lose precision when converted to `double`.

**Test:** `S8: NumericConversion_IntToFloat`

### 4.3 Division

- Integer division: Truncates toward zero
- Division by zero: Throws `DivideByZeroException`
- Float division by zero: Returns `Infinity` or `NaN` per IEEE 754

## 5. Contracts

Contracts are semantic constructs that specify behavioral requirements.

### 5.1 Preconditions (REQUIRES)

```calor
module CoreRequires
  func Positive (int:x | (# > 0)) → int
    !
    return x
```

A precondition is an inline refinement on a parameter. `#` stands for the
parameter's value. A condition over several parameters goes on the last
parameter it mentions, as in `(int:lo, int:hi | (# > lo))`.

**Semantics in every contract mode, including `off`:**
1. Evaluated **before** the function body runs, in parameter order
2. Can read the constrained parameter (`#`) and all other parameters
3. If the condition is `false`, throws `System.ArgumentOutOfRangeException`.
   Its `ParamName` is the parameter name, and its message is
   `Violation of inline refinement for parameter '<name>'`.
4. A failed precondition never throws `ContractViolationException`.
   `--contract-mode off` does not remove the check.

`Positive(1)` returns `1`. `Positive(0)` and `Positive(-1)` throw
`ArgumentOutOfRangeException` in `debug`, `release`, and `off` modes.

**Test:** `S10` in `tests/Calor.Semantics.Tests/ContractTests.cs`

### 5.2 Postconditions (ENSURES)

```calor
module CoreEnsures
  func Positive (int:x) → int
    !
    => result > 0
    return x
```

**Semantics with runtime checks enabled:**
1. Evaluated **after** function body, **before** return
2. Has access to parameters and special `result` binding
3. If condition is `false`, throws `ContractViolationException`

### 5.3 Contract Evaluation Order

1. All parameter-refinement preconditions (in parameter order)
2. Function body
3. All ENSURES clauses (in declaration order)

Precondition guards are emitted in every contract mode. `debug` and `release`
both emit supported postcondition checks; `release` uses leaner exceptions.
`off` removes postcondition and invariant guards only. Explicit `proof`
statements retain their separate runtime checks unless eligible obligation verification discharges them. Optional
verification may remove only eligible clean proven postcondition guards;
it never removes preconditions based on satisfiability. Unsupported runtime
lowering fails compilation instead of silently omitting requested checks.
See [verification guarantees](/docs/guides/verification-guarantees/).

## 6. Nullable Values and Exceptions

The absence model is .NET nullability. `string?` permits a null reference;
`int?` is a nullable value type. Use `??` to supply a fallback.

```calor
module CoreNullableValues
  func Fallback (string?:value) → string
    !
    return value ?? "none"

  func Fail () → void
    ! alloc,throw
    throw new System.InvalidOperationException("missing")
```

`Fallback(null)` returns `"none"`; `Fallback("abc")` returns `"abc"`.
`Fail()` allocates and throws the declared exception rather than returning a
special error wrapper.

Failure uses .NET exceptions: `throw` raises one, `try` / `catch` handle it,
and `finally` runs cleanup. A bare `throw` in a catch rethrows. Explicit throw
operations require the corresponding effect row. A pure row does not promise
that checked arithmetic, indexing, or every other operation cannot throw.

Third-party generic types use ordinary library APIs, with no special language
encoding or implicit conversion.

## 7. Effects System

Effects track side-effect capabilities of functions.

### 7.1 Effect Categories

| Effect | Symbol | Description |
|:-------|:-------|:------------|
| Console Read | `cr` | Reads from console |
| Console Write | `cw` | Writes to console |
| File Read | `fs:r` | Reads from files |
| File Write | `fs:w` | Writes to files |
| Network Read | `net:r` | Network input |
| Network Write | `net:w` | Network output |

### 7.2 Effect Enforcement

Functions may only:
1. Perform effects they declare
2. Call functions whose effects are subsets of their own

That rule depends on selected-call coverage and effect contracts for external
APIs; it is not whole-program proof of arbitrary library behavior. Unknown
calls are rejected under ordinary enforcement rather than assumed pure.
Review [effect coverage and manifests](/docs/guides/effect-manifests-dotnet-ecosystem/).
