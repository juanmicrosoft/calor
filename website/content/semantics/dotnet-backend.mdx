Semantics Version: 2.0.0

This page describes the production C# emitter and its intended conformance
rules. Current native examples use C# type spellings. CNF is a separate partial
prototype, not a production emitter input.

## Compilation-context imports

CLI compilation and conversion, Calor projects, MCP compilation, and editor
diagnostics import **`System` only** by default. This is a compilation setting,
not a change to preserved source. It does not import Tasks, LINQ or IO. Original
and generated C# use the same selected context; raw C# remains non-native.

Use `--no-implicit-system` on compilation-backed CLI commands, or
`CalorImplicitSystemUsing=false` in a project. Calor SDK/init projects supply a
real MSBuild `Using` item for downstream C# compilation. A genuine standalone
project must also disable the SDK's independent `ImplicitUsings` and any explicit
global System import. A `.g.cs` compiled elsewhere needs the same project context.

Low-level compilation/conversion/validation APIs remain standalone by default;
set `IncludeImplicitSystemUsing=true` to select this context. The separate
`IncludeImplicitGlobalUsings` switch still enables the full SDK compatibility
profile. The original conversion scorecard remains standalone.

LSP initialization accepts `implicitSystem` (default `true`), `projectPath`,
`configuration` and `targetFramework`. Select a restored project explicitly for
its references, global aliases, nullable settings and conditional symbols.
Otherwise the editor uses platform references. Published generated-C# diagnostics
and rename preflight use the same selected context. MCP compile places the switch
in `options.implicitSystem`; other compilation-backed tools use `implicitSystem`.

C# binding reports ambiguous short names as `CS0104`. Use aliases or fully
qualified names such as `global::System.Action`. Imports do not prove unknown
calls pure or relax effect safety. Case081 and its exact preserved output both
fail standalone with `CS0103`; both compile with the System-project context.
That is a context change, not a standalone score improvement.

## Why This Document Exists

> **"It emits C#" is not a semantics specification.**

The .NET backend generates C# code, but C# is not the source of truth for Calor semantics. This document specifies:

1. **Where C# behavior matches Calor** - Direct emission is safe
2. **Where C# behavior differs or is unspecified** - Additional code is required
3. **How to verify conformance** - Test cases and validation checklists

Without this specification, subtle differences between C# and Calor could cause:
- "Works on my machine" bugs
- Version-specific behavior changes
- Agent-generated code that fails on different .NET versions

---

## Core Principle

> **The emitter must not rely on unspecified behavior in C#.**

When C# evaluation order matches Calor semantics, direct emission is acceptable. When C# behavior is unspecified or differs, the emitter must generate code that enforces Calor semantics.

### What "Unspecified" Means

C# specifies many behaviors, but not all. For example:
- Argument evaluation order **is** specified (left-to-right)
- `checked` overflow behavior **is** specified
- Some optimization behaviors **are not** specified

The emitter must never assume unspecified behavior matches Calor semantics.

## Evaluation Order

### Function Arguments

C# specifies left-to-right argument evaluation (C# spec 12.6.2.2), which matches Calor.

**Direct emission is safe:**
```csharp
// Calor: f(a(), b(), c())
f(a(), b(), c());  // C# guarantees left-to-right
```

### Binary Operators

C# evaluates binary operator operands left-to-right (C# spec 12.4.1), matching Calor.

**Direct emission is safe:**
```csharp
// Calor: a() + b()
a() + b();  // C# guarantees left-to-right
```

### From CNF

The following shows how a backend could preserve explicit CNF temporaries.
It is a design illustration: the current C# emitter visits the AST, not CNF.

**CNF:**
```
t1 = a()
t2 = b()
t3 = t1 + t2
```

**C#:**
```csharp
var t1 = a();
var t2 = b();
var t3 = t1 + t2;
```

---

## Short-Circuit Operators

### Logical AND and OR

C# `&&` and `||` short-circuit identically to Calor.

**Direct emission is safe:**
```csharp
// Calor: A && B
A && B;  // C# short-circuits

// Calor: A || B
A || B;  // C# short-circuits
```

## Numeric Semantics

### Integer Overflow

**Calor Default:** TRAP (throw OverflowException)

**C# Implementation:**
```csharp
// Use checked arithmetic
checked
{
    var result = a + b;  // Throws OverflowException on overflow
}
```

**C# project setting, not a Calor CLI option:**
```xml
<PropertyGroup>
  <CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>
</PropertyGroup>
```

The emitter uses checked expressions and statements for the native module's
default policy; consumers do not need this project setting to make those
emitted operations checked. Migration can retain imported unchecked semantics.
See [overflow policy](/docs/guides/verification-guarantees/#integer-overflow-policy).

### Type Mapping

| Calor Type | C# Type | Notes |
|:-----------|:--------|:------|
| `int` | `int` | 32-bit signed |
| `long` | `long` | 64-bit signed |
| `short` | `short` | 16-bit signed |
| `sbyte` | `sbyte` | 8-bit signed |
| `uint` | `uint` | 32-bit unsigned |
| `ulong` | `ulong` | 64-bit unsigned |
| `double` | `double` | 64-bit IEEE 754 |
| `float` | `float` | 32-bit IEEE 754 |
| `bool` | `bool` | Boolean |
| `string` | `string` | Reference type; use `string?` for nullable inputs |

Historical internal type aliases do not change the current native spelling.

### Conversions

**Implicit Widening:**
```csharp
// Native int to double (implicit)
int i = 42;
double f = i;  // C# allows implicit widening
```

**Explicit Narrowing:**
```csharp
// Native double to int (explicit required)
double f = 3.14;
int i = checked((int)f);
```

## Contracts

### Preconditions

A precondition is an inline refinement on the parameter it constrains:
`func MyFunction (int:x | (# > 0)) → int`. The emitter turns it into an entry
guard. The guard throws `System.ArgumentOutOfRangeException`, and the
exception's `ParamName` is the parameter name. The guard is emitted in every
contract mode, including `off`.

**C# output** (what the emitter produces for that signature, with `#line`
directives removed; the file starts with `using System;`):
```csharp
public static int MyFunction(int x)
{
    if (!(x > 0)) throw new ArgumentOutOfRangeException(nameof(x), "Violation of inline refinement for parameter 'x'");
    return checked(x * 2);
}
```

### Postconditions

**Schematic C# implementation** (the ID and spans are placeholders):
```csharp
public static int MyFunction(int x)
{
    // Body
    var __result = checked(x * 2);

    // ENSURES: result > x
    if (!(__result > x))
    {
        throw new Calor.Runtime.ContractViolationException(
            "Postcondition failed", "f001", Calor.Runtime.ContractKind.Ensures,
            startOffset: 0, length: 0,
            condition: "__result > x");
    }

    return __result;
}
```

### Contract Mode

| Mode | Behavior |
|:-----|:---------|
| `debug` | Precondition guards, plus postcondition and invariant checks with detailed `ContractViolationException` messages |
| `release` | The same guards and checks; postcondition and invariant failures carry leaner messages |
| `off` | Precondition guards only; no postcondition or invariant checks |

A precondition is a parameter refinement, so `off` does not remove it.

With optional verification, only eligible clean proven postcondition guards
may be removed; use `--keep-proven-guards` to retain them. Unsupported runtime
lowering fails rather than silently dropping a requested guard.
Explicit `proof` statements retain their separate runtime guards unless
eligible obligation verification discharges them, including in `off` mode.

## Generated Code Markers

The emitter includes markers in generated code:

```csharp
// <auto-generated>
// This code was generated by the Calor compiler.
// Do not modify this file directly.
// </auto-generated>
```

This marker does not select or attest a semantics version. Native source
currently has no source-version declaration; pin the compiler package.

## Validation Checklist

These are review obligations, not a claim that every possible source program
or preserved C# block is enforced:

- [ ] Left-to-right evaluation preserved
- [ ] Short-circuit semantics correct
- [ ] Integer overflow traps (default)
- [ ] Type conversions explicit where required
- [ ] Contracts generate correct exception type
- [ ] Contract exception includes function ID
- [ ] Native nullable types and exception handling
- [ ] Pattern matching behavior matches the admitted native forms; do not infer general exhaustiveness proof
