# v0.13 freeze registrations (F-1 … F-4)

**Date:** 2026-08-10
**Status:** Registered — frozen at the merge commit of this document
**Owning plan:** `roadmap-v0.13-v0.15.md` (§2.1, §2.5). That plan requires every release gate to
name its instrument, denominator, and freeze point, and requires these four registrations to land
**before** the work they gate merges. The freeze event for each registration below is **the commit
that lands this document on main** (squash merges produce no merge commit; the linear-history
ordering is what carries the control — checkable from git history, per the A-1.5 lesson: an
ordering control cannot be defeated by arithmetic).

**Amendment rules (apply to all four):**
- **Additive amendments** (new corpus files, new edit scripts, residual→registered promotions) are
  allowed by PR at any time — additions can only make the gates harder.
- **Subtractive or weakening amendments** (removing corpus files, registered→residual demotions,
  loosening generator bounds) require an explicit supersession entry in this file stating what was
  weakened and why, and may not merge in the same PR as work that benefits from the weakening.
- **The completeness check is bidirectional.** The 61-name list below is frozen by name, not by
  "whatever subclasses `ExpressionNode` at check time": a class that is re-parented out of the
  hierarchy, deleted, or reclassified as a helper/value object (#762 item 8) without a supersession
  entry here is a red CI failure — the item-8 maneuver applied to **any** listed class (not just
  the two Tier B candidates) is a subtractive amendment. Otherwise a code-only PR could shrink the
  frozen denominator without ever touching this file.

Instrument: a CI job that compiles both legs and greps the bound trees for `<unsupported:` — with a
**discriminating pin**: a fixture containing a known Tier A construct temporarily reverted to the
fallback path must turn the job red (revert-the-fix test, per `pins-must-discriminate`).

  instrument that could not be built — the fallback was silent). The denominator is unchanged

  `Binder_FallbackExpression_ReturnsOpaqueExpression` (asserts the 0259 emission directly).

### 2. Re-registration — the corpus as it exists

**Location:** `tests/TestData/EditScripts/` (unchanged). **Harness:**
`tests/Calor.Compiler.Tests/EditScriptIdentityTests.cs`. **Corpus rules:**
`tests/TestData/EditScripts/README.md`.

**Schema.** Each script is a directory `ES-NN-<name>/` containing:

- `script.json` with exactly these fields (every field is read by `LoadScript`, and a missing one
  fails the test): `id` (string, `"ES-NN"`); `title` (string); `pins` (string — the failure the
  script would catch; the README makes stating it mandatory); `expectsReuse` (bool — the
  incrementality-witness expectation, §"Witness" below); `reuseNote` (string — why reuse is or is
  not expected); `steps` (array of `{ "dir": "<step directory name>", "options": "<profile>" }`).
- `options` is one of three profiles, resolved by the harness to `CompilationOptions`:
  `effects-on` → `EnforceEffects = true`; `effects-off` → `EnforceEffects = false`;
  `docs-required` → `EnforceEffects = true, RequireDocs = true`. Any other value fails the test.
- One `step-NN-<label>/` directory per step, holding the **complete** `.calr` file set at that
  point (a snapshot, not a patch). A file absent from step N+1 is a deletion; a new file is an
  addition; changed bytes are an edit. The harness syncs the workspace to each snapshot in turn
  (`SyncWorkspace`: copy in, delete what is absent along with its `.g.cs`).

**Instrument, as it exists.** One in-process path only — `CompilationDriver.CompileAll` with
`crossModuleEnforcement: true`, `crossModulePolicy: UnknownCallPolicy.Strict`, and
`DriverCacheSettings` whose options token is the step's `options` string. Per script:

- `IncrementalDiagnosticsAreIdenticalToFullRebuild` — every step compiled from scratch in its own
  workspace (`clearFirst: true`) vs. one workspace and one cache carried across all steps
  (`clearFirst: false`); asserts equal canonicalised diagnostics (workspace-relative path | code |
  severity | line | column | message, ordinally sorted) and equal `AnyErrors` at every step.
- `IndexContentsAreIdenticalToAFullRebuild` (added by #934) — same fresh-vs-sequential pairing
  over `ProjectIndexBuilder.Build`, comparing a canonical serialisation (declarations, call edges,
  occurrences, residuals) with the machine-dependent header stripped. v1 rebuilds the index
  wholesale, so this leg pins canonical form, not incremental reuse; the test says so.
- `ScriptStatesDifferFromEachOther` — consecutive steps must differ in files or options (ES-06
  exempt), so no step is padding.
- `RegisteredScriptIdsAreStable` (`EditScriptIdentityTests.cs:217-231`) — hard-lists the seven
  directory names and compares them to the ordinally-sorted directory enumeration. A directory
  added or removed without editing the list fails the test.

**Witness (incrementality, as implemented).** `CacheReuseMatchesTheScriptsRegisteredExpectation`
sums `result.Skipped.Count` over the warm sequence and asserts **two-sided** against
`expectsReuse`: `true` ⇒ at least one file was served from cache (otherwise the identity result is
"a full build against a full build" and the test says so); `false` ⇒ zero files were served
(global invalidation is a registered, tested claim — if it narrows, the script names itself).
`EveryStepRewritingIdenticalContentRecompilesNothing` states the strong form on ES-06 alone: after
a cold build, every warm step must have `CompiledCount == 0` and `SkippedCount` equal to the cold
`CompiledCount`. This is the mechanism roadmap §2.5 gate 2 calls the incrementality witness; it is
per-script and reads the driver's skip count, nothing finer.

**Members** — `pins` quoted verbatim from each `script.json`:

| Script | Edit (steps, profile) | `expectsReuse` | Invariant pinned (`pins`) |
|---|---|---|---|
| ES-01-local-edit | `alpha.calr`/`beta.calr`; baseline → edit body of one file → introduce a violation in it (`effects-on` throughout) | `true` | "The baseline shape. An edit confined to one file must not change any other file's diagnostics, and the untouched neighbour must be served from cache (the witness) rather than silently rebuilt." |
| ES-02-add-file | baseline → add clean `gamma.calr` → add violating `delta.calr` (`effects-on`) | `false` | "A new file must be compiled and its diagnostics must appear, while the pre-existing files stay cached. Adding a clean file first, then a violating one, separates 'new file compiles' from 'new file's diagnostics reach the report'." |
| ES-03-delete-file | baseline with `noisy.calr` → delete the violating file → delete a clean file (`effects-on`) | `false` | "A deleted file's diagnostics must disappear. The failure this pins is a stale cache entry keeping a removed file's findings alive, which a full build would never report." |
| ES-04-cross-module-effect | `caller.calr` never edited; `callee.calr` clean → gains an effect → loses it (`effects-on`) | `true` | "The hard case for any per-file cache: the file whose diagnostics change is not the file that was edited. Cross-module effect enforcement (Calor0410) runs over cached effect summaries, so a stale summary would let the caller's violation vanish on a warm build. Step 2 reverses the edit, pinning the direction a cache is most likely to get wrong (appearing findings are noticed; disappearing ones are not)." |
| ES-05-options-flip | files identical at every step; profile `effects-on` → `effects-off` → `effects-on` | `false` | "The #788 / #883 shape. Every diagnostics-affecting option must be in the options token: flipping one with a warm cache has to invalidate, or unchanged files are served from the previous option set and findings the new set would report never appear. | ES-06-touch-noop | files rewritten with identical content, twice (`effects-on`) | `true` | "Rewriting a file changes its timestamp and size-independent stat data without changing its content. Diagnostics must not move. This is the script that would catch identity being bought by never being incremental: nothing changed, so nothing may be recompiled." |
| ES-07-persistent-finding | `violating.calr` (undocumented, never edited), `stable.calr` (documented, never edited), `churn.calr` edited every step (`docs-required` throughout) | `true` | "The disappearing-diagnostic shape, on a PER-FILE diagnostic. violating.calr is undocumented and never edited, so it reports Calor0601 on every build; stable.calr is documented and never edited, so it is the cache hit; churn.calr is edited every step to keep the build warm. Only diagnostic-clean files may be cached — if that rule were dropped, violating.calr would be skipped on the warm builds and its warnings would vanish, which the full-vs-incremental comparison catches. This is the shape #788 and #883 both had: findings present in a cold build and silently absent in a warm one. Distinct from ES-04, whose cross-module diagnostics are recomputed from summaries every run and therefore survive skipping by construction." |

The three `expectsReuse: false` scripts rebuild everything **by design** (file-set change moves
the cross-module function-map hash, compared unconditionally — #823 review m1; options-token
change invalidates globally — #788); their `reuseNote` fields record that, and the two-sided
witness makes it a tested claim.

### 3. The #883 leg, re-identified

- **What carries the #883 / #788 shape now:** **ES-05** (a diagnostics-affecting input outside the
  options token answers from the previous option set) and **ES-07** (a finding present cold and
  silently absent warm). Both pin the *shape* — "warm build answers for stale inputs" — through
  the only non-file input the harness can express, the `options` profile.
- **What does not exist:** an equivalent of F-3's ES-04. The registered ES-04 changed an
  **IL-analysis input** (referenced assembly / `RuntimeDirectory` / deps file) with no source edit
  and was required to **FAIL on the pre-#883-fix compiler**. The tree corpus has no step kind for
  that: `LoadScript` accepts only the three option profiles, the harness runs
  `CompilationDriver.CompileAll` in-process (not the MSBuild task, where #883 lived), and no script
  references an assembly, runtime directory, or deps file. #924's discrimination evidence was two
  **manual** arm-reverts recorded in the PR body (drop the options hash from
  `IsGlobalInvalidation` → ES-05 identity + reuse fail; let diagnostic-bearing files be cached →
  ES-07 identity fails); neither is encoded as a test, and neither exercises the IL-input path.
- **Where the nearest pin lives:** outside this corpus, and therefore outside the gate-2
  denominator. #883 was fixed by PR #890 (merged 2026-08-10; issue closed 2026-08-11). PR #1018
  (2026-08-19) added `CanonicalInputs_MutatingAnalysisInput_InvalidatesWarmCache`
  (`tests/Calor.Tasks.Tests/CompileCalorIntegrationTests.cs:919`, a Theory over
  `referencedAssembly` / `runtimeDirectory` / `nuGetPackageRoot` / `depsFile`) plus the
  `*ContentMutation_InvalidatesWarmCache` pair (`:997`, `:1025`). It is a live green guard written
  after the fix; this record does not claim it was run against the pre-fix compiler.
- **Open residual (R-F3-1):** the gate-2 corpus carries no discriminating pin for the literal #883
  input class. Closing it means either an additive script with a new step kind that mutates an
  IL-analysis input under the in-process driver, or an explicit decision — recorded here as an
  amendment — that the Tasks-level guard is the pin of record and gate 2 claims only the
  options-token shape. Until one of those lands, gate 2's "includes the #883 reproduction" wording
  (roadmap §2.5) is satisfied by shape (ES-05/ES-07), not by input class.

### F-4 implementation (2026-08-11)

- **Instrument:** the `VerifierRuntimeDifferentialTests` xUnit fixture under
  `tests/Calor.Verification.Tests`, run through a blocking filtered-test step in
  `.github/workflows/test.yml`. A missing Z3 runtime is a failure, never a skip.
- **Frozen denominator encoding:** 65 named forms derived bidirectionally from the generated
  whitelist appendix: 10 scalar types, 8 array element types, 15 expression kinds, 18 binary
  operators, 2 unary operators, 10 string operations, the ordinal-comparison rule, and one
  declarable quantifier-type representative. Each form has all 18 registered cells:
  3 positions × depths 1/2/3 × provable/refutable = **1,170 deterministic executions**.
- **Self-reference encoding:** `SelfRefNode` is refinement-contextual. The harness explicitly binds
  `#` to an `i32 __self__` solver/runtime parameter before translation, matching the emitter's
  existing `__self__` lowering. This covers the modeled meaning without claiming that an unbound
  `#` is ordinary source-valid syntax in `§Q`, `§S`, or `§PROOF`.
- **Field-access encoding:** the production contract pass and obligation solver derive a typed
  field registry from module classes. The `FieldAccessNode` row therefore translates
  `Probe.Value: u8`, proves both bounds `0..255`, and executes the `255` boundary witness. An `i8`
  mutation violates non-negativity and an `i32` mutation admits out-of-range values. The same
  production lookup merges partial/nested declarations, includes non-private inherited instance
  fields on derived types, and explicitly refuses missing dotted fields rather than guessing.
- **Scalar/array sort encoding:** integer scalar and array-element rows use width/signedness
  boundary predicates, not `x == x`. Complete ranges cover 8-bit types; bounded existential
  witnesses expose narrowing for 16-bit and `i32`; `i64`/`u32`/`u64` use signedness and arithmetic
  around the `i32` overflow boundary because larger typed literals are outside the current model.
  Array witnesses are non-null one-element arrays and retain the exact nullable-reference-model
  assumption. The string row uses non-negative length with a non-null ASCII witness and retains the
  exact string-model assumption; neither row overclaims nullable/non-ASCII equivalence.
- **Oracle and paths:** every case emits both guard-forced and opt-in C#. The guard-forced assembly
  is compiled with Roslyn and invoked; the opt-in emission is inspected to measure actual
  postcondition and obligation elision. Bounded `forall`/`exists` cases exercise emitter lowering
  (including D15's implication path), and explicit `ProofObligationNode` cases exercise the
  `ObligationStatus.Discharged` route. Target-presence and non-vacuity assertions prevent empty or
  mislabeled rows. Provable cells require `Proven`, refutable cells require `Refuted`, and
  `Assumed` is accepted only for an exact per-form production assumption set published in the
  report; all other non-decisive matrix statuses are uncovered.
- **Fail-safe controls:** typed `Unsupported`, `Timeout`, solver-error `Unknown`, `Unavailable`, and
  `Assumed` outcomes reach both postcondition and obligation emitter choke points; timeout and
  solver-error use the deterministic classifier shared by production `ProofOutcome.Assign`, while
  the remaining controls use production evidence constructors. Every control must retain and fire
  its false runtime guard even with elision enabled.
- **Harness lifetime and portability:** generated assemblies use collectible load contexts and are
  disposed/unloaded after execution. Repository discovery accepts `.git` directories and worktree
  `.git` files; the two canonical report paths are LF-pinned in `.gitattributes`.
- **Published reports:** `bench/phase0-agent-native/verifier-runtime-differential.{json,md}`.
  Current result: **65/65 forms solver-handled, 1,170/1,170 cells solver-handled, 40/65 forms
  eliding (61.54%), zero mismatches**. CI byte-checks both reports, so denominator or outcome
  movement must be reviewed rather than silently changing the published fraction.
