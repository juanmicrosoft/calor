**Method.** `python3 docs/plans/evidence/v0.25-r0-1426/reproduce/reproduce.py` runs each C# fixture
through four public surfaces:

- `calor convert` with no flags (`cli-default`);
- `calor convert --passthrough` (`cli-passthrough`);
- MCP `calor_convert` with default arguments (`mcp-default`);
- MCP `calor_convert` with `passthroughOnError: true` (`mcp-passthroughOnError`).

MCP calls pass only `source` and the mode flag. A fifth surface (`passthroughOnError` plus a custom
`moduleName`) is recorded only for F6-REPORT-11.

It compiles each produced `.calr` with `calor` (default options). If that fails only on effect
diagnostics (`Calor04xx`), it also compiles with `--permissive-effects`, the mode the CLI help names
for converted code. Both results are kept. `ProbeRunner.cs.txt` then compiles the original and each
generated C# file in memory and compares `Probe.Run()` results and exceptions. Two runs produced
identical results except the recorded commit.

**Limits.** This is a baseline, not a T1 oracle. Each behavior has one input. `calor migrate`, MCP
`calor_migrate`/`calor_batch`, SDK, MSBuild, LSP and the #1139 corpus modules were not exercised;
they are `not-measured` rows. `@permissive-effects` comparisons show behavior, not that the default
compile succeeds.

**Vocabulary.** A surface outcome is `native-match`, `native-mismatch`, `preserved-match` (some C#
kept as `§CSHARP` or inline `§CS{}`), or `compile-error:<codes>`; `@permissive-effects` marks a
comparison made after that compile.

## 10. Readiness records and the denominator rule

Each family's `readiness.status` is `NOT_STARTED` (all six now), `IN_PROGRESS`, `READY` or `BLOCKED`,
updated by #1428 (T1) and #1429 (W1), which do not close per family.

- **BLOCKED** names a `reason` and `blockedBy`.
- **READY** must contain all of the following (`S007`):
  - `scopeVersion`: the registered scope version it was assessed under;
  - `candidate.commit`: a full 40-hex SHA;
  - `cases`: for every registered case of the family, including `not-measured` rows, a `passed`
    result, an `evidence` file under `docs/plans/evidence/`, and `passed` for each registered `cells` entry;
  - `tests`: each with a non-blank `project`, numeric `total` > 0, and numeric `failed` = 0;
  - `websiteExamples`: existing pages under `website/content/` (an `#anchor` is allowed);
  - `reviews`: each with `reviewer` and an existing record under `docs/plans/evidence/**/reviews/`;
  - `approver`: `login` and a `https://github.com/juanmicrosoft/calor/pull/N#pullrequestreview-M` URL;
  - `independence`: `"reduced"`;
  - `blockersResolved`: a `reference` for every family blocker, including #1423.
- A READY record is **stale** once a later amendment adds, changes, moves (old and new family), or
  removes one of its family's cases. Mechanical checks cannot prove the cited tests passed; the
  approver's review does.

**Denominator rule.** `denominatorV1` freezes the 49 registered cases: id, family, role, expected
outcome, baseline status, fixture hash, and `requirementSha256` (a digest of the fixture path, note,
cells and observations, so an acceptance obligation cannot shrink silently). `evidenceSeal` holds the
SHA-256 of `baseline-results.json`, of every generated output, and of both producers. The test pins
one SHA-256 over both. Amendments carry a version, UTC date, PR, justification and `afterInspection`,
and apply in order as state transitions: `addedCases` registers or restores a case,
`removedCases` retains the last status, and `changes` gives the exact `from` and `to` of a tracked
field. Failure alone is not a reason to move a case out of scope. Editing `denominatorV1` or the
evidence fails the pinned seal.
