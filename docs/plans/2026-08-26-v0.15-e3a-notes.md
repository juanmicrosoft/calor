# v0.15 E3 slice a — effect-row compatibility at the five monomorphic sites

Working notes for `feat/v0.15-e3a-row-checking`. Branched from `b6530fac`
(E2 slice b, PR #1102). Governing document:
`docs/design/effect-rows-in-the-type-system.md`, §6 in full, plus §4.4/§4.5,
§5, §8.2, §13.1/§13.2/§13.4/§13.5(a).

## What this slice is

The **five monomorphic** compatibility sites of §6.2 — 1 assignment,
2 argument, 3 return, 4 override, 5 interface implementation — adjudicated by
the one relation `EffectRow.Fits` E2 slice b built, plus the cross-module site
(`CrossModuleEffectEnforcementPass.cs`) re-implemented on the same relation.

Site 6 (rank-1 generic instantiation), the lambda body row ρ_body, and
alpha-equivalence of `eff` binders are **slice b's**. Calor0418's replacement
is **E4's**.

## Decisions taken here, and why

### D1 — a site exists only where a DESTINATION DECLARATION is visible

Sites 1–3 fire when a function VALUE the pass can name — a `§LAM`, a
function-typed local/parameter/field, or a method group naming an in-module
callable — flows into a function-typed position **whose declaration this module
contains**. An external callee has no destination row at all: §8.4 freezes the
manifest schema without a row field in 0.15, so a BCL parameter is not an
Unknown destination, it is *not a site*. The alternative would put a Calor0425
on every BCL argument in every converted file, which is precisely the noise
§13.4's ledger exists to bound.

### D2 — an effect-POLYMORPHIC position is skipped, and that is the slice line

A row that mentions an `eff` variable is site 6. `Binder.BindRow` already makes
such a row `EffectRow.Unknown`; treating that as a slice-a destination would put
a Calor0425 on every call in the four A3 combinator fixtures, whose PP-E1 leg-A
negative-control baseline is **zero effect-family diagnostics**. So
`IsPolymorphicRow` (`EffectsNode.EffectVariables.Count > 0`) declines the site.

Sites 4/5 keep computing their rows from `EffectSet` (where an `eff` name
contributes nothing), which is byte-identical to today's answer and is what
keeps `A3-middleware-alpha`'s renamed binder passing without alpha-equivalence
being implemented. Naming it here rather than letting it read as support for
alpha-equivalence: **slice a does not unify `e` with `f`; it never compares
them.**

### D3 — `--permissive-effects` suppresses Calor0425; it never touches Calor0424

§4.5. The variance demotion at `EffectEnforcementPass.CheckEffectVariance` is
deleted: `varianceSeverity` is now `const … Error`. Priced first —
`grep -n "Permissive" tests/Calor.Enforcement.Tests/StrictnessBatchTests.cs`
finds only the 0418 waiver, and the committed-corpus differential below shows no
file depends on it.

### D4 — the two external-base Calor0419s are NOT retired here, and they must move together

§6.2 retires both external-base Calor0419 emissions in favour of Calor0425. This
slice takes **neither**, and the reason is that they are not the same kind of
code:

- the **interface-implementation** arm is a direct
  `_diagnostics.Report(… AssumedEffects …)` — trivially convertible;
- the **override** arm is an `AddAssumption(…)`, not a report. The assumption it
  registers propagates through the SCC pass into every caller's *computed* effect
  set. Turning it into a diagnostic deletes that propagation and moves Calor0410
  across the corpus — a blast radius with nothing to do with rows.

Converting only the first would make sites 4 and 5 disagree about what an
unresolvable base means, in exchange for a better message. Recorded as owed by
the slice that redesigns the assumption channel; §13.1's `:260` and `:607`
rewrites are **not** discharged here, and
`OverrideOfExternalBase_RoutesToAssumedChannel` /
`C3_ExternalInheritedImplementation_RoutesToAssumed` stay green as written.

§6.4's **third** message sample therefore ships with them, not here. P22's own
enumeration asks for "§10.1's … , §10.3's two, §6.4's **0424** text" — §10.1 and
§10.3 are the invocation-charging and rank-1 strings, so the string this slice
owes P22 is §6.4's 0424 text, and that is what it pins.

### D5 — §4.4's destination rule is applied at site 1

A binding whose initializer *fits while carrying reasons* takes
`AtDestination(src, dst)` = `Assumed(declared, reasons)`, so passing it onward
reports a **second** Calor0425 rather than laundering the assumption. Reasons
are read through `CarriedReasons` (total), never off `AtDestination` on a
`CannotTell` hop — the edge §4.4's E2 note warns about.

The one source of an `Assumed` row in slice a is a **method group whose own
effects this pass could only assume** (`_assumedEffects`), which is why
`CheckRowCompatibility` runs after `PropagateAssumptions()`.

### D6 — `FunctionBoundType` at every function-typed position (§8.2)

`Binder.TryBuildRowedFunctionType` → `TryBuildFunctionType`: it now builds one
for any function-typed spelling, rowed or not (row = `Unknown`), and a
function-typed `§B` with no row and no function-typed initializer gets one too.

Slice b declined this for fear of moving Calor0418. **Measured instead of
inherited:** `VariableSymbol.FunctionType` and
`FunctionSymbol.ReturnFunctionType` have no reader anywhere in `src/`
(`grep -rn '\.FunctionType\b' src/` → declarations only), and
`EffectEnforcementPass.IsFunctionBoundType` reads
`CallGraphAnalysis.BoundValueTypes`, which is built from bound call *receiver*
expressions, not from these two properties. The corpus differential is the
proof: **Calor0418 count unchanged at 619 over 886 files.**

## A pre-existing crash this slice found and did not fix — issue #1104

Running `EffectEnforcementPass.Enforce` directly over **unbound**
Lossy-converted corpus modules is fatal: `serilog/src/Serilog/Core/Logger.cs`
and `Core/Sinks/Batching/BatchingSink.cs` take the test host down. It reproduces
with E3's row checking disabled, so it is not this slice's.

Filed as **https://github.com/juanmicrosoft/calor/issues/1104** with the repro, the suspected cycle
(`EffectInferrer.InferKnownCallResultType` → `FindLocalDeclarationType` →
`ResolveLocalValueTypeFromAst` → back), and the reason it has not been seen
before: the pass normally runs behind the binder inside `Program.Compile`, which
returns as soon as binding has errors, and these modules do not bind. All 886
committed `.calr` compile through the CLI without incident.

The crash is an uncatchable `StackOverflowException`, so no `catch` and no
larger thread stack contains it — measured, with a 64 MB stack in place (F8).
P32's ledger works around it by binding first and skipping modules the binder
rejects. That is independently the *correct* denominator, since those modules'
Calor0425s could never be emitted — but it costs 265 of 364 modules (F7).
