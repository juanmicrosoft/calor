## Where `EffectRow` lives, and why — the architecture decision

`ArchitectureTests.BindingLayer_HasNoReferenceToEffectsNamespace` forbids any
file under `src/Calor.Compiler/Binding/` from naming the `Effects` namespace:
the binder is upstream of effect enforcement. §8.2 nevertheless requires
`FunctionBoundType` — which lives at `Binding/BoundTypes/BoundType.cs` — to
carry an `EffectRow`. A row whose carrier were `Effects.EffectSet` would force
exactly the reference the pin forbids.

**Decision.** `EffectRow` is declared in `Binding/BoundTypes/BoundType.cs`
(namespace `Calor.Compiler.Binding.BoundTypes`, no new `src/` file — the
Calor-first guard and `facts.py`'s `Effects/*.cs` = 10 count both hold), and its
carrier is an `ImmutableSortedSet<string>` of **compact surface codes**
(`"cw"`, `"db:r"`) — the same vocabulary `BoundFunction.DeclaredEffects` and
`BoundLambdaExpression.DeclaredEffects` already use, so `Binding/` gains no new
dependency at all.

The family/narrow relation moves with it: `EffectRow.FamilySubtypes` is now the
**single source of truth**, and `Effects.EffectSubtyping.Subtypes` is *derived*
from it by projecting compact codes into the internal `(EffectKind, string)`
vocabulary. This is the same shape as E1 slice 2b's
`MapShortTypeNameToFullName` → `Binding/TypeIdentity` move (§8.1). Two
hand-written tables would be two things to keep in step; a derivation cannot
drift, and `EffectSubtypingTests` keeps testing the `Effects`-side API (P7).

Rejected alternatives, and why:
- *Put `EffectRow` in `Effects/EffectSet.cs`* — `BoundType.cs` would need
  `using Calor.Compiler.Effects;`. Pin red.
- *Relax the pin to allowlist `EffectSet`* — weakening a pin to fit the change
  it is meant to constrain. Declined.
- *`EffectSet` as the carrier via a partial class outside `Binding/`* — the
  constructor and property declaration still name the type. Contorted, and the
  pin would be satisfied only by accident of where a token sits.

`Effects` → `Binding` is the ALLOWED direction and already exercised
(`EffectEnforcementPass.cs:3`, `ExternalCallCollector.cs:3-4`).
`eng/compiler-components.json` does not list `Effects` as a component at all, so
the dependency-contract test is unmoved.

`Fits`, as nine cells:

| src ↓ / dst → | `Concrete(B)` | `Assumed(B, R_d)` | `Unknown` |
|---|---|---|---|
| **`Concrete(A)`** | `Fits` iff `A ⊆ₑ B` else `DoesNotFit` | `Fits` iff `A ⊆ₑ B` else `DoesNotFit` | `CannotTell` |
| **`Assumed(A, R_s)`** | `Fits` iff `A ⊆ₑ B` else `DoesNotFit` | `Fits` iff `A ⊆ₑ B` else `DoesNotFit` | `CannotTell` |
| **`Unknown`** | `CannotTell` | `CannotTell` | `CannotTell` |

`Assumed` fits exactly like its underlying set; the reasons ride along through
`CarriedReasons` and are what E3 turns into Calor0425. Unknown on **either** side
is `CannotTell` — `EffectSet.IsSubsetOf`'s `if (other.IsUnknown) return true` is
deliberately not carried into the row relation, and P8's discriminating revert
is re-introducing it.

## Deviations from the doc's literal wording, and why

1. **The carrier is the internal `category:value` code, not the compact surface code.**
   §8.3 writes the row's display in compact codes (`cw`, `fs:w`). The compact spelling is a
   projection through `EffectCodes.Registry`, an `Effects` table, and `Binding/` may not
   reference `Effects/`. So identity is the internal spelling and the compact rendering is
   `Effects.EffectRowDisplay.ToCompactDisplayString` — an extension method on the row, on the
   side of the layering that owns the registry. The user-facing strings §8.3 specifies
   (`[unknown]` / `[pure]` / `cw, fs:w` / `[assumed: cw]`) are unchanged and pinned in
   `EffectRowLatticeTests.DisplayStringIsRowFree`.

2. **Not every function-typed position gets a `FunctionBoundType` — only rowed ones.**
   §8.2 could be read as "function-typed positions bind to function types now". Doing that
   unconditionally makes `EffectEnforcementPass.IsFunctionBoundType` answer true where it
   answers false today, which moves Calor0418 on programs containing no rows at all. Slice b's
   whole claim is a zero corpus delta, so the widening waits for E3, which has a checking site
   to justify it.

3. **An un-annotated `§LAM`'s row is `Unknown`, not the body's row.**
   §3.5 says an omitted lambda row is inferred from the body. ρ_body is computed by the effect
   pass — an AST walk the binder is not on — so slice b cannot compute it. `Unknown` is the
   sound placeholder: it fits nothing and is fitted by nothing, so no check can pass on the
   strength of a row that was never computed. Pinned as such, with the debt named in the test.

4. **A row that mentions an effect VARIABLE is `Unknown`.**
   §7.4's instantiation is E3's. Until a row is instantiated the variable's contribution
   genuinely is not known, and the lattice has no fourth shape for "polymorphic". The binder
   still **checks that each variable is bound** by the enclosing declaration's `eff` binders, so
   a row cannot silently mention a name nothing declares. It does **not** resolve the variable to
   an ordinal: an earlier revision computed one and discarded it while this note claimed E3
   "inherits the resolution" (review round 1, MINOR 6). It does not — the variable names are on
   the AST (`EffectsNode.EffectVariables`) where E3 can read them, and the ordinal, with the
   alpha-equivalence that makes it the right key, belongs to the slice that substitutes an
   argument's row for a binder.

5. **Binder-side Calor0404 is a defensive check, not a reachable diagnostic — and slice b says
   so.** The task list called for "an unbound variable is Calor0404 at the binder (the parse
   side only recorded it)". Executed, the parse side does **not** record unbound variables: the
   parser tracks the same `eff` scope while it parses the row, and a name no enclosing
   declaration binds never enters `EffectsNode.EffectVariables` at all — it falls through to
   `EffectCodes.TryParseCompact` and becomes **Calor0403 `Unknown effect code`**. So nothing
   reaches the binder unbound. The check exists because the binder is the layer that owns
   scope, and it is honest about being unreachable from source today. **Routing Calor0403 →
   Calor0404 stays E3's**, as E2 slice a's deviation 5 already recorded.

6. **`Calor0404`/`Calor0405` had to be added to `BindingDiagnosticPolicy.IsCompilationError`.**
   Not a deviation from the design so much as a mechanism the design does not mention:
   `Program.Compile` propagates only an allowlisted set of binder diagnostics. Without the two
   codes on that list a binder-reported row error is computed and then dropped. Neither can fire
   on a program with no rows, and the corpus has none.

7. **`TypeIdentity.IsFunctionTypeName` — a move, with a forwarder.** The binder needs the same
   "does this spelling name a function type?" predicate the effect pass uses. Rather than a
   second copy, the list moved to `Binding/TypeIdentity` and
   `EffectEnforcementPass.IsFunctionTypeName` forwards — the pattern E1 slice 2b established
   for `MapShortTypeNameToFullName`. Behaviour is statement-for-statement identical, including
   the generic-name stripping.
