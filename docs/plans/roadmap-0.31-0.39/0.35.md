# Milestone 0.35 — Proofs that reach real code

Before deepening the verifier, make its proofs count on the code agents and converters actually produce: inventory what is Proven, lift the demotions that can be lifted soundly, and give preconditions consumers on class members.

## Entry criteria

- Soundness sweep green for the proof-claim count in docs/release-policy.md (#1783), counted from the latest re-registration of the packet (a freeze that only adds rows does not restart it).
- Seeded-defect replication published or declined; its registered consequence for 0.35 applied (#1816).

## Exit criteria

- Proof yield (Proven, Assumed, Unsupported) reported before and after on a named set of native modules; or, if fewer than six corpus modules qualify under the selection rule of #1843, the outcome the maintainer recorded on #1662 (a relaxed rule fixed before measuring, or "not measurable on the corpus" with the yield reported under that caveat).
- Every new verifier step has seeded unsound controls and safe controls in the registered instrument for that analysis (the sweep for the contract and obligation engines; BenchmarkSubjectRegressionTests and BugPatternRuntimeOracleTests for the bug-pattern and taint analyses), and that instrument is green.
- The release is not earlier than the last freeze in the milestone that changed an existing sweep verdict plus the proof-claim count in days.

## Maintainer decisions, batched

- Reference-null modelling (#1860); an opt-in surface for obligation verification (#1868); which null gaps clear the gate (#1869).
- Guard lift re-read at the 0.35 close: if #1866 is held, the census reading is re-read from the corpus job and the maintainer adds a dated entry to the #1847 record.

## Epic #1662 · [0.35] Epic: verification depth

Existing epic #1662. The body below replaces or amends it as marked.

#### Goal

Make the verifier's proofs count on the Calor that the converter and agents actually produce. Measure what is reported Proven, Assumed and Unsupported today; lift the demotions that can be lifted soundly; decide whether obligation results get a command-line surface; then model more of the BCL and prove loop properties, in the order the measurement supports.

#### Why

At HEAD bc80daeb a successful proof is reported `Proven` only if the solver query contains no string, array or user-type term, and every parameter of the callable is put into the query before anything is translated. A proof that touches the solver's string theory comes back `Assumed` under the named assumption `string-model`; one that touches an array or user-type sort comes back `Assumed` under `reference-model`. The runtime check is kept in both cases (`src/Calor.Compiler/Verification/Z3/Z3Verifier.cs:576-631`, `src/Calor.Compiler/Verification/Obligations/ObligationSolver.cs:326-357`, `docs/verification-modeled-forms.md` section 4.1). Each demotion closed a false proof that deleted a failing check. While they stand, the string and collection modelling in #1660 and the index-bounds proofs of #1661 report `Assumed`, not `Proven`. Three issues narrow them. #875 lifts the string demotion where non-null is established. #1851 does the same for arrays, or records why it cannot. #1862 stops a parameter that the query never reads from demoting or refusing the proof. User-type sorts, which include `List<T>`, stay demoted in 0.35, and no release text may call a proof over them proven.

Four more facts set the order of work:

- There is no count of where proofs stop today, so "more Proven" cannot be checked and the issues below cannot be ordered (#1853).
- The converter writes no contracts (`CHANGELOG.md:39-40`), so the contracts 0.35 proves have to be authored (#1843).
- Refinement obligations, including the index-bounds obligations generated for array accesses, exist only under `CompilationOptions.VerifyRefinements` (`src/Calor.Compiler/Program.cs:1074`). No CLI command and no build property sets it; the MCP tool `calor_refine` does. #1868 decides whether a command should.
- The k-induction prover runs only behind a switch that no command sets, and its only output is two diagnostics (`src/Calor.Compiler/Analysis/VerificationAnalysisPass.cs:43`, `:512-524`).

#### Work

| Issue | Item |
|---|---|
| #1853 | Proof-status inventory on the conversion corpus: Proven, Assumed by named assumption, Unsupported and runtime-only, over both verification channels |
| #1843 | Name the native modules, author their contracts by hand and by agent, and report proof yield on them before and after the milestone |
| #875 | Lift the string-proof demotion where non-null is established; keep it everywhere else |
| #1851 | Lift the `reference-model` demotion for arrays where non-null is established, or record why not |
| #1862 | Declare only the variables a query reads, so that an unread string, array, user-type or floating-point parameter no longer demotes or refuses a proof |
| #1868 | Decision: an opt-in CLI and build surface for obligation verification |
| #1660 | Model more BCL in Z3: the unsupported string operations, collection `Count`/`Contains`/indexing, common `Math` functions |
| #1661 | Promote k-induction and loop-invariant synthesis into the verification pipeline for `for` and `while` loops |

The same comment lists the counted runs (first and last run URL, and the count) and records the commit of `main` at which both held. That commit is the *entry commit*: #1843 measures its `before` value with the compiler built from it.
2. **#1853** first. It is report-only and tells the rest what to do first.
3. **#1843** next. Its `before` value is committed before any issue below changes a verdict. **#1868** is a decision that changes no verdict; it can be taken any time after the #1853 record exists.

All five can change existing verdicts. A case that is `Assumed` or `Unsupported` today may become `Proven`; #1660 models operations that the registered rows STR-UNMODELED-OPS and CALL-IN-CONTRACT expect to be refused; #1661 targets loop shapes that the rows BODY-LOOP-CALL-MUTABLE and OBL-LOOP-VARIABLE expect to be refused. ### #1853 · [0.35] Proof-status inventory on the conversion corpus

**Action:** new · **Labels:** tests · **Depends on:** #1779 · **Blocks:** #1843, #875, #1851, #1862, #1868, #1660, #1661, #1860, #1866, #1703 · **Displaces:** none: new capacity justified in body

#### Change

Build one counter that reports what the verifier establishes about a set of `.calr` files, and run it on the conversion corpus (MediatR, Serilog and FluentValidation, pinned under `bench/corpus/`).

1. **The counter.** A console project under `tools/` (for example `tools/Calor.ProofInventory`) that takes `.calr` files or a directory and writes the JSON below. It is a measurement tool, not a `calor` command: whether obligation results get a CLI surface is the decision in #1868, which may adopt this counter. It must not depend on the corpus job, because #1703 re-runs it on the pilot component in 0.36.
2. **Both channels.** An *obligation* is one thing the verifier is asked to establish. Call `Program.Compile` on each file with both options set, as the soundness-sweep harness does (`bench/Calor.Soundness.Sweep/BaselineHost.cs:56-61`):
   - the contract channel (`CompilationOptions.VerifyContracts`; results in `CompilationOptions.VerificationResults`): one result per postcondition and one per parameter refinement. The refinement result is a satisfiability check, not a proof about callers; it gets its own column and is never counted as `proven`;
   - the obligation channel (`CompilationOptions.VerifyRefinements`; results in `CompilationOptions.ObligationResults`): one entry per `ObligationTracker` obligation, by kind (`RefinementEntry`, `RefinementReturn`, `ProofObligation`, `IndexBounds`, `Subtype`).

   A corpus file refers to types in other files of its project. If compiling files one at a time leaves most of them not verified, compile them with their project context, the way the build task passes references and cross-module types (`src/Calor.Tasks/CompileCalor.cs:810-826`).
3. **Columns.**

| Column | Content |
|---|---|
| Files | given, verified, and not verified with the first error code of each |
| Obligations | total, by channel and by kind |
| Status | `proven`, `assumed`, `refuted`, `unknown`, `timeout`, `unsupported`, `unavailable` (the `ProofStatus` wire names) and `runtime-only`; the eight sum to the total |
| Assumed by assumption | one count per assumption name, the text before ` — ` in the assumption string: `string-model`, `reference-model`, `checked-arithmetic`, `exceptional-paths:division`, `exceptional-paths:contract-division`. An obligation with two assumptions counts under each and once in `assumed` |
| Unsupported by reason | every reason string with its count in the JSON; the record prints the ten most frequent and always the reason "Null literals are not modeled by the contract translator.", which #1860 reads |
| Refinement satisfiability | satisfiable, unsatisfiable, undecided |

   `runtime-only` is an obligation the solver never sees and the emitter always guards: `ObligationStatus.Boundary`. An obligation left `Pending` because no solver ran counts as `unavailable`. The counter reads each obligation's proof outcome: Discharged is `proven`, Failed is `refuted`, a demoted proof is `assumed`. Under the default obligation policy a failed obligation is a compilation error (Calor1121, or Calor1140 for a `proof` obligation; `src/Calor.Compiler/Program.cs:1104-1105`). A file whose only errors are those two codes is counted as verified, and those obligations as `refuted`.

   Call-site obligations share the kind `Subtype` with assignment obligations at HEAD. #1864 (epic #1861) adds a field that tells them apart, and the by-kind table reports them as their own row once that field exists: if #1864 merged first, this issue adds the row; otherwise #1864 does, in the counter.
4. **On the corpus.** #1779 delivers the corpus report job (`scripts/corpus_report.py`, `.github/workflows/corpus-report.yml`), whose per-project report has a `columns` object that later issues fill. Add a column function that runs the counter on the migrated working copy and stores its output under the key `proof_status`. Count the files the job classifies as native and, separately, those it classifies as partly preserved (some members kept as raw C#).
5. **Record.** Publish the first run in `docs/plans/0.35-proof-status-inventory.md`: Calor commit, corpus tags, the table per project, the number of files verified and not verified, and a ranked list of what keeps obligations from `proven` (each assumption name and each unsupported reason, by count). Post the list on #1662.

#### Baseline (HEAD bc80daeb)

- No job reports proof status on the corpus. `calor migrate` has a verification phase (`src/Calor.Compiler/Migration/Project/ProjectMigrator.cs:2214`), but it runs the contract channel only, folds `Assumed` into `Unproven` (`src/Calor.Compiler/Verification/ProofOutcome.cs:390`), and counts a file that yields no result as skipped with no reason (`ProjectMigrator.cs:2297`, `:2302`).
- The converter writes no contracts: every `preconditions:` and `postconditions:` argument in `src/Calor.Compiler/Migration/RoslynSyntaxVisitor.cs` is `Array.Empty` (21 occurrences, counted with `grep -c "preconditions:\|postconditions:"`), and the 0.30 notes say conversion does not recover contracts that exist only as `throw` guards (`CHANGELOG.md:39-40`). On converted code the contract channel has nothing to check.
- What converted code does have is index-bounds obligations, one per array access and indexed write (`src/Calor.Compiler/Verification/Obligations/ObligationGenerator.cs:798-817`) in the bodies of functions, methods, constructors and operators; accessor bodies and members of nested classes are not visited (`:57-86`). They exist only under `VerifyRefinements` (`src/Calor.Compiler/Program.cs:1074`), which no CLI command sets. The MCP tool `calor_refine` sets it (`src/Calor.Compiler/Mcp/Tools/RefineTool.cs:104`), and so does the sweep harness (`bench/Calor.Soundness.Sweep/BaselineHost.cs:59`), which is a model for calling the compiler with both options.
- A discharged index-bounds obligation is reported `Assumed` with `reference-model` (`src/Calor.Compiler/Verification/Obligations/ObligationSolver.cs:326-357`).
- A parameter refinement that the contract channel reports as `Proven` is one that is satisfiable (`src/Calor.Compiler/Verification/Z3/Z3Verifier.cs:183-203`), and `calor verify` adds it to its `Proven Rate` (`src/Calor.Compiler/Commands/VerifyCommand.cs:570`).
- Where the vocabulary lives: `ProofStatus` (`ProofOutcome.cs:15-46`), the five assumption strings (`Z3Verifier.cs:27-70`), `Boundary` (`ObligationGenerator.cs:664`, `:691`, `:851`).

#### Why

0.35 sets out to prove more about real programs, and there is no number for what is proved about them today. The inventory orders #1660 and #1661, gives #875, #1851 and #1862 something to report against, supplies the numbers the decisions #1860 and #1868 read, and is repeated by #1703 on the pilot component to size the 0.37 claim. Read from the code, the first run should find no contract-channel obligations on converted code and no `proven` index-bounds obligation. That prediction has not been run; the record must say where it was wrong.

This is new capacity and displaces no issue: it is report-only, and the milestone's first exit criterion cannot be checked without it.

- The counter runs on a directory of `.calr` files with no corpus job present, and a test covers it.
- A test gives the counter a fixture with one array access and no contract and finds at least one `IndexBounds` obligation. This guards against an inventory that reads zero because it ran one channel.

### #1843 · [0.35] Where the 0.35 contracts come from, and a proof-yield metric on real programs

**Action:** new · **Labels:** tests · **Depends on:** #1853 · **Blocks:** #875, #1851, #1862, #1660, #1661 · **Displaces:** none: new capacity justified in body

#### Change

1. **Name the set.** Add `bench/proof-yield/manifest.json` (new directory). Candidates are the natively converted files in the #1779 corpus output at the commit of the #1853 record. The rule is fixed here so that the set is not chosen by its results: per corpus project, order the native files by number of public members, descending, path as tie-break, and take the first four that have a member with an `int`, `string`, array or `List<T>` parameter or result and that compile on their own with default `Program.Compile` options. Copy them to `bench/proof-yield/modules/<project>/` with source path, corpus tag and converter commit. List each skipped candidate with its first error code. Four per project, twelve in all, is set by this issue. If fewer than six qualify in total (half the intended set, also set here), stop and report the count on #1662 before authoring anything. The maintainer then records one of two outcomes on #1662: (a) a relaxed selection rule, written before any yield is computed, under which this issue continues; or (b) "not measurable on the corpus", in which case `manifest.json` lists the modules that did qualify, `before.json` is committed over that smaller set with the reason, the release notes report the yield with that caveat, and the issues this one blocks are released.
2. **Author the contracts in two layers.** Neither is produced by a tool that lifts `throw` guards.
   - `hand`: for every public member with an `int`, `string`, array or `List<T>` parameter or result, at least one parameter refinement or postcondition that is true of the code, or a line in the manifest saying why there is none.
   - `agent`: the same starting files given to one coding agent with `docs/syntax-reference/current-language.md` and a prompt committed beside the manifest. Record the model id. Contracts that do not compile are removed and counted. There is no floor: an empty layer is recorded and the issue still closes.

   This is authoring in an ordinary session. Nothing about cost, iterations or success is read from it, and no criterion depends on how well the agent writes Calor. Producing the layer through the benchmark harness would be a paid run that needs its own registration; this issue does not authorise one.
3. **Metric.** *Proof yield* is the number of obligations by status over the set, produced by running the #1853 counter (the console project that issue adds under `tools/`) on each layer. Do not write a second counter. The headline is `proven`, `assumed` by assumption and `unsupported` by reason. Refinement satisfiability stays in the counter's own column and is never added to `proven`: a satisfiable parameter refinement says the function can be called, not that anything was proved. A step of the corpus report workflow (`.github/workflows/corpus-report.yml`, added by #1779) runs the counter on the set, uploads `proof-yield.json` and prints it beside the committed baseline.
4. **Before value.** Commit `bench/proof-yield/before.json`: the yield per layer, the *entry commit* and the command that produced the numbers. The entry commit is the commit of `main` recorded on #1662 when the 0.35 entry criteria were met; the `before` value is the yield of the compiler built from it, so that it does not depend on which verifier changes have merged since. If `git diff --stat <entry commit> HEAD -- src/Calor.Compiler` is empty, measure at `HEAD`. Otherwise check out the entry commit, apply `bench/proof-yield/` and the counter as it was at the #1853 merge commit (a later counter may read compiler members the entry commit lacks, such as #1864's call-site field) and measure there; `before.json` names that counter commit.
5. **Test and record.** `tests/Calor.Verification.Tests/ProofYieldManifestTests.cs` checks that every manifest module and both layers exist and compile, and that the status counts in `before.json` sum to its totals. `bench/proof-yield/README.md` states where the contracts come from, the selection rule, the one command that prints the before-and-after table for release notes, and that a contract the verifier refutes is corrected with the reason recorded, or kept and counted, never deleted to raise the yield.

#### Baseline (HEAD bc80daeb)

### #875 · [0.35] Lift the string-proof demotion where non-null is established

### #1862 · [0.35] Scope proof demotion and unsupported-type refusal to the variables a query reads

**Action:** new · **Labels:** enhancement, p1 · **Depends on:** #1853, #1843 · **Displaces:** none: new capacity justified in body

#### Change

Today the verifier declares every parameter of a callable in the solver before it translates anything. Declaring a `string` marks the query as touching the string theory. Declaring an array, a `List<T>` or any type the translator does not know marks it as touching a reference sort. A `float` or `double` parameter cannot be declared and refuses the whole obligation. So a proof that reads only integers is reported `Assumed` (proved under a named assumption, runtime check kept) or `Unsupported` because of a parameter it never reads. Declare only the variables the query reads.

1. **Where.** `Z3Verifier.VerifyPrecondition` and `Z3Verifier.VerifyPostcondition` (the contract channel) and `ObligationSolver` (the obligation channel). `Z3ImplicationProver` already declares only the parameters its contracts read and is the model.
2. **What "reads" means.** The query is everything asserted into the solver for one obligation: its condition, every precondition and collected fact asserted with it, and, for a postcondition that names `result`, the function body as encoded. A variable is read if any of those refers to it. `result` is declared only when read.
3. **How.** Keep the trigger where it is: the two flags stay set at the point a sort is minted. Change what gets minted. Prefer deferring the mint to first use inside the translator (register each name with its type up front, create the solver constant when a reference, array access or length is first translated) over walking the syntax tree in advance. The first version of the string trigger walked the contract, missed the body and let a false proof through (`docs/verification-modeled-forms.md:126-140`).
4. **True types only.** A name that is read is declared with its declared type, or the obligation is refused. It must never reach the translator's on-demand defaults, which create an `i32` array and a free length for a name they do not know (`src/Calor.Compiler/Verification/Z3/ContractTranslator.cs:1496-1511`, `:2545-2555`). Those defaults are safe today only because every parameter is declared first.
5. **Refusal.** A parameter of a type that cannot be declared refuses the obligation only when the query reads it. The refusal text does not change.
6. **The tests and text that pin today's behaviour.** `StringTypedParameter_DemotesEvenNumericObligation` and `ArrayParameter_DemotesEvenAPurelyNumericPostcondition` assert the coarse behaviour as a decision. Replace each with a pair: the same signature with an obligation that does not read the parameter (now `proven`), and one where the parameter is read only through the body (still `assumed`). Rewrite the two paragraphs of `docs/verification-modeled-forms.md` that document the coarseness (`:142-145`, `:157-165`).

This issue and the two lifts are independent and can merge in either order. This one narrows which terms enter the query; #875 and #1851 decide which of the terms that do enter are trusted to be non-null.

### #1864 · [0.35] Call-site refinement obligations for class methods and constructors (operator bodies as callers)

**Action:** new · **Labels:** enhancement · **Depends on:** #1800 · **Blocks:** #1863, #1866 · **Displaces:** none: new capacity justified in body

#### Change

Generate call-site refinement obligations for calls made from, and to, class members of the same module. A *call-site obligation* states that the arguments of one call satisfy the callee's parameter refinements; the solver discharges it, refutes it or refuses it. The work is in `src/Calor.Compiler/Verification/Obligations/ObligationGenerator.cs`.

1. **Callers.** Run the walk that `GenerateCallObligations` (`:106-207`) performs for module functions over the bodies of class methods, constructors and operator overloads (the loops at `:72-86`). Record each obligation under the member's `Id`; `ObligationSolver.BuildFunctionInfo` already builds solver state for all three (`ObligationSolver.cs:523-621`, same directory).
2. **Callees.** Besides module functions, resolve methods of classes declared in the module, static and instance, in every spelling the parser accepts (`this.M(...)`, `Type.M(...)`, `receiver.M(...)`), and constructor calls `new T(...)` (`NewExpressionNode`, which the walk at `:136-145` does not visit). Take the callee's conditions from `ContractVerifier.EffectivePreconditions`, as `:192` does.
3. **Exactness.** Generate a provable obligation only when the call resolves to exactly one source declaration and binds exactly. Keep the existing conditions (`:157-164`, and `ExactArgumentType` at `:120-134`) and add two:
   - the callee is not `virtual`, `abstract`, `override` or an interface implementation, because the member that runs may be another declaration;
   - every name the callee's refinements read is one of its own parameters. In a class a refinement can read instance state, and the receiver of `other.M(...)` is not the caller's `this`. `FactCollector.SubstituteCallParameters` already refuses a dotted read such as `this.limit`, but leaves any other bare name in place (`FactCollector.cs:916-917`, same directory), where it would be read in the caller's scope and could collide with a caller variable of the same name. Whether the binder resolves a bare name in a refinement to a field is not verified; refuse it either way.

   When a candidate callee has a refined parameter and the call does not qualify, add the existing refusal obligation (`:182-190`, status Unsupported). A candidate is the declaration the call resolves to or, when resolution fails, any same-module member of that name. No call to a refined same-module member may be skipped silently.
4. **No guard is removed.** A discharged call-site obligation deletes no runtime check; the callee keeps its entry guard.
5. **Landing form.** #1800 records whether call-site obligations are a default-build break. At HEAD they are not (see Baseline). Re-check when you start. An opt-in surface chosen by #1868 is not a default build and changes nothing here; say in the pull request how a Failed call-site obligation appears on it. If a default command or a default build runs refinement verification by then, land in a form #1800 allows for a rejecting guarantee (a warning in this edition, or behind the per-module opt-in) and say which in the pull request.
6. **Countable.** At HEAD a call-site obligation has kind `Subtype`, which it shares with assignment obligations (`ObligationTracker.cs:33-49`), and is told apart only by its description. Add a field on `Obligation` (`ObligationTracker.cs:54`), for example the callee's name, set where the generator creates the refusal and the provable call-site obligation (`ObligationGenerator.cs:184-186`, `:199-201`), so that a tool can count call-site obligations without matching text. Keep the kind and the description: existing tests select on them.
7. **Controls.** Add cases to the registered packet of the soundness sweep (`bench/Calor.Soundness.Sweep`, the daily job that compares each proof the verifier claims with an independent oracle; packet in `tests/TestData/SoundnessSweep/` at HEAD). A *seeded unsound control* has a claim that is false on a reachable input, so Discharged is a false proof. A *safe control* has a claim that holds on every input. Add rows the way the packet's design record prescribes (section "Successor soundness packet: design" of `docs/plans/0.31-toolchain-and-sweep-record.md`, written by #1769), and set expected verdicts with `python3 scripts/soundness_sweep_gate.py freeze` (`bench/Calor.Soundness.Sweep/README.md`, "Updating the expected verdicts") from a macOS ARM64 run; `freeze` refuses a run that contains a finding. At HEAD the harness takes as a case's claim the single obligation of the template's `obligationKind` (`bench/Calor.Soundness.Sweep/CaseExecutor.cs:150-154`) and looks for a guard marker per kind (`:206-211`); a call-site case has one `Subtype` obligation and no guard at the call. If the harness in force cannot judge such a case, extending it is part of this issue. Minimum set:
   - unsound: a method passes a violating literal to a refined method of its class; a two-parameter relation `(int:lo, int:hi | (# > lo))` called with the arguments swapped; `new T(arg)` with an argument that can violate the constructor's refinement; a call through a base-typed receiver to a `virtual` method; an overloaded callee; a caller that reassigns its parameter before the call; a callee name shadowed by a local; a callee whose refinement reads a field, by bare name and through `this`, called on another instance from a caller that has a parameter of the field's name;
   - safe: a method whose own refinement implies the callee's; a constructor call with a satisfying literal; a static call `Type.M(1)`.

Example (written from `docs/syntax-reference/current-language.md`; not compiled):

```calor
module Metering
  class Meter
    func Clamp private (int:value | (# >= 0)) → int
      return value

    func Read (int:raw | (# >= 0)) → int
      !
      return this.Clamp(raw)

    func ReadRaw (int:raw) → int
      !
      return this.Clamp(raw)
```

With the switch on, a qualifying guard becomes a refinement on the guarded parameter, with the negated guard condition as its predicate, and the guard statement is removed.

- The switch is a property on `ConversionOptions` (`src/Calor.Compiler/Migration/CSharpToCalorConverter.cs:107`), off by default, and an option on `calor convert` (`src/Calor.Compiler/Commands/ConvertCommand.cs`, `BuildCSharpToCalorOptions` at `:329-346`). A guard qualifies only if all of these hold:

- It is an `if` with no `else` whose body is one `throw new ArgumentOutOfRangeException(...)`, resolved to `System.ArgumentOutOfRangeException`, whose `paramName` argument names a parameter of the member.
- Its condition reads only that parameter, earlier parameters and constants, contains no call, and its negation can be written as a refinement on that parameter.
- Every statement before it is itself a lifted guard, and the lifted guards appear in parameter order (refinements are checked in parameter order on entry, `src/Calor.Compiler/CodeGen/CSharpEmitter.cs:6463-6498`).

Exclusions. Each is an acceptance test that shows the guard left in the body, unchanged:

1. The parameter is assigned, incremented, or passed by `ref` or `out` anywhere in the body (a refinement is checked again on every assignment, `docs/syntax-reference/refinement-types.md:17-19`).
2. The member is `virtual`, `abstract`, `override`, or implements an interface member. This exclusion is unconditional. The member that runs at a call may be another declaration, so a refinement lifted on one declaration does not describe the others; and on a member that implements an interface, a refinement the interface lacks is the error Calor0810 (`src/Calor.Compiler/Verification/ContractInheritanceChecker.cs:1631-1643`; the checker also compares an override with a base-class method that carries contracts, `CollectBaseMethods`, `:593-635`). #1735 does not lift the exclusion; it is a prerequisite so that every refinement in converted code has one pinned runtime behaviour before the converter starts to emit them.
3. The guard is a null guard in any form (`== null`, `is null`, `?? throw`, `ArgumentNullException`, `ThrowIfNull`).
4. A statement with a side effect precedes the guard.
5. The guard throws any other exception type, names no parameter, or names a parameter its condition does not constrain.
6. The throw carries a custom message or an `actualValue` argument, unless the #1847 record allows lifting such guards.

**What to build.** A bug-pattern check that reports a local that owns a disposable object and can leave the function without disposing it. The definitions are the spike's, so that the check reports what the spike counted. Where the note differs from this list, the note wins and the pull request says so.
