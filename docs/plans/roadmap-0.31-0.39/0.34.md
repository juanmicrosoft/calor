## Epic #1659 · [0.34] Epic: native conversion coverage

Existing epic #1659. The body below replaces or amends it as marked.

#### Goal

Convert more C# natively, measured against a baseline restated on 0.30, and leave no unsupported construct without an owner. Since 0.30 every C# file that parses is migrated (#1609, `CHANGELOG.md:107-113`); each construct the converter cannot express is kept as preserved C# (the original text inside a raw frame in the `.calr` file). Preserved code costs more tokens than the C# it wraps (5% to 10% for a file preserved whole, measured by hand in #1746), and Calor's effect, contract and nullability checks do not apply to it.

#### Why

The previous body of this epic described the converter before 0.30:

- It counted 48 unsupported entries. At HEAD bc80daeb the registry `src/Calor.Compiler/Migration/FeatureSupport.cs` has 184 entries: 96 `Full`, 30 `Partial`, 58 `NotSupported`. The committed export `website/public/data/feature-support.json` carries the same counts and is kept equal to the registry by `WebsiteFeatureSupportParityTests.TheWebsiteExportIsTheRegistry` (`tests/Calor.Compiler.Tests/WebsiteFeatureSupportParityTests.cs:239`).
- Record classes (`record`, `FeatureSupport.cs:60-66`) and `lock` (`lock-statement`, `:621-626`) are already `Full`. Three entries listed under #1658 are `Full` and two are `Partial`.
- 23 of the 58 entries were named in no child issue, so "each family converts or has a recorded reason" could not be evaluated.
- The conversion scorecard already reports 100 of 100 snippets fully converted (`tests/Calor.Evaluation/Scorecard/ConversionScorecardTests.cs:31`), so it can act only as a floor: it shows a coverage gain only when a snippet is added.
- The density target depends on how much of a project is native, and the one measurement on record was taken with MediatR and Serilog preserved whole (#1746). The target is therefore read after this coverage work (#1844), not before it.

### #1847 · [0.34] Decision: guard-derived preconditions — which form?

**Action:** new · **Labels:** enhancement · **Depends on:** #1848 · **Blocks:** #1849, #1866 · **Displaces:** decision-only

#### Change

Record one maintainer decision in `docs/plans/0.34-guard-precondition-decision.md`. Converted C# validates its inputs with throw guards (`if (month < 1) throw new ArgumentOutOfRangeException(nameof(month));`); Calor's precondition form is a refinement on the parameter (`int:b | (# != 0)`). The decision is whether, and how, Calor derives anything from guards. The options are compatible, so the record answers each one separately: yes or no for (a) and (c); yes, no or "not now" for (b).

| Option | What it is | What it costs | Follow-up |
|---|---|---|---|
| none (no to all) | Guards stay ordinary body statements. Contracts on converted code come only from authoring (#1843). | Nothing. Converted code contributes no facts and no caller-side obligations. | #1849 and #1866 closed as not planned |
| (a) | Verifier-only facts: after a guard that dominates the rest of the body, the verifier assumes the negated condition for the code that follows. No source change, no runtime change. | One verifier change with seeded unsound and safe controls in the soundness sweep. Helps proofs inside the member only; callers get nothing. | #1849 |
| (b) | An opt-in `calor convert` switch that rewrites a guard as a refinement. Never part of the default (Lossless) path. Limited to leading guards that already throw `ArgumentOutOfRangeException` for one named parameter that the member never assigns. Each lift is recorded in the loss ledger (`ConversionLossKind` and `ConversionLoss`, `src/Calor.Compiler/Migration/ConversionContext.cs:131-193`) under the three conditions below the table. | It puts a non-Lossless switch back on a command from which 0.30 removed `--lossy` as destructive (`CHANGELOG.md:82-83`). Converter work in a 17,630-line visitor (`src/Calor.Compiler/Migration/RoslynSyntaxVisitor.cs`, measured by `wc -l`). The exception message changes; the type and parameter name do not. Callers gain obligations only after call-site obligations exist for class members (#1864, #1863). | #1866, last row of its epic |
| (c) | Let a refinement carry an exception type and a message, so any guard can be lifted. | New syntax, emitter and teaching text; it reverses #1618, which removed `requires` and custom messages one release ago (`CHANGELOG.md:41-50`). | None in this plan |

**Recommendation.** (a) yes. (b) yes only if the guard census (#1848) reads "go"; on "hold" or "not measurable" record "not now"; on "drop" record no. (c) no: this is the recorded default, because #1618 is settled and choosing (c) would need a separate decision that reopens it. Reasons: (a) is the only option that changes no observable behaviour and trips no gate; (b) covers the one class of guard for which a refinement is a faithful respelling, and the census says how large that class is.

**Conditions on (b).** A ledger entry has side effects today that would defeat the acceptance of the lift (Baseline), so a yes to (b) records these three, or states what replaces them:

1. The lift gets a `ConversionLossKind` of its own that is not a semantic loss (or a fidelity value of its own), so that Lossless conversion does not refuse the file.
2. For a file that contains a lift, member-oracle differences are counted before the loss-recorded waiver is applied.
3. Acceptance of a switch-on round-trip run is pass counts equal to the switch-off run. The native fraction of a switch-on run is reported, not gated, because a lifted file leaves the native count.

The record also says whether guards with a custom message or an `actualValue` argument, and `ThrowIf...` helpers, may be lifted; the recommendation is no to both, which is what the `liftable` count of the census assumes.

"Not now" for (b) means #1866 stays open and unstarted until the census is read again from the corpus job at the 0.35 close. The re-read is done under #1866. The record is append-only after sign-off: a later dated maintainer entry may change (b) from "not now" to yes or no, and #1866 reads the latest entry.

#### Baseline (HEAD bc80daeb)

Why a plain lift (every guard becomes a refinement, by default) is not on the list:

- A refinement emits `throw new ArgumentOutOfRangeException(nameof(p), "Violation of ...")` (`EmitRefinementParameterGuards`, `src/Calor.Compiler/CodeGen/CSharpEmitter.cs:6463-6499`). The reference says this happens in every contract mode including `--contract-mode off`, before the body runs, and again whenever the body assigns the parameter (`docs/syntax-reference/contracts.md:37-41`; `docs/syntax-reference/refinement-types.md:17-19`). So it fires before any guard kept in the body.
- A refinement has no custom message; the reference says to keep a body guard when an API needs a particular exception type (`contracts.md:299-301`; `docs/syntax-reference/current-language.md:388`).
- `tests/Calor.RoundTrip.Synthetic/SyntheticLib` has five leading guards, each pinned in `tests/Calor.RoundTrip.Synthetic/SyntheticLib.Tests` by `Assert.Throws<T>`, which requires the exact type. Four throw another type and would fail after a lift: `DivideByZeroException` (`Calculator.cs:23`; `CalculatorTests.cs:41`), `ArgumentException` (`Calculator.cs:30`, `FizzBuzz.cs:19`; `CalculatorTests.cs:56`, `FizzBuzzTests.cs:51`), `ArgumentNullException` (`StringUtils.cs:8`; `StringUtilsTests.cs:23`). Only `DateHelper.cs:18-19` survives (`DateHelperTests.cs:61-62`).
- The member-level oracle (the `member-oracle` CI job, which drives the original and the round-tripped build of each file with generated inputs) compares thrown exception types (`bench/corpus/README.md:223`). Default conversion is Lossless and keeps the original C# when any semantic loss is recorded (`src/Calor.Compiler/Migration/CSharpToCalorConverter.cs:658-662`). `CHANGELOG.md:1905-1906`: "Conversion does not invent defaults, throws, or implicit unwraps."
- On a member that implements an interface, a precondition the interface lacks is the error `StrongerPrecondition` (`src/Calor.Compiler/Verification/ContractInheritanceChecker.cs:1631-1643`). That check runs on every compile whatever the contract mode (`src/Calor.Compiler/Program.cs:979-985`), so the round-trip jobs would show it. What they do not show, because both compile paths run with contracts off and effects unenforced (`tools/Calor.RoundTrip.Harness/RoundTripPipeline.cs:679-680`, `:1598-1599`), is an inherited precondition check or a postcondition check in the emitted C#; #1795 adds the leg that does.

What options (a) and (b) would build on:

- The verifier scopes an `if` condition to the body it guards and gives the code after `if (c) throw` no fact (`src/Calor.Compiler/Verification/Obligations/FactCollector.cs:25-29`, `:561-591`).
- Call-site obligations are generated only in the loop over `module.Functions` (`src/Calor.Compiler/Verification/Obligations/ObligationGenerator.cs:58-62`) and only when every argument is exactly `int` or `bool` (`:120-134`). The converter produces a module-level function only for C# top-level statements (`src/Calor.Compiler/Migration/RoslynSyntaxVisitor.cs:293-308`), so a refinement lifted onto a converted class member creates no caller-side obligation today.
- The contract translator refuses null literals (`src/Calor.Compiler/Verification/Z3/ContractTranslator.cs:836-841`), so a null guard yields no fact under either option.
- Refinement inference exists only for top-level functions (`src/Calor.Compiler/Analysis/ContractInference/ContractInferencePass.cs:43-45`).
- What a ledger entry does today: Lossless conversion refuses a file with any semantic loss (`IsSemanticLoss`, `ConversionContext.cs:190-193`; `CSharpToCalorConverter.cs:1631-1638`) and `calor convert` can select no other fidelity; the member oracle waives every difference in a file whose conversion recorded a loss other than `InteropPreserved` or `EmitterFallback` (`tools/Calor.RoundTrip.Harness/Oracle/OracleRunner.cs:293`, `:399-402`); and a file with any ledger entry stops counting as native (`bench/corpus/README.md:366-367`).

#### Why

Lifting every guard into a refinement during conversion looks like the cheapest way to give converted code contracts. It changes which exception a program throws, which the converter's Lossless rule and the member-level oracle exist to reject, and it creates no caller-side obligation on class members today (Baseline). The question still has to be closed in writing because #1849 and #1866 are conditional on the answer. None of the options changes an existing spelling, so the decision does not belong to the 0.32 breaking window.
