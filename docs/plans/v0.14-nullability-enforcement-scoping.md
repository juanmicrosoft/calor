## 1. Current state (measured 2026-08-20)

Every number regrepped; v1's numbers were audit-flagged and corrected.

- **`str`/`string` are surface aliases canonicalizing to `STRING`** (`Binding/Scope.cs:346`).
  Corpus uses `:string`; predicates in this doc match the canonical `STRING` (not the surface
  spelling), so behavior is invariant across aliases.
- **`STRING` is unenforced.** Calor's type system claims `STRING` is non-nullable
  (`?string` / `?str` is the nullable form). Nothing enforces it today.
  `§B{bad:string} §C{Environment.GetEnvironmentVariable} §A STR:"MISSING_VAR" §/C` binds to
  `null` with zero diagnostics. Reproduced end-to-end in #875.
- **Nullability plumbing exists on `BoundType`.** `BoundType.NullableAnnotation`
  (`src/Calor.Compiler/Binding/BoundTypes/BoundType.cs:53`) has three states:
  `Annotated` / `NotAnnotated` / `Oblivious`. Present on `NominalBoundType`,
  `GenericInstantiationBoundType`, `ArrayBoundType`. Currently every `NominalBoundType`
  defaults to `Oblivious` (`NominalBoundType.cs:111`).
- **`MetadataBinder` reads Roslyn nullability but throws it away.** At
  `MetadataBinder.cs:331-332` it inspects `IMethodSymbol.ReturnType.NullableAnnotation` and
  emits `Calor0271` (`SignatureResolvedNullableOblivious`) as an Info-level diagnostic —
  but does NOT write the annotation into the `BoundType` it produces.
- **Option-B mitigation is live and load-bearing.** `Z3Verifier.cs:50-65` demotes every
  string-involving proof from `Proven` to `Assumed` to prevent unsound elision (D3 hole).
  Comment: *"Lifting it is tracked by #875."*
- **Existing bind-time type checks.** `Binder.BindBindStatement` (`Binder.cs:1067`) already
  emits `Calor0202` (`TypeMismatch`) and `Calor0256` (`BindRebindTypeMismatch`) via
  `AreAssignmentCompatible`. Nullability check would slot into the same site.
- **Corpus surface (`.calr` files only).** `samples/` + `benchmarks/` contain 80 `§B{}`
  bindings total; 42 use `:string` (52.5%). `str[]` count: 0. `List<string>` count: 0.
  `bench/corpus/` is C# submodule content (`MediatR`/`serilog`/`FluentValidation`, all
  `.cs`), so does not add to the `.calr` measurement. Actual initializer-side
  possibly-null sources measured at S1 (kind-classified: literal / Calor expression /
  interop call).
- **Next available diagnostic code.** `Calor0272` (Calor0271 is highest 02XX allocated at
  `Diagnostic.cs:290`).
- **No nullability tests today.** F-1 fixtures cover metadata *shape* of nullable
  parameters/returns but not the enforcement path.
- **Roslyn annotation reliability.** Third-party assemblies without
  `<Nullable>enable</Nullable>` return `NullableAnnotation.None` (Oblivious). BCL is
  fully annotated on .NET 10. Corpus 3rd-party subjects (MediatR / serilog /
  FluentValidation) are annotated.

## 2. Design decisions

**D1 — `NullableAnnotation` on `BoundType` is the ground truth for per-declaration
nullability.** `MetadataBinder` populates it from Roslyn during resolution (fills in
what it currently discards). No new fields on `VariableSymbol`; the annotation rides on
`VariableSymbol.Type` (a `BoundType`) once `VariableSymbol.Type` lands (S2 of this
workstream). Until then, bind sites read from the initializer expression's
`Type.NullableAnnotation`. **Layering:** per-declaration nullability lives on
`BoundType`; per-flow null-state is task #8's `VariableSymbol.NullState` (not
introduced here). The two compose without conflict — this workstream provides the
substrate task #8 will read.

**D2 — Check fires at three sites, keyed by a single predicate defined in one place.**
The predicate `IsPossiblyNullAssignedTo(BoundExpression source, BoundType target)` lives
in a new file `Binding/NullabilityChecker.cs` (or extension method on `BoundType`) and
is called from exactly three sites:

| # | Site | Method | Diagnostic |
|---|---|---|---|
| 1 | `§B{x:string} = <possibly-null>` | `BindBindStatement` | `Calor0272` |
| 2 | `§R <possibly-null>` returning `string` | `BindReturnStatement` | `Calor0273` |
| 3 | `f(<possibly-null>)` where `f`'s parameter is `string` | `ResolveCall` overload-check | `Calor0274` |

Three codes rather than one so suppression granularity is per-site (a project may
choose to suppress bind-time noise but keep return-type strictness). One predicate
prevents drift in nullability reasoning; **architecture test pins that all three call
sites reference the same method symbol** (analog to F-3 anti-drift).

**D3 — Interop annotations are trusted when present, conservative when absent.** For
Roslyn-resolved calls:

| Roslyn returns | Calor treats as |
|---|---|
| `NotAnnotated` | non-nullable (source of truth) |
| `Annotated` | nullable (must be `?string` on the Calor side) |
| `None` / `Oblivious` | conservative: **possibly-null** for the check; emit `Calor0271` Info as today |

The "Oblivious = possibly-null" choice is the conservative-for-safety default and matches
Roslyn's own strict-mode behavior. It IS the migration cost we're taking. See D4 for the
"irremediable-Oblivious" escape hatch that keeps this from blocking Phase B.

**D4 — Migration path is a soft-landing period with a documented escape hatch.**
Because ~42 sites in the corpus likely light up, the enforcement rolls out in two phases:

1. **Phase A (S3 of this workstream):** `Calor0272/0273/0274` are Info-level. Corpus
   scan produces a ratchet baseline (F-1). PR-scoped code changes cannot raise the count;
   migration lowers it.
2. **Phase B (S5 of this workstream):** After the ratchet reaches its **agreed floor**
   (0 for `Annotated` cases; a listed-exception file for `Oblivious`-only cases where the
   underlying API cannot be annotated), the severity flips to Error. This is the F-5
   analog exit criterion for THIS workstream.

**Irremediable-Oblivious escape hatch:** F-1's baseline schema splits the count into
two buckets — `annotated_nullable` (must reach 0) and `oblivious_irremediable`
(third-party APIs the consumer cannot make annotate). The latter has a listed-exception
file at `bench/phase0-agent-native/nullability-oblivious-exceptions.json` with
per-site justification. Phase B's severity flip is gated on the former bucket only.

**D5 — Elision re-enable is gated on ALL string-shaped positions, not just scalar
`STRING`.** The `Assumed`-demotion in `Z3Verifier` stays in place through Phase A.
Phase B's severity flip is what lets the demotion be lifted — but only if string-shaped
positions (`STRING`, `STRING[]`, generic instantiations with `STRING` args) all
enforce non-null. Since v1's D6 explicitly scoped only scalar `STRING`, **the demotion
lift lands in a FOLLOW-ON slice** (not S5 of this workstream) that adds enforcement
for the compound positions. S5 removes the demotion for scalar-only proofs; array/
generic proofs remain `Assumed` until the follow-on slice ships. Explicit sequencing:
demotion-lift PR merges after Phase B **and after** array/generic enforcement.

**D6 — Scalar `STRING` first; other reference-typed positions later.** #875 covers
`STRING` scalar only. Arrays (`STRING[]`, `T[]`), Options (`?T`), Results
(`Result<T,E>`), user reference types (nominal classes/records) all have the same
soundness issue but are OUT OF SCOPE for this workstream. They land as their own
scoping doc(s), likely early in the v0.14 body work after this workstream. **Explicit
non-goal — see §5.** The elision lift (D5) waits on those.

**D7 — SemanticsVersion sequencing (promoted from v1 R4 to a first-class decision).**
The severity flip in S5 requires `SemanticsVersion.Major >= 2` at the file being
compiled, OR no `§SEMVER` directive at all. Precondition: the `SemanticsVersion.Major=2`
bump ships as its own precursor PR before S5, coordinated with v0.14 metadata-binding
F-7. Explicit merge order: [F-7 semantics bump] → [S5 severity flip + scalar-demotion
lift]. S5 no-ops silently for `Major<2` files (backward compat during the migration
window). Cross-references `v0.14-metadata-binding-scoping.md` F-7.

## 3. Slice sequence

**S1 — Corpus measurement + F-1 baseline.** Grep `.calr` files under `samples/` and
`benchmarks/` for `§B{...:string}` sites; classify each by initializer kind (literal /
Calor expression / interop call) AND by projected annotation outcome (annotated_nullable
/ oblivious_irremediable / not_possibly_null). Freeze the count as
`nullability-info-baseline.json` with both buckets. Adds nothing to the binder.

**S2 — Wire nullability from Roslyn into `BoundType`.** `MetadataBinder` populates
`NominalBoundType.NullableAnnotation` from `IMethodSymbol.ReturnType.NullableAnnotation`
and `IParameterSymbol.Type.NullableAnnotation`. No diagnostics yet; verified via unit
tests on F-1 fixtures ("this return produces `NotAnnotated`, this one `Annotated`, this
one `None`"). Simultaneously: `VariableSymbol.Type` is populated so declared-type
nullability is queryable at bind time (currently `VariableSymbol.TypeName` is a string).

**S3 — Phase A: `Calor0272` at bind sites, Info severity.** `BindBindStatement` calls
`IsPossiblyNullAssignedTo` (single predicate, single method); emits `Calor0272` Info
with span on the initializer. Includes the S1 baseline as a ratchet.
**Discriminating pin:** if the Phase-A count in the corpus differs from the S1
baseline by more than 5 in either bucket, the PR must justify each new site.
Architecture-test pin: the three future call sites reference the same predicate method.

**S4 — Return + call sites (still Info).** `BindReturnStatement` gets return-type
awareness (currently has none); `ResolveCall` learns parameter-nullability checking.
`Calor0273` and `Calor0274` codes wire up, calling the same S3 predicate. Ratchet
counts each site type separately.

**S5 — Phase B: severity flip to Error + scalar-`STRING`-demotion lift.** Ratchet's
`annotated_nullable` bucket must be 0 for all three sites AND the SemanticsVersion.Major=2
precursor must be merged before this PR merges. Single PR flips
`Calor0272/0273/0274` to Error (gated on `SemanticsVersion.Major>=2` OR no
`§SEMVER`) AND removes the scalar-branch of `StringModelAssumption` demotion in
`Z3Verifier`. Compound-position (array/generic) demotion remains until the follow-on
slice ships. Required fixture set at
`tests/Calor.Verification.Tests/StringElisionRegression/`: (a) ≥1 scalar-`STRING`
proof that is `Assumed` pre-S5 and `Proven` post-S5; (b) ≥1 that remains `Assumed`
for reasons unrelated to scalar nullability (e.g., array-position). Both ship in the S5
PR.

## 4. Freeze events

**F-1 — Corpus-nullability baseline (S1 measurement point).** JSON file
`bench/phase0-agent-native/nullability-info-baseline.json` at S1 merge, with two
buckets (`annotated_nullable`, `oblivious_irremediable`). Additive PRs cannot raise
either bucket; subtractive amendments require supersession-entry discipline (analog
to v0.14 F-3). The `oblivious_irremediable` bucket is cross-referenced against
`bench/phase0-agent-native/nullability-oblivious-exceptions.json` (per-site
justification file).

**F-2 — Diagnostic code allocation frozen at S3.** `Calor0272` (bind), `Calor0273`
(return), `Calor0274` (call). Reserved even if code lands piecewise.

**F-3 — Phase-B exit criterion.** `annotated_nullable` ratchet reaches 0; severity
flips to Error (gated on SemanticsVersion.Major>=2); scalar-`STRING` demotion
removed. This is the workstream's release-exit-criterion analog to v0.14 F-5.

**F-4 — Roslyn-oblivious handling.** D3 codified: `NullableAnnotation.None` is
treated as possibly-null. If a future PR flips this to "treat as non-null" (more
permissive), that flip requires its own scoping doc and adversarial review.

**F-5 — Predicate-singleness pin.** Architecture test asserts
`Calor0272/0273/0274` emitters all reach the same
`NullabilityChecker.IsPossiblyNullAssignedTo` method (via reflection or dataflow of
`DiagnosticCode` usage). Prevents drift.

## 5. Explicit non-goals

- **Reference types other than scalar `STRING`.** Arrays, Options, Results, user
  classes/records — see D6. The elision lift (D5) is gated on THESE landing.
- **Null-state narrowing** (`x is not null`, pattern narrowing). That's task #8's
  concern (typed CFG null-state slice); this workstream provides the *annotations* it
  will consume via D1's layering.
- **Fixing D12** (Z3 UTF-8-bytes vs .NET UTF-16 code units). Separate divergence; docs
  in `docs/verification-modeled-forms.md`.
- **Migrating .calr files in the corpus to use `?string`.** The Phase-A ratchet drives
  migration via Info diagnostics; humans (or a follow-up automated migrator, task #15)
  do the file edits. This workstream does NOT ship a migrator.
- **Cross-file soundness** for module-boundary types. If a public function returns
  `string` and a caller in another file passes the result to another `string`
  parameter, the check is per-site local. Whole-program null-flow is task #8's territory.
- **Non-scalar-`STRING`-demotion lift.** Only the scalar branch of
  `StringModelAssumption` lifts in S5. Array/generic branches wait on D6's follow-on.

## 6. Risks and mitigations

**R1 — Corpus explosion at Phase A.** If S1 measures >100 sites in `annotated_nullable`,
migration burden is excessive for the Phase-B goal. **Mitigation:** S1 is a measurement
gate. If count exceeds 100, revise D4's Phase-B target from "0" to "≤ N" with
justification.

**R2 — Roslyn Oblivious is more common than expected.** Handled by D4's
`oblivious_irremediable` bucket + exceptions file. If per-site exceptions grow beyond
20, consider a per-file opt-out header (out of scope initially).

**R3 — Lifting Assumed demotion breaks existing proofs.** S5's fixture set (b) is the
positive observation that catches this. If S5 measures a new `Refuted` on a previously
`Assumed` proof, human triage as part of the S5 PR (not deferred).

**R4 — SemanticsVersion coordination.** Handled by D7 promotion — sequencing pinned.

**R5 — Predicate drift across the three call sites.** F-5 pin catches it. If the pin
ever fails, review-round-2 on the diverging code.
