- **FIX** means the verifier now gives the outcome the oracle supports: a true claim is proved, or a
  violated claim is refuted with an input that reaches it.
- **DEMOTE** means the form visibly becomes `Assumed` or `Unsupported` (or is refused), the guard is
  kept, and no claim is made. A demotion withdraws a claim; it does not prove the property.
- **VALIDATED** is used only for the 79 `CLEAN-WITHIN-BUDGET` rows, including the 5 control rows. It
  means "no counterexample within this matrix and budget". Each row records `validatedProofCases`.
  On B1 and N1, 44 of the 79 clean rows have no validated-proof case, including all assumed and
  refused rows. Those 44 rows support no claim that relies on `Proven`/`Discharged`.
- **NOT-INVESTIGATED** is used only for the 7 `XCL-*` rows that the frozen scope excluded.
- A row with findings takes the most conservative disposition among them.

## Spurious refutations

These are not soundness defects. The frozen vocabulary has no "known incompleteness" value, so each
one is fixed or demoted like any other finding.

- **FIX** applies where the model now reaches the obligation or the claim is proved: else facts,
  named-refinement facts, UTF-16 literals, and the Substring range.
- **DEMOTE** applies where the result is `Unsupported` or `Assumed` instead of a `Failed` compile
  error with an unreachable counterexample.

## R-NUM (decision Q1: demote per the frozen table)

The frozen registration classifies three numeric rows:

- `NUM-NARROW-ARITH` and `NUM-LITERAL-OVERSIZE` are `unsupported-refused`. The frozen modeled-forms
  doc lists them as divergences D1 and D2, "refused".
- `NUM-OVERFLOW-CHECKED` is `assumed`.

S1 found `Proven` on all three. Each proof agreed with the oracle, so none is a false proof. Under
the frozen table each is still a finding.

#1502 implements the table exactly:

- narrow arithmetic and negation are refused;
- out-of-range `INT:` literals are refused;
- checked arithmetic that can overflow for some value of its types is `Assumed` even when entailed.

The phrase "unless entailed" is not treated as an exception. Overflow sensitivity is decided
without preconditions, so arithmetic that cannot overflow for any input stays `Proven`. #1502
updates the 15 tests that pinned the old behavior, each justified in the PR. The committed #1135
differential reports do not change.

## Published artifacts (decision Q3: advisory adopted)

B1 (tag v0.22.0) and N1 (the NuGet 0.21.0 package) are immutable. Each disposition is candidate-side:
the change lands on the post-repair candidate (#1423), and the findings stay recorded against those
releases.

The release-notes advisory text is drafted in the record (`baselines.N1.artifact.releaseNotesAdvisoryDraft`).
It is published with the first release that carries the repairs. It distinguishes three mechanisms:

1. **Guard removal.** Obligation and cache proofs could remove a runtime guard that the program
   needed.
2. **Wrong acceptance.** Interface contract checks could accept an implementing precondition that
   throws on inputs the interface allows. No guard is removed, but the acceptance is wrong.
3. **#1493.** A potential, not observed, Windows-only identifier collision.

## Discoveries outside the registered sweep

- **#1493.** On Windows, non-ASCII identifiers can collapse into one Z3 symbol through ANSI
  marshaling, which could produce a false proof. It is `FIX-IN-0.24` by R-TEXT, through an
  injective ASCII symbol encoding. Its end-to-end witness runs on Windows in the
  z3-consumer-matrix job.
- **D-OBL-PROOF-GETTER and D-OBL-THROWING-PREDECESSOR.** These are review-found spurious
  refutations of the obligation solver, never false proofs. They are `DEMOTE-IN-0.24` by
  R-OBL-RESIDUALS (#1503), and the counterexample becomes `Unsupported`.
  - Contract amendment 1.3.0 raises the S2 repair cap 6 → 7, for these two discoveries only
    (decision Q7).
  - The record's `capacity.amendmentAllowance` names the amendment, the repair, and exactly these
    discoveries.
  - The validator accepts the seventh repair while the record is open. At closure it requires the
    amendment in the contract.

## Closure binding

The validator binds each repair mechanically to:

- its pinned PR number;
- an S2 branch;
- a merge commit on main that is GitHub's merge of that PR from that branch;
- its regression witnesses in that commit.

`validatorLimitations` lists the boundaries that stay manual:

- whether a merged PR's contents match its reviewed repair (the maintainer's merge review);
- whether an amendment's text actually covers what the record cites it for;
- the R0 terminal-success validator does not read this record, so `closure.result` is carried into
  the terminal adjudication by hand (Q6).
