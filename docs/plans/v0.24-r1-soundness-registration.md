## 0. What this is and is not

This registers the search for **false-established proofs** in the released verifier: a claimed
property that is false on a concrete input while the verifier reports it unconditionally
established (contract §4: `Proven` non-vacuous, or `Discharged` with a passed non-vacuity check).
It freezes the denominator, the oracle, the case set, the budget, and the rules **before** any
decision-bearing result exists. It does not run the sweep, change the verifier, or authorize a
release. A sweep with zero findings will mean *no counterexample found within this matrix and
budget*, not whole-compiler soundness.

## 3. Channels and observation

Each case runs through the channel of its row, in-process against the baseline's own `calor.dll`
loaded in a collectible `AssemblyLoadContext` (`Program.Compile` bound by name):

- **CH-CONTRACT** — `VerifyContracts = true`, cache off, solver timeout 5,000 ms, compiled twice:
  elision on (the default user path) and elision off. Outcomes come from
  `ContractVerificationResult.EffectiveOutcome`.
- **CH-OBLIGATION** — additionally `VerifyRefinements = true`; outcomes from
  `options.ObligationResults`. This is the path behind `calor_refine` and the public API. At B1 and
  N1 the CLI and MSBuild task do not solve obligations.
- **CH-IMPLICATION** — the always-on inheritance checker (`Calor0815` = `Proven`; LSP-violation errors
  = `Failed`).
- **CH-CACHE** — prime with `calorPrime`, compile `calor` in the same cache directory, then a cold
  compile; the semantics-version row rewrites primed entries to a stale version string in between.
- **CH-CLI-CROSSCHECK** — on control cases only, the baseline CLI's JSON envelope must agree with the
  in-process status; disagreement invalidates the run (a harness defect, not a finding).

If a baseline assembly cannot be loaded in-process, the registered fallback is the CLI (envelope plus
emitted `.g.cs`) and `calor mcp` (`calor_refine`), chosen on the control cases before any sweep case.

Every claim-bearing raw status maps to exactly one contract §4 token from `ProofOutcome`, never from
a legacy enum; an unmapped status is a harness error. Each case has exactly one claim, fixed by the
template's `claimSite` (and `obligationKind` for obligations). Guards are observed in both
emissions: absent with elision only for `Proven` (non-vacuous) or `Discharged` with a guard-free
policy action, and always present with elision off.

## 4. Independent oracle (R1-O1)

The C# oracle text for every case is written by the registrant in `templates.json` and rendered per
case by `SweepCaseGenerator`. It is compiled with Roslyn against **BCL assemblies only** — no Calor
assembly is referenced or loaded — and executed over the case's input domain under `en-US` and the
module's overflow mode. It never calls the verifier's translator, simplifier, emitter, solver, or
cache.

- **forall claims** (postconditions, obligations, implications): for every input where the
  hypothesis holds and the body returns normally, the property must evaluate to `true` without
  throwing. A false or throwing property is a violation. Inputs where the hypothesis or body throws
  are excluded and counted (normal-return semantics, D5).
- **exists claims** (precondition satisfiability): a witness is an input where the property holds.
- **Domains:** exhaustive when every parameter is `bool` or an 8/16-bit integer and the product is at
  most 65,536 inputs; otherwise the per-type boundary table plus 6 seeded values per parameter,
  capped at 4,096 tuples. A sampled domain can show a violation but never establishes truth.
- Where C# defines no semantics (u64 mixed with a signed operand; unary minus on `ulong`), the oracle
  uses exact integers and the row is a refusal or hypothesis row.

**Corroboration (R1-O2).** The baseline's forced-guard emitted C# runs on every O1 witness. O2
executes post-simplification code — `ContractSimplificationPass` rewrites contracts before
emission — so it shares the simplifier's assumptions and is never the sole oracle. An O1/O2
disagreement adds a `semantic-divergence` record; it never changes the O1 verdict.

## 5. Case generation and freeze

Deterministic template expansion: each template has a row, an instance count, holes, Calor text, and
oracle text. Case ids are `R1-<row>-<nnn>`. Each case seeds SplitMix64 with master seed `1419002401`
XOR the first 8 bytes of SHA-256(case id). `cases-index.json` holds the SHA-256 of every rendered
text, and a test regenerates the cases and fails on any byte difference. Control templates carry an
`expectedOutcome`; sweep templates carry none (the oracle decides; checked).

## 7. Execution rules

- **Order:** controls first on each baseline; then round-robin by case index across rows, B1 and N1
  alternating per case. A timebox stop leaves coverage spread, not chosen.
- **Timeouts:** solver 5,000 ms per query (production default); 120 s wall clock per case; 60 s per
  oracle evaluation.
- **Retry:** a `TimeoutOrUnavailable` claim or a crashed/over-time case is retried exactly once with
  identical inputs, charged to the reserve. Both attempts are kept. Disagreeing attempts make the
  case `flaky` (never established). Any `Proven`/`Discharged` attempt with an O1 violation is a
  finding regardless of the other attempt. No third attempt; no run-until-green.
- **Environment:** exact `dotnet --version`, OS, and architecture recorded and fixed per baseline
  sweep; `en-US` culture; no Z3 seed injection (production behavior is under test; determinism
  itself is #1421/#1135); sequential execution.
- **Invalid runs:** a pin mismatch, an SDK change mid-sweep, an oracle control with the wrong
  verdict on the executing machine, a CLI cross-check disagreement, or harness (not compiler)
  crashes above 10% invalidate a run. Invalid runs are archived, never used for row status, and the
  baseline restarts from its first case. A fourth invalid run makes every unexecuted
  release-critical row of that baseline `BLOCKED`.
- **Front-end rejections:** every case lexes and parses cleanly at B1 (checked), so a lexer/parser
  rejection (Calor0001–0199) during the sweep is harness-invalid. A later-phase rejection validates
  a refusal only on an unsupported-refused row.

## 8. Results, row status, and findings

Case result classes (closed): `false-unconditional-proof`, `false-proof-unconfirmed-vacuity`,
`required-demotion-absent`, `guard-elided-without-proof`, `vacuity-mislabel`,
`spurious-refutation`, `stale-cache-proof`, `semantic-divergence`, `candidate-unconfirmed` (all
findings); `validated-proof`, `refusal-validated`, `no-claim`, `harness-invalid`.

The registered **non-vacuity check** for every counted `Discharged` (contract §4 condition 5) is
`R1-O1-reached`: O1 must report at least one input where the hypothesis held and the body returned.

Row status per baseline, mechanically: `FALSE-PROOF` if any false-unconditional-proof; else
`FINDING` if any other finding; else `INCOMPLETE` if any allocated case is unexecuted, harness-invalid
cases exceed 20%, or every executed case of a modeled row timed out; else `CLEAN-WITHIN-BUDGET`
(reported with its counts of validated proofs, refusals, no-claim cases, and exhaustive domains).
Timeouts, `Assumed`, `Unsupported`, and front-end rejections never count as validated proofs.

Each finding is a JSON record (`registration.json` `findingRecord`) with the case hashes, the raw
and mapped outcome, guard observations, witness, O1/O2 results, non-vacuity check, a minimized Calor
case with a standalone C# reproduction, binary and environment hashes, every attempt, the other
baseline's result, the affected guarantee, and an empty disposition for #1413.

## 9. Controls and hypothesis

- **Oracle controls (13, executed in R1):** known-true and known-false C# properties, including
  wrap-around, checked-overflow throws, mixed-sign promotion, shift masking, null strings, culture,
  body-excluded overflow, exists witnesses, and an empty domain.
- **Verifier controls (30 per baseline, executed by #1311):** 8 positive (expected `Proven`), 6
  negative (expected `Failed`, counterexample replayed), 2 mutation pairs (behavior-preserving and
  contract-preserving: oracle verdicts must match; a changed verifier outcome alone is not a
  finding), 4 #845 cases, and 8 post-fix vectors (D3, D4, D8, D11, D14, D15, #807, G1-C1).
- **#845 / PR #961 (retrospective, discriminating):** ULONG bounds near `ulong.MaxValue`, satisfiable
  (expected `Proven`) and violated (expected `Failed`), run on P845, B1, and N1. On P845 the pair must
  show the pre-fix defect; if it does not, the control is reported as non-discriminating, not as a
  pass. #845 stays open.
- **Hypothesis H1 (from R0, not tested):** "`ExpressionSimplifier` folds unary `Negate` and
  `BitwiseNot` over `IntLiteralNode` without checking `IsUnsigned`/`IsLong`." Source reading at B1
  (not execution) shows an early return that gates folding to non-long, signed literals, and that
  `BitwiseNot` is folded although it is not in `ModeledForms.UnaryOperators`. Both are recorded as
  hypotheses for the `SIMP-H1-UNARY-FOLD` row; neither was executed.

## 10. Stopping, amendments, owners, and handoff

- **Stop** at the first of: 10 days after merge, 20 agent-hours, 1,500 case executions, 600 CI
  minutes, 10 local machine-hours. Unreached cases are `not-investigated`; a release-critical row
  with an unreached case is `INCOMPLETE` and therefore `BLOCKED`, unless a reviewed #1407 amendment
  raising the ceiling merges first. Contract §8 stopping conditions apply unchanged.
- A **finding does not stop** the sweep: minimize it from the reserve, file it, continue in order.
- **Amendments** carry a version, UTC time, justification, reviewed PR, and an
  after-decision-bearing-inspection flag. They cannot remove a row or case; removed items stay
  reported with their last status. Cases added after the freeze are `post-registration`: they can
  add findings, never clean status.
- **Owners:** implementation by a Claude Code agent under #1311 (at most 2 PRs; agents never merge);
  review, merge, decision, and amendment authority @juanmicrosoft under the contract's recorded
  independence deviation. The #1311 executor does not edit templates, the generator, or the oracle.
- **Handoff to #1413:** each row on each baseline and each finding gets exactly one of `VALIDATED`,
  `FIX-IN-0.24`, `DEMOTE-IN-0.24`, `NOT-INVESTIGATED`, `MILESTONE-FAILED`. `VALIDATED` only for
  `CLEAN-WITHIN-BUDGET`; `NOT-INVESTIGATED` only for the four excluded rows; a false unconditional
  proof needs a fix or visible demotion within the s2-repairs ceilings, or the milestone fails. A
  retained guard does not cure it. B1 and N1 are immutable releases, so their findings stay recorded
  against them with the candidate-side disposition.

Executed in R1, none of it decision-bearing: the 13 oracle controls (registrant C# only); one Roslyn

unsupported-refused because B1's front end rejects runtime lowering of a nested quantifier
(Calor0326); that is a front-end fact, not a verifier outcome.
