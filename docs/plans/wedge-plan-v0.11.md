## 0. Objective

> **Make per-module Calor adoption consumable by an external team with verification as the leading artifact — and measure, above the authorable-fixture ceiling, whether trustworthy verdicts convert earliness into outcomes.**

Call G's ceiling honesty is this plan's founding observation: on the D5.1 probe fixtures the v0.10 verify gate moved the *channel* (all three contract-class defects surfaced `runtime-guard` → `build-proof`: earlier, attributed, counterexample-bearing) but not the catch *outcome* — the control arm already caught 9/9, because frontier agents at current capability do not ship seeded defects on well-specified tasks of authorable size. Whether earliness converts to outcome differences is measurable only on tasks above that ceiling — real codebases, incomplete specs, generated tasks — which is exactly the parked real-scale design (`real-scale-benchmark-design.md`). The measurement half of v0.11 builds and runs it.

The adoption half is the Wedge as the strategy scoped it: pure/contract-dense modules plus first-order effect-checked code inside an existing C# repo, onboarded per-module, with the review artifact leading with the unproven remainder — now stated in the honest seven-status vocabulary v0.10 built. The audit (§1) shows the verification centerpiece exists and every adoption surface around it does not: no `calor import`, no review packet, no tested eject, no adopter playbook, no consumable SDK package, and every effect-soundness hole from strategy §1.1 still open. That is the product work.

The two halves are deliberately separable: the measurement half needs no adopter; the adoption half's demand question has its own pre-committed kill wording ("demand unproven"). Neither half crosses the one-way door — §6.3 governs the crossing.

Non-goals: Phase 3 items (TIER2D/effect-annotated function types, syntax editions, staged null elimination, floats); frames/`old()` (still default-not-run per the v0.10 register); async/concurrency verification; ghost state/lemmas; the machine-zone M-milestones (separately registered); re-running the parked 2a gate on the authored suite (§8); 1.0.

## 2. Workstreams

Ordering rationale: WS-W1 is prerequisite to both halves — an adopter needs a consumable SDK and honest conversion; the real-scale benchmark needs a trustworthy converter and a failure-safe harness. WS-W2 closes the effect-laundering holes before any external module relies on effect discipline and before real-scale tasks exercise it. WS-W3 is the adoption product work and consumes WS-W1/W2. WS-W4 builds the measurement substrate in parallel with WS-W3. WS-W5 measures, spend-gated, and hosts the calls.

### WS-W3 — The adoption surface (size: L; shed order stated)

- **D-W3.1 `calor import <package>` — effect half.** Productize the existing machinery (`effects suggest` templates, IL derivation for concrete chains, manifest overlay system) into a first-class command per the v4 manifests plan's three tiers: Tier A compile-time IL analysis for concrete chains; **Tier B curated interface-level manifests** (~20–30 framework interfaces — `ILogger`, `DbContext`, `IConfiguration`, `IMediator`, … — annotated at the interface with expected effects, not union-of-implementations); Tier C user supplemental manifests. Every emitted annotation stamps **provenance** (`derived` vs `assumed`); output rides the WS1 envelope. Honest limit unchanged: IL analysis resolves concrete chains, not irreducible dynamic dispatch — unresolved calls are *surfaced*, never silently under-approximated.
- **D-W3.2 `calor import` — contract-synthesis half, scoped.** The v0.10 register deferred this "until WS-G2 lands"; it has. Synthesis enters **only as `Assumed`-provenance output**: signature/nullability-derived contracts (mechanically justified) distinguished from XML-doc/heuristic-derived ones (assumed); nothing synthesized is ever `Proven`, ever elides, or ever enters verification as trusted (M-T1 pins this in CI). Scope decision (which sources, which forms) priced at W3 kickoff; the default is the narrow mechanical set.
- **D-W3.3 Review packet v1 (strategy 2a item 3) — the verification centerpiece's adoption artifact.** A per-change report that **leads with the unproven remainder** over the seven-status vocabulary: statuses + assumption lists (content-addressed, from D-G2.1), vacuity flags, the interop/permissive fraction (D-W2.3), caller impact from the in-memory `CallGraphAnalysis` (available per build), and both waiver disclosures (§5.2 rules). ### WS-W4 — Real-scale benchmark (size: L; the measurement centerpiece)

Per `real-scale-benchmark-design.md`, built at last, with its named open problems assigned:

- **D-W4.1 Task generation (mutation-injection).** For each corpus project with a green suite: derive tasks by reverting a real upstream bug-fix commit or injecting a semantic mutation whose covering test is **removed from the visible suite and moved to held-out**; both arms receive the same failing-behavior report (not the test); held-out = removed tests + the project's full suite (regression net). Escaped bug = held-out failure at declared-done (gates §2 semantics carry over). **Construction order, stated (review C2): mutate-then-convert** — the mutation is applied in the C# source and the converter carries it into the Calor arm mechanically; convert-then-mutate would require hand-porting the defect into Calor, which is authoring asymmetry. **Per-task eligibility predicate, registered at A-1.4 before *epoch* task selection** (ordering per review n3: decided at W4 kickoff, governs dry-run selection, movable by the dry-run per the D4.5 rule, frozen at tranche 2 before the epoch's tasks are selected)**:** (a) the mutated region converts **natively** — not interop-preserved and not in a revert-recovered file (the harness's per-file revert-recovery would otherwise leave the defect in raw C# inside the "Calor" arm, measuring nothing Calor-differentiated); (b) the mutation **survives conversion**, checked mechanically — the removed held-out test fails on both arms' baselines identically. Ineligible tasks are excluded with the exclusion counted and disclosed. **Presentation asymmetry, named:** the Calor arm works on machine-converted `§`-syntax while the C# arm works on the idiomatic original — a bias **against** Calor, so a PP-W2 win is conservative and a loss is confounded with conversion idiom; recorded as an interpretation rule in the A-1.4 entry.
- **D-W4.2 Corpus pinning.** Start from the round-trip corpus (MediatR, Serilog, FluentValidation + Synthetic), **vendored at pinned commits** (the external `--projects-dir` dependency ends — un-pinned corpus = unreproducible epoch); dependency effect manifests via D-W3.1. Corpus bias named honestly: 3 OSS projects, shape-C#-selected (direction-doc postscript) — conclusions scope to "on converted OSS C# codebases of this shape", nothing broader.
- **D-W4.3 Conversion-fidelity gate (consumes D-W1.4).** Per project, per task: the converted arm's baseline suite must be green and coverage above the registered bar **before** any task from that project counts; a defect expressible only through converter-introduced divergence is excluded (attribution rule registered at A-1.4). This is the design sketch's hardest open problem, and it gets a deliverable, not a hope.
- **D-W4.4 Feasibility dry-run — mandatory, no determinism shortcut.** The last two registrations (A-1.2, A-1.3) replaced the D4.5 dry-run with feasibility-by-determinism; that argument is **unavailable here** — real-scale outcomes are agent-behavior-dominated and nothing about them is deterministic-by-construction. A costed dry-run (≥3 runs/arm on ≥5 tasks across ≥2 projects) estimates variance, run cost (full test suites per iteration is the named cost risk), and the achievable MDE **before** any PP-W2 threshold freezes; the dry-run may move the threshold, task count, N, or corpus before freezing — never after. The dry-run's own agent spend is authorized separately, with numbers, via `phase-2-spend-authorisation.md` **before W4's dry-run starts** — it is not covered by the W5 epoch authorization *(review m6)*. **Ceiling-recurrence guard (review M5 — the gates §3.6 analog the real-scale substitutions were missing):** the dry-run must show **C#-arm escaped-bug incidence above a floor frozen at A-1.4** on the dry-run tasks; a relative-reduction threshold is structurally blind to both-arms-at-zero, which is exactly how the authored suite died (strategy §9). Pre-committed branch: incidence ≈ 0 → PP-W2 is **not frozen and not adjudicated**, and the finding is published as **"the ceiling persists at real scale"** — itself a decisive program input, fed to Call W's not-adjudicated branch (§6.2), not a quiet failure.
- **D-W4.5 Calor-arm annotation protocol — the registered fairness decision (review C1).** Converted OSS C# arrives with **no `§Q`/`§S`**; every build-proof result in the v0.9–v0.10 evidence chain ran on fixtures with frozen, authored contracts — so what the Calor arm carries at real scale is a design decision that must be made results-blind, and the frozen gates §3.3/§3.4 authoring-symmetry machinery has no real-scale analog unless this deliverable supplies one. The decision is made at **W4 kickoff** — where it governs the dry-run's task selection and may still be moved by the dry-run per the D4.5 rule — and is frozen in A-1.4 tranche 2 **before epoch task selection** *(the ordering that makes the pre-registration machinery consistent — review n3)*, choosing among (with the constraint set frozen now): **(i) mechanical-only** — the arm carries converted code + effect enforcement + `calor import`-derived annotations only (the product's actual day-one onboarding output; blind by construction; honestly stated consequence: the `build-proof` channel is starved and PP-W2 tests enforcement + runtime-contract value, not proof depth); **(ii) authored-under-blindness** — contracts authored on the converted corpus by a registered rule, **frozen before mutation selection** so no contract can be aimed at a known defect, with the authoring rule and coverage recorded; or **(iii) both, as separately labeled arms** (the arm-C mold). Constraint added to the frozen set *(review n1)*: under mutate-then-convert, each task's Calor arm is a fresh conversion carrying no contracts — options (ii)/(iii) therefore require a **deterministic contract-overlay mechanism** (re-applying the frozen authored set to every task snapshot mechanically) that does not exist today; W4 kickoff prices it as part of choosing the protocol rather than discovering it mid-build. Whatever is chosen, PP-W2's claim wording is **restated at A-1.4 to match the protocol** — the D-G3.1 restate-or-demote precedent: a scope decision may not masquerade as measurement evidence at Call W.

Exit criteria: harness generates ≥ N tasks (N frozen at A-1.4) across ≥ 2 fidelity-passing projects; dry-run complete with a written feasibility verdict; all four design-sketch open problems (coverage bias, manifest gaps, run cost, converter attribution) have recorded dispositions.

## 6. Decision structure

### 6.1 Per-milestone gates

- **W1 kickoff is a scope gate** on the epic subset (D-W1.1 triage may grow the floor; the box moves with it, visibly).
- **PP-W5's guard registers before the strictness batch merges** (control = tag `v0.10.0`); a batch-then-measure ordering would be unfalsifiable in the wrong direction.
- **W3 kickoff prices D-W3.2's synthesis scope**; the shed order in WS-W3 is the pressure valve — D-W3.3/D-W3.4 are never shed.
- **W4 kickoff decides the D-W4.5 annotation protocol**, results-blind, frozen in A-1.4 tranche 2 before **epoch** task selection (it governs dry-run selection from kickoff); PP-W2's wording restates to match (§2).
- **W4's fidelity gate is per-project and rule-driven**: a project failing it is excluded with the exclusion disclosed (no silent corpus shrinkage); if fewer than 2 projects pass, PP-W2 is **not adjudicated** (reported only) and the fidelity work returns to W1-style engineering — a measurement that can't establish its substrate doesn't get to claim its conclusion. The D-W4.4 ceiling-recurrence branch routes to the same not-adjudicated outcome, published as a finding.
- **D-W4.4 may move PP-W2's threshold, task count, N, or corpus before A-1.4 freezes — never after** (the D4.5 rule, applied as a real dry-run this time).

### 6.2 Program-level call

- **Call W (at W5, the v0.11→v0.12 gate):** adjudicated on **PP-W2 + PP-A2 together**; **PP-A1 and PP-W5 are release gates for v0.11.0, orthogonal to Call W's shape decision** — they decide whether v0.11.0 ships as scoped, not what v0.12 looks like *(review M1)*. PP-W2 carries the science weight (the program's headline claim meeting its first adequate venue); PP-A2 carries the go-to-market weight. The PP-W2 input is **four-valued** — hit, miss, underpowered, **not-adjudicated** (sub-2-project fidelity per §6.1, or the D-W4.4 ceiling-recurrence branch) — and every value has a branch: hit + adopter secured → v0.12 is the adoption push, Call 3 crossable per §6.3; hit + no adopter → evidence-led demand-building, door stays closed; miss → the differentiated claim re-scopes (earliness/attribution/cost), v0.12 planning starts from the transcript corpus, door closed; underpowered → the measurement design iterates (variance-informed re-plan) before any claim moves, door closed; **not-adjudicated → the measurement half returns to substrate engineering (fidelity or ceiling, whichever fired) with the finding published, the adoption pair still adjudicates, door closed**. In every branch the program continues — what Call W decides is *shape*, the Call 2/Call G pattern.

### 6.3 Call 3 — the one-way door, governed (the v0.9 §6.3 register's required sign-off)

**What the register requires:** the v0.11 adoption step ("real external teams put Calor modules in production C# solutions") opens only on Calls 1–2 passed (they are) and **explicit sign-off at v0.11 planning**. This section is that sign-off, in deliberately scoped form:

1. **Signed off now (by merging this plan):** executing the adoption *preparation* — WS-W1/W2/W3 in full, the adopter search with its deadline and pre-committed kill wording, and the Wedge's public offer once PP-A1 is green. All of this is two-way work.
2. **The crossing itself is NOT exercised by this plan.** The door is crossed — first external module in production — only when ALL of: (a) PP-A1 green; (b) a named adopter per strategy §1.3 (≥1 non-maintainer reviewer, agreed in writing); (c) the #793 release policy cleared for every surface the adopter consumes; (d) a **dedicated crossing record** (its own PR, the A-1.0 sign-off precedent) stating the adopter, the module scope, the eject commitment, and the maintenance obligations being accepted. Bus factor 1 makes (d) self-asserted, disclosed as always.
3. **Why scoped, recorded:** a planning-time blanket sign-off would let the door be walked through by drift the moment any external team showed interest — the exact failure the register exists to prevent. The one-way costs (migration paths, compatibility promises, maintenance expectations, reputational exposure) attach to a *specific* adopter and module; the sign-off that accepts them must name them. **To prevent misquotation** *(review m9)*: merging this plan does **not** open the door; the v0.9 §6.3 register row remains open until the dedicated crossing record of item 2(d) exists, and any future reading of "explicit sign-off at v0.11 planning — given" must carry this scoping with it.

The register's second row (time at bus factor 1) is re-read here per its own instruction, with the clock stated *(review M7 — v1 wrote "~5 weeks", which was wrong on any clock)*: **realized calendar** from strategy inception (2026-07-01) through Call G (2026-07-30) is ~4.3 weeks, in which the program bought a PROCEED-backed instrument, a sound verifier, and two adjudicated program calls — realized velocity ran far under the plans' calendar boxes (the v0.9+v0.10 boxes sum to roughly 5–8 months depending on how much parallelism is netted out — review n5). v0.11's ~4-month box is therefore the largest single *planned* bet since the strategy was written, read against a program that has so far spent weeks, not months; Call W is deliberately placed to re-read this row with the real-scale answer in hand, on realized time.

## 7. Risks

1. **Two programs in one plan.** The adoption half and measurement half could each fill a version. Mitigation is structural: the halves are separable (neither blocks the other after W1), each has its own shed order and kill wording, and W3/W4 parallelize with distinct deliverable owners (bus factor 1 caveat: "owners" means calendar slices, disclosed).
2. **Real-scale cost blowout.** Full test suites per iteration is the design sketch's named cost risk. Mitigation: D-W4.4 dry-run prices it before any threshold freezes; corpus can shrink to 2 projects; the $1,500/epoch ceiling stands; spend authorized with numbers, per gate.
3. **Converter-attribution confound.** A "Calor advantage" that is really converter-divergence noise (or a Calor *disadvantage* from converter bugs) would corrupt PP-W2 in either direction. Mitigation: the D-W4.3 fidelity gate + attribution rule are registered at A-1.4 before the epoch; sub-2-project fidelity → PP-W2 not adjudicated (§6.1).
4. **Strictness batch breaks real code.** The flip + delegate error will break existing samples, tests, and any downstream user. Mitigation: one coherent batch with migration policy (interop-wrap now honest via D-W2.3; permissive as surfaced waiver); PP-W5 adjudicates the loop tax with a pre-registered control; CHANGELOG-visible.
5. **Adopter stall.** Pre-committed deadline + "demand unproven" wording (§3); the measurement half proceeds regardless; no benchmark conclusion is drawn from a BD outcome.
6. **Audit-epic underestimate.** The blocking subset may be larger than the W1 floor. Mitigation: D-W1.1 triage at kickoff corrects the box visibly; the epic's own phases stay the backlog of record (this plan does not absorb the epic — it consumes its adoption- and benchmark-blocking subset).
7. **Fixture/corpus meaning drift.** Real-scale tasks derived from live OSS repos can drift (upstream moves, tests flake). Mitigation: D-W4.2 vendored pinning; task determinism checks per gates §0.2 (5-green rule) applied to held-out suites at authoring.
8. **Bus factor 1 / self-asserted approvals.** Unchanged, disclosed; A-1.4 freezes, the §6.3 mechanics, and any crossing record are maintainer-approved via PR, recorded as such.
